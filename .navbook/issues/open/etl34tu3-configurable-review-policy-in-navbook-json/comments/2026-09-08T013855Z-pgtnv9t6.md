Done, across `core`, `cli`, `server`, `web`, the specification and the conformance fixtures.

The shape that survived the build: `parseTree` hangs the reading on every `Repo`, and `reviewSummary` takes the policy — so the decision a listing shows, a `show` shows, the `review:` query filters on and the API serves is one reading of one rule. The defaults reproduce §2.7 exactly, and no existing conformance expectation moved, which is the evidence for that rather than the claim.

Two things the first pass had wrong, both found by trying it rather than by reading it:

- `show` hid the decision whenever nobody had been asked. Right for a repository counting one approval, wrong for one counting two: under a policy wanting more, the policy *is* the ask, and the count was the only thing standing in the way. The web badge already said so, so this was also the two front ends disagreeing.
- `readReviewPolicy` opened the marker directly, so a path that is not a readable file threw where a listing should have carried on. It now reads as no marker at all — which is what `readNavTree` already concludes, since it walks files. A repository whose `doctor` and whose `pr list` disagreed about whether a policy exists would be worse than one quietly counting by the defaults.

The advisory promise is kept structurally, not by discipline. The merge decision is a pure function over three booleans, tested across all eight combinations, and the only outcome that can end in a merge not happening is the one reachable when somebody is at a terminal to say no.
