## Implementation plan

Taking the shared fix rather than the local one: every numeric flag in the CLI moves to a parser that refuses at parse time, so the class of bug closes rather than this one instance of it. Four flags, one helper, and a deliberate change to what a bad value prints.

### 1. The helpers — new `packages/cli/src/args.ts`

Commander's documented mechanism is to throw `InvalidArgumentError` from the custom parser; commander catches it and turns it into its own usage error, so the value never reaches the command.

```ts
/**
 * Numeric option values, refused where they are read.
 *
 * Commander catches `InvalidArgumentError` from a parser and reports it as a
 * usage error, so a bad value never reaches a command — which is what keeps a
 * flag's validation beside its declaration rather than in whichever command
 * happens to read it, and is why `nav feature show --commits 2.5` used to
 * report an empty history instead of a mistake (#kw143sq9).
 *
 * Each takes the noun so the message names the unit: "takes a whole number of
 * levels" reads better than a shared "takes a whole number", and the words are
 * the ones the commands already used.
 */
export function wholeNumber(unit: string): (value: string) => number {
  return (value) => {
    const parsed = Number(value);
    if (!Number.isInteger(parsed) || parsed < 0) {
      throw new InvalidArgumentError(`takes a whole number of ${unit}`);
    }
    return parsed;
  };
}

/** A position rather than a count: any finite decimal, negatives included (spec 02 §2.5). */
export function finiteNumber(): (value: string) => number {
  return (value) => {
    const parsed = Number(value.trim());
    if (value.trim() === "" || !Number.isFinite(parsed)) {
      throw new InvalidArgumentError("must be a number");
    }
    return parsed;
  };
}
```

`--rank` needs its own shape and must not be folded into `wholeNumber`: spec 02 §2.5 allows "any finite decimal … negative values included", and `rank: 0` has to survive — which is why `newIssueFile` asks whether one was *given* rather than whether it is truthy.

### 2. The call sites — `packages/cli/src/program.ts`

```diff
-    .option("--commits <n>", "recent commits to list (default 10)", (value) =>
-      value.trim() === "" ? Number.NaN : Number(value),
-    )
+    .option("--commits <n>", "recent commits to list (default 10)", wholeNumber("commits"))

-      command.option("--depth <n>", "levels of subtasks to render (default 1)", (value) =>
-        value.trim() === "" ? Number.NaN : Number(value),
-      ),
+      command.option("--depth <n>", "levels of subtasks to render (default 1)", wholeNumber("levels")),

-    .option("--rank <n>", "where it sits in the queue; lower first", (value) =>
-      value.trim() === "" ? Number.NaN : Number(value),
-    )
+    .option("--rank <n>", "where it sits in the queue; lower first", finiteNumber())

-    .option("-n, --count <n>", "how many IDs to print", (value) => Number.parseInt(value, 10), 1)
+    .option("-n, --count <n>", "how many IDs to print", wholeNumber("ids"), 1)
```

`-n/--count` additionally needs `>= 1` rather than `>= 0`; either give `wholeNumber` a minimum or keep `mintIds`' own check, which already says `--count must be a positive integer`. Keeping it is fine — a count of 0 reaching the operation is harmless — but refusing at parse time is the point of the exercise, so a `wholeNumber(unit, { min: 1 })` is worth the extra parameter.

### 3. What downstream can then be deleted

- `packages/cli/src/commands/entity.ts`, `cmdShow`: `if (!Number.isInteger(depth) || depth < 0) fail(…)` — unreachable, remove.
- `packages/cli/src/commands/issue.ts`, `cmdIssueOpen`: the `--rank`/`Number.isFinite` check — remove. Keep the `--deadline` check, which is a calendar-date question and not a numeric one.
- `packages/cli/src/commands/feature.ts`, `cmdFeatureShow`: `const limit = opts.commits ?? 10;` stays; the `if (limit > 0)` guard stays too, because `--commits 0` is a legitimate request to omit the history (spec 04 §4.3).
- `packages/core/src/ops/init.ts`, `mintIds`: keep its `Number.isInteger` check. It is an exported operation the server could call, and core must not rely on a front end having validated anything.

### 4. The behaviour change, which is the part to agree on

Today a bad value is a `NavError` and prints one line to stderr:

```
nav: --depth takes a whole number of levels
```

After this it is a commander usage error. Verified against the version in the lockfile:

```
error: option '--depth <n>' argument 'abc' is invalid. takes a whole number of levels

Usage: nav show [options] <id>

Options:
  --depth <n>  levels of subtasks to render (default 1)
  -h, --help   display help for command
```

Exit code is unchanged — commander's `invalidArgument` carries `exitCode: 1`, and `main.ts`'s `report()` maps any non-zero `CommanderError` to 1, so spec 04 §4.2's "1 operational error" still holds.

The full help block comes from `.showHelpAfterError()` on the root program, and it is arguably too much for a mistyped number. Two options, and this is a judgement call worth making explicitly:

- **Leave it.** Consistent with every other usage error the CLI already produces (`nav issue` with no verb, an unknown flag), which is an argument in itself.
- **`.showHelpAfterError("(run with --help for usage)")`.** One line instead of a block, applied to *every* usage error in the CLI — so it is a wider change than this issue, and should be its own decision if taken.

My recommendation is to leave it and keep one behaviour for usage errors.

### 5. Tests

Two existing assertions pin the old message and must move:

- `packages/cli/test/cli/issue.test.ts:753` — `assert.match(result.stderr, /--rank must be a number/, value)`
- `packages/cli/test/cli/links.test.ts:475` — `assert.match(result.stderr, /--depth takes a whole number/)`

Both still match if the regexes are loosened to the new phrasing (`/--rank.*is invalid.*must be a number/`), which is the smaller edit and keeps the intent visible.

New cases, in `packages/cli/test/cli/feature.test.ts` beside the existing `--commits 0`:

```ts
for (const value of ["abc", "2.5", "-1", ""]) {
  it(`refuses --commits ${JSON.stringify(value)}`, () => {
    const result = repo.nav(["feature", "show", "auth", "--commits", value]);
    assert.equal(result.code, 1);
    assert.match(result.stderr, /--commits/);
  });
}
```

`2.5` is the case that matters most: it is the one that currently exits 0 and reports `recent commits (0)` when there are commits.

**No conformance fixture pins any of these messages** — I checked; the three fixtures that mention these flags use valid values. So the suite needs no change, and none of this is a format-level behaviour.

### 6. Order of work

1. `args.ts` with unit tests for the two helpers.
2. `program.ts` call sites; delete the four downstream checks.
3. Update the two existing assertions; add the `--commits` cases.
4. `pnpm --filter @navbook/cli test`, then `pnpm check` and `pnpm test:conformance`.

### Risks

- **Scripted callers reading stderr.** Anything grepping for `nav: --depth …` breaks. The audience is small and the exit code is unchanged, so a release-note line covers it.
- **Over-correction.** `--commits 0` and `--rank 0` and `--rank -3` must all still work; the tests above and the existing `--commits 0` case are what keep that honest.

### Done when

`nav feature show auth --commits 2.5` exits 1 with a message naming the flag, `--commits 0` still omits the history, `--rank -3.5` still opens an issue, and no command body re-checks a value commander already refused.
