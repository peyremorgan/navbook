## Implementation plan

Landing on `dev` now, independent of the plugin tooling: D15 is a format check a conforming tree is judged by, it runs under `--staged`, and it is what the conformance fixtures assert. The `worktree-plugins` branch will want the *reading* this adds (`repo.plugins.declared`) rather than having to add its own, so doing it here is a head start rather than a conflict — see the merge note at the end.

### 1. The parser — `packages/core/src/core/policy.ts`

A third parser beside `parseReviewPolicy` and `parseMergePolicy`, deliberately their mirror image so all three fail the same way.

```ts
/* ------------------------------------------------------ plugin declaration */

/**
 * What a repository says its tree contains — spec 02 §2.12.
 *
 * Data about the tree, never instruction to a tool: a name here is read to
 * report what is missing, and is never permission to fetch or execute
 * anything. That rule lives in the tool; what lives here is the shape.
 */
export interface PluginDeclaration {
  /** Each extension's name, and the settings it carries. */
  plugins: Record<string, Record<string, unknown>>;
}

export const NO_PLUGINS: PluginReading = { declaration: { plugins: {} }, declared: false, problems: [] };

export interface PluginReading {
  declaration: PluginDeclaration;
  declared: boolean;
  problems: string[];
}

export function parsePluginDeclaration(markerText: string | undefined): PluginReading {
  if (markerText === undefined) return NO_PLUGINS;

  let marker: unknown;
  try {
    marker = JSON.parse(markerText);
  } catch {
    return { ...NO_PLUGINS, problems: ["is not valid JSON"] };
  }
  if (!isPlainObject(marker)) return { ...NO_PLUGINS, problems: ["is not a JSON object"] };

  const declared = marker.plugins;
  if (declared === undefined) return NO_PLUGINS;
  if (!isPlainObject(declared)) {
    return { ...NO_PLUGINS, problems: ["'plugins' must be an object"] };
  }

  const problems: string[] = [];
  const plugins: Record<string, Record<string, unknown>> = {};
  // Key order, so two faults are reported in the order somebody reads them.
  for (const [name, settings] of Object.entries(declared)) {
    if (isPlainObject(settings)) plugins[name] = settings;
    else problems.push(`'plugins.${JSON.stringify(name)}' must be an object`);
  }
  return { declaration: { plugins }, declared: true, problems };
}
```

Three details that are not arbitrary:

- **The key's grammar is not checked.** §2.12: the key "is the extension's own name for itself", and "a second implementation naming its extensions some other way is conforming so long as the names agree". The `^[a-z][a-z0-9]*$` short-name grammar governs the *namespace* a plugin occupies in the tree, not the marker key. Validating it here would reject `@navbook/plugin-kb`, which is the spec's own example.
- **Falling back means declaring nothing**, per key as well as overall — a marker with one good entry and one bad one reports the bad one and keeps the good one, exactly as `review` falls back per key.
- **The settings' contents are not validated.** §2.12 says they are "committed, shared and non-secret" and carry "whatever settings that extension reads" — there is nothing a general validator could check. That is what the `X-<short>-<n>` check namespace of spec 04 §4.3 is for.

### 5. Conformance fixture — `doc/spec/fixtures/format/invalid/d15-plugins/`

This is the deliverable that holds a second implementation to the same answer, and it is the part that cannot be inferred from the prose. Modelled on `d15-merge-policy/`:

`case.yaml`:
```yaml
spec-version: 1
description: D15 rejects a plugins declaration that is not an object of objects
init: {from: tree, date: 2026-09-02T12:00:00Z}
run: {command: [doctor, --json]}
expect:
  exit: 2

    - {check: D15, level: error, path: .navbook/navbook.json}
```

`tree/.navbook/navbook.json`:
```json
{
  "version": 1,
  "plugins": ["@navbook/plugin-kb"]
}
```

plus the five `.gitkeep` files the sibling fixtures carry.

A second fixture is worth it, because §2.10 says "D15 reports one diagnostic per fault it finds, so a marker that mistypes two of its policy keys names both" and nothing currently proves that across *different* keys:

`d15-two-faults/` — a marker with `"plugins": {"kb": true}` and `"review": {"minApprovals": 0}`, expecting two D15 diagnostics.

### 6. Unit tests — `packages/core/test/policy.test.ts`

Beside the existing review and merge cases: no marker, no `plugins` key, an array, `null`, a value that is not an object, a well-formed declaration, and a marker that is not JSON at all (asserting the fault is reported once, not three times, via `validateRepo`).

### 7. Order of work

1. `policy.ts` + its unit tests.
2. `tree.ts`, `validate.ts`, `workspace.ts`.
3. The two fixtures; `pnpm test:conformance`.
4. `pnpm check` and the full suite.

### Merge note for `worktree-plugins`

That branch will touch `policy.ts`, `tree.ts` and `validate.ts` for the same reason. To keep the merge cheap, this change should confine itself to **reading and reporting** and add nothing about loading, resolving or installing — no `navbook` manifest parsing, no store path, no version negotiation. If `worktree-plugins` has already written its own `plugins` reading, the right resolution is to keep this one (it is the one the fixtures assert) and let that branch build its loader on top of `repo.plugins.declaration`.

### Done when

`nav doctor` on a marker with `"plugins": ["@navbook/plugin-kb"]` reports one D15 error and exits 2; a marker mistyping both `plugins` and `review` names both; `nav doctor --staged` catches the same before a commit lands; and `pnpm test:conformance` passes with the new fixtures.
