Confirmed on `dev` (25a7cbc) with a new Playwright spec, `packages/web/test-e2e/wrong-kind.spec.ts`, run against a `nuxi generate` build of unfixed code. Both directions fail the same way. What the page renders for `/prs/aaaa0001` (an issue in the e2e fixture):

```yaml
- main:
  - text: That is the other kind of thing
  - paragraph: "#aaaa0001 is an issue — use 'nav issue show'"
  - button "Try again"
```

and for `/issues/bbbb0001` (a pull request): `#bbbb0001 is a pull request — use 'nav pr show'`, then the same "Try again".

**Repro:** `pnpm --filter @navbook/web dev:stack`, sign in, open `/prs/<id of any issue>`.

**Why it happens:**

- `pr(ref:)`/`issue(ref:)` resolve the id through `resolveEntity` in `packages/core/src/workspace/resolve.ts`, which raises `wrong-kind` when the id names the other kind. The server maps that to `WRONG_KIND` verbatim (`packages/server/src/errors.ts`).
- Both detail pages (`packages/web/app/pages/prs/[ref].vue`, `issues/[ref].vue`) hand every query error to `QueryState.vue`. It shows `errorHeading(code)` (`WRONG_KIND` → "That is the other kind of thing", `app/utils/errors.ts`), the server's message, and one "Try again" action that refetches. That can never succeed: the id's kind will not change.
- The message is also written for the CLI. Its advice ("use 'nav issue show'") means nothing in a browser.

**Suggested fix:** it stays in the client. The page knows which kind it asked for and the reference it was given, so on `WRONG_KIND` it knows the right route (`/issues/:ref` ↔ `/prs/:ref`). `QueryState` can take the kind it asked for and, for `WRONG_KIND`, replace the retry with a link to the other page and the CLI hint with a sentence that makes sense in a browser. The `/ref/:ref` resolver already reads `WRONG_KIND` this way to redirect.
