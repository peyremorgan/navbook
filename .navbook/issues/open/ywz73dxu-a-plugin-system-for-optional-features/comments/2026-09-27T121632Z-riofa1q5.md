**What needs deciding**

1. **Names that don't follow the rule.** 02 §2.12 says `specs/` and `feature:` are grandfathered and "no extension may claim either name". But the example manifest in `doc/plugins.md` declares `"short": "kb"` with `format.root: ["specs"]` and `frontmatterKeys: ["feature"]`. Neither `specs` nor `feature` fits the `<short>/` or `<short>-*` pattern for the short name `kb`. P1's registry needs a rule for this. Options:
   - (a) A carve-out allowing only `@navbook/plugin-kb` to register those two names.
   - (b) Core keeps reading and checking `specs/` and `feature:`. The plugin only adds the commands and UI on top.
   - (c) Relax the grammar for names the spec itself defines.
2. **D13/D14 or X-kb-1.** 04 §4.3 says D13/D14 stay D-numbered and are reported "either way" (by core or by a plugin). `doc/plugins.md` gives the same check as `X-kb-1 "the layout and schema of specs/"`. One of the two documents has to change.
3. **A repository using the knowledge base without the plugin installed.** After P6, a `nav` without the plugin would stop reporting D13/D14. The conformance fixtures assert those checks, and this repository uses `.navbook/specs/` itself (16 features). Options:
   - (a) `@navbook/cli` depends on `@navbook/plugin-kb`, so the plugin is always there by default.
   - (b) The plugin must be installed explicitly. Then `nav` needs a warning along the lines of "specs/ is present but @navbook/plugin-kb is not declared or installed", and the fixture runner has to install the plugin.
   - (c) Option (b) under point 1, which avoids this problem.

The phase ordering does not depend on these answers: P1 → P2/P3 → P4 → P5 → P6.
