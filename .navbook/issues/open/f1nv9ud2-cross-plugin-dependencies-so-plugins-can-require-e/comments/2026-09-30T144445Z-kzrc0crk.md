Notes from building `@navbook/plugin-tests` (#z9yqtsbv, pull request `nbo2fvc9` on `feat/z9yqtsbv-plugin-tests`) beside `@navbook/plugin-kb`. They cover how the hosts find plugins today, where plugins already touch each other, and what tests and kb would need to work together. #l2xyp1u5, attaching test plans to features, is the concrete case this issue should be able to serve.

## How a plugin's features are found today

- **Declared, then loaded lazily.** Each part of the host reads the `navbook` block of `package.json` without importing plugin code. A verb loads a plugin only when the plugin changes that verb's run. The plugin-tests branch fixed a gap here: a plugin that only offers completions to `pr list` used to be loaded to list pull requests, and now is not. An import trace test in plugin-tests guards this. Any dependency mechanism has to resolve from manifests alone, or it breaks this rule.
- **Three ways to find a plugin.** The CLI and server look at `NAVBOOK_PLUGIN_PATH`, then the store `nav plugin install` fills. The repository's `plugins` declaration says what a tree uses. The web client is decided at build time by `NAVBOOK_WEB_PLUGINS`, because a layer is compiled in. A dependency graph therefore has to be resolved in three places, and the web one cannot change at run time.
- **Namespaces are mapped by hand.** When a tree holds `specs/` or `tests/` without a declaration, the CLI names the plugin it belongs to from a hard-coded table in `hint.ts`. The manifests already declare `format.root` and `format.entityDirs`, so the table could be derived. It cannot name a plugin that is not installed, though, and that is the one case the hint is for.
- **Versions are checked, but only against the host.** A plugin carries `engines.navbook`, a range over `PLUGIN_API_VERSION`, and `@navbook/core` as a peer. plugin-tests needed new host seams, so the branch bumps the API to 1.1.0 and asks for `^1.1.0`. Nothing checks one plugin's range against another's. The API image now checks core peers after install, in `check-plugin-peers.mjs`, and that script is a natural place to check plugin-to-plugin ranges too.
- **The web layer merges, and nothing more.** A layer's pages exist once it is merged. It appears inside the host only by registering with `useNavbookSlots()`: nav links, panels, row badges, filters, listings and cache policies. Panels and filters are typed to the nouns `issue` and `pr`, so no plugin can add a slot for a noun another plugin defines, such as a feature.
- **Generated types stop at each package.** Each layer runs its own codegen against the server schema plus its own SDL. So plugin-tests' generated types cannot mention kb's `Feature`, even when both are installed. A web integration between two plugins needs each one's SDL visible to the other's codegen.

## Where plugins already interact

- **Registrations collide, and the host refuses them.** `mergeExtensions` reports two plugins claiming one tree directory, entity directory, frontmatter key, query term or check ID. On dev it also refuses names the format reserves. That is enough to keep plugins apart, but it gives them no way to cooperate.
- **`entity.ext` is readable by everyone.** An entity location stores its model on the record under its directory name, `entity.ext.get("tests")`. Nothing stops kb from reading tests' model, or the reverse. That is an undeclared, unversioned dependency, which is exactly what this issue wants to replace.
- **Query terms see only the entity.** A query key's `matches(values, entity)` gets no tree, deliberately, because a listing may be reading entities from another branch. So a term that combines two plugins' data only works if both put their data on the entity itself. That is why `tested:` reads runs through an entity location. A term like "PRs whose feature has a failing plan" cannot be written today.
- **JSON keys and GraphQL fields share one namespace.** `pr show --json` merges every plugin's `jsonExtra`, and dev now drops any key the entity already has. Two plugins adding the same key still silently overwrite each other. On the server, kb and tests both `extend input PrFilter`. Different fields merge fine, and the same field would fail at schema merge with no hint of which plugin to blame.
- **Contributions only reach built-in verbs.** A plugin can add a section to `pr show`, options to `issue open`, or completions to `pr list`. It cannot add to another plugin's verbs, such as a "test plans" section on `nav feature show`.
- **Host API changes ripple through every plugin.** #yp56dc43 replaces the server's `writeTarget` with `writeEntity`, and plugin-tests uses `writeTarget`. #kw6afa4a gives server plugins `host.api.execute` to run operations against the composed schema. That is already a cross-plugin surface in practice: a plugin can call another plugin's resolvers through GraphQL without importing it.
- **Adding a plugin means editing many host files.** plugin-tests had to touch both Dockerfiles, the image's install filter, the release loop, publish steps and smoke test, the web package scripts and devDependencies, the e2e stack's plugin list, the dev stack and the e2e fixture. `@navbook/plugin-chat` (#c43a2w7e) hit the same list at the same time, and #uniyh2hy carries notes on which branch adds what. The deploy tests now enumerate `packages/plugin-*` rather than naming kb. The other lists could be derived the same way before a dependency graph adds edges to them.

## What tests and kb need to work together

The goal is a test plan that names the feature it covers, with the features pages able to say how well tested a feature is. Here is each gap, and the seam that would close it.

1. **A plan cannot carry `feature:` today.** kb registers `feature` as a frontmatter key for the kinds `issue` and `pr`. A plan is a record in plugin-tests' own tree location, not an entity, so the key registry never sees `plan.md`. tests also cannot register its own `feature` key: that would be two plugins claiming one key. What is needed is for kb to publish membership as an extension point, for example "a plugin may declare records that belong to features". tests would then declare its plans, and kb would own the key's grammar and its D14 dangling-reference check for them.
2. **tests would need kb's feature list.** To validate or complete `feature:` on a plan, tests needs kb's list of features. Today that means importing kb's `./core` or reading its tree model by directory name. It should be a published, versioned surface from kb, reachable only when the dependency is declared.
3. **Both CLI directions need a new seam.** In one direction, `nav feature show <slug>` would list the plans covering the feature and their latest outcomes, and `nav feature list` could show a tested column. That needs contributions to another plugin's verbs. In the other direction, `nav test open --feature` and `nav test list feature:x` belong to tests, but can only exist when kb is present. That is the optional-dependency case: the option is declared in the manifest and switched on by kb's presence.
4. **The server needs an optional schema.** `extend type Feature { testPlans: [TestPlan!]! }` is only valid when kb's SDL is merged. The manifest could name a second schema file that is loaded only when a named plugin is present. The same applies to `TestPlan.features` and a `feature` argument on `testPlans`.
5. **The web client needs slots on other plugins' pages.** A test plans panel on kb's feature page needs slot nouns that plugins can define, so kb would offer a `feature` noun. The structured plan editor would need a feature picker built on kb's queries, and so would need kb's generated types. The same goes for a "feature" filter chip on `/tests`.
6. **The files must stay valid without either plugin.** A plan written with `feature: login` must stay valid, and doctor-clean, when kb is removed. tests' spec already preserves unknown keys, so this holds today. It stops holding as soon as tests validates the key itself. The rule should be written down: a dependent validates another plugin's data only through that plugin, and says nothing when it is absent.
7. **Useful cross-plugin readings.** Once plans name features, a feature's tested state can be read the way a pull request's is: the outcome of the newest run of each covering plan. So can "open pull requests on this feature whose tested state is failed". The second combines kb's `feature:` and tests' `tested:`, which already works on `nav pr list feature:x tested:failed`, because both live on the entity. Only the feature-level reading needs the new seams.
8. **The deferred export needs the same surface.** #w5m6r8im, CTRF and Xray export, would carry the feature as a requirement link, and Xray models that directly. It needs the same published surface from kb, not a second private reading of `specs/`.

**A suggested order.** Manifest-declared dependencies with ranges, checked where core peers are checked now. Then a published-surface API that a plugin receives at activation, carrying the dependency's version. Then slot nouns and contribution targets that plugins can define. Each is independently useful, and together they are enough to deliver #l2xyp1u5 without either plugin importing the other.
