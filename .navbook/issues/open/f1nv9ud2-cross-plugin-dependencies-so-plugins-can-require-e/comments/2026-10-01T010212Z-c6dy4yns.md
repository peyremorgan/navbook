The design, decided in an interview after the research above and a survey of other plugin systems (VS Code, IntelliJ, OSGi, Fabric, NeoForge, Factorio, Paper, Debian, npm/pnpm, Nuxt, Vite, Jenkins, WordPress). Subtasks carry the phases: #q85rhz8l spec and docs, #zbw7nh43 core, #ulukw5vr CLI, #ij3xw87w server, #xjerfwj0 web, #gpa8kdxl kb as the first provider. Deriving the hard-coded plugin lists is #ra3cek1n.

1. **Where.** In the plugin's own `navbook` manifest block, keyed by full package name, so every host can resolve from manifests without importing code. npm `peerDependencies` may mirror an edge but are not the source of truth: the store installs with `--omit=peer`.
2. **Grades.** Five, as in Fabric: `depends`, `recommends`, `suggests`, `conflicts`, `breaks`, each `{ "<package>": { range?, reason?, with? } }`. A name sits under one grade only.
3. **What each grade does.**
   - `depends`: when the provider is absent or out of range, the dependent is skipped by the CLI, refused by the server and fails the web build, with the reason.
   - `recommends`: when the provider is present and in range, the `with` fragment lights up. When it is absent, nothing happens at run time, and `nav plugin install` offers it as a separate opt-in. When it is out of range, the fragment stays off with one warning.
   - `suggests`: lights up the same way, but is never offered and never warned about.
   - `conflicts`: when both are present, one warning, and both load.
   - `breaks`: when the named plugin is present, the declaring plugin is skipped or refused.
4. **Ranges** are npm ranges over the provider's package `version`, read by `satisfiesRange`. The host gate, `engines.navbook`, is unchanged.
5. **Presence.** The CLI now loads declared plugins plus `NAVBOOK_PLUGIN_PATH`, as the server does, so the two agree on what "present" means. One pure resolver in core, `resolvePluginGraph`, runs in every host over that host's set and iterates to a fixed point, so a dropped provider drops its dependents.
6. **Order.** A stable topological order, provider first along every `depends`, `recommends` and `suggests` edge, with ties kept in declaration order. Contributions merge in two phases: every base contribution, then every fragment. Any cycle is refused, and the message names the path.
7. **Surface.** A part's `activate(host)` may return its API. Dependents read it with `host.plugins.get(name)`, which refuses a name the manifest does not declare. Types come from a provider's types-only `./api` subpath through `import type`. GraphQL `api.execute` stays a complement, not the mechanism.
8. **Fragments.** `with: { core?, cli?, server?: { schema }, web? }` is merged only when the provider resolved. Its code lives in `./with/<provider-short>/<part>` entries exporting `activate(host, provider)`, which load only then and lazily. A fragment that fails loses only itself. `short` must be unique across the loaded set.
9. **Provider-owned extension points** are in scope. A CLI contribution may target any command path, another plugin's verbs included, along a declared edge, and the provider reads them with `host.contributions(path)`. Web slot nouns are open strings, so a provider can register `feature` and render `<NavbookPanels noun="feature">`.
10. **Web.** `webLayers()` runs the same resolver over `NAVBOOK_WEB_PLUGINS` and fails the build with the server's wording. It extends base layers, then fragment layers, and exposes the set as `useNavbookPlugins()`.
11. **Doctor.** D17, *the plugins declaration is not closed under its dependencies*. It is an error for an undeclared `depends` target or a declared `breaks` pair, and a warning for a declared `conflicts` pair. It reads manifests only and is silent for a plugin that is not installed. The rule that an extension validates another's data only through that extension goes into §2.12, enforced by such checks living only in fragments.
12. **Deploy.** `check-plugins.mjs` in the API image runs the resolver after install. The web image fails through `webLayers()`.
13. **API version.** A minor bump. A plugin that uses the new keys must exclude older hosts through `engines.navbook`, because an older host drops unknown manifest keys and would load it unchecked.
14. **`nav plugin`.** `install` works in rounds, since a manifest only arrives with its package: required dependencies are planned and asked for, and recommended ones are asked for separately (`-y` never takes them). `breaks` warns. `remove` names the plugins it leaves without a provider. `list` shows every edge and its state.
15. **First users.** kb is the first provider. The consumers are test fixtures until plugin-tests builds on kb in #l2xyp1u5.
16. **Delivery.** One subtask, branch and pull request per phase.
