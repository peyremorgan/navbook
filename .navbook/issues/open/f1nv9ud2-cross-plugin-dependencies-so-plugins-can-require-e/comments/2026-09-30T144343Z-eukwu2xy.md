Research notes from building the Changes tab's tracker timeline (#tj3a28x6, merged as #qjxo5qqd), and from rebasing it over the plugin-kb extraction. This covers three things: how features are discovered, how the host and plugins meet today on `dev` (e80628b), and what the tracker timeline would need to gain knowledge-base behaviour cleanly. That last part is a worked example of this issue's **optional** dependency, with the host as the provider.

## 1. Feature discovery

**Features are plugin-owned end to end.**
- The files live at `specs/<slug>/feature.md` plus any `*.md` documents (`SPECS_DIR`, `FEATURE_FILE`, `SLUG_PATTERN` in `packages/plugin-kb/src/core/files.ts:34-40`).
- Core only routes the paths. kb registers `treeLocations: [{ dir: "specs", build }]` (`plugin-kb/src/core/index.ts:39-45`). `parseTree` hands each location its bucket of paths, then stores the result as opaque `Repo.ext.get("specs")` and `Repo.extProblems.get("specs")` (`core/src/core/tree.ts:218-225`).
- The plugin builds `KbModel { features, featureBySlug, paths }` itself (`plugin-kb/src/core/tree.ts:63-75, 100-211`). `kbOf(ext)` is the accessor.

**Membership is asserted only by the entity.**
- `feature:` is a plugin-registered frontmatter key: `{ key: "feature", kinds: ["issue","pr"], shape: "string-or-list" }` (`index.ts:47-56`).
- Core normalises it into `entity.fm.feature`, at the top level with no `ext` namespace, because it is the grandfathered §2.12 pair.
- `featureMembers` scans every issue and PR with the plugin's `readFeatures` (`plugin-kb/src/core/ops.ts:104-114`). Nothing on the feature side lists members.

**A feature's history is the union of two `git log` walks** (`featureCommits`, `ops.ts:140-191`, over core's `searchCommits`, `core/src/git/history.ts:282-296`):
1. By path: the feature's directory plus every member's directory.
2. By reference: `--grep` for the member IDs, confirmed with `extractProseRefs` and `extractTrailerRefs` (`ops.ts:193-198`).

`docs(feature): … <slug>` subjects are never searched. They are found only because they touch `specs/<slug>/`.

**Commit subjects.**
- `docsFeatureSubject` left core in 42fab43. The plugin builds its subjects on core's generic `docsScopedSubject(scope, action, subject, file?)` (`core/src/core/ops.ts:91-98`).
- Grammar: `docs(feature): <create|edit|add> <slug>[/<file>]`, per spec 03 (`doc/spec/03-merge-and-branches.md:35-45`).
- Actual history on `dev`: `create` ×15, `add` ×12, no `edit`, and 5 hand-written prose subjects (`docs(feature): say …`). A summariser has to fall back to files, as the host's does.

**Checks and query.**
- D13 (layout and schema) and D14 (a dangling `feature:` slug) are implemented by kb. Core keeps their IDs in `CHECKS` (`core/src/core/validate.ts:57-63`).
- `feature:` is a plugin `queryKeys` term. Core's `query.ts` parses it generically and calls `def.matches` (`:257-276, 306-314`).

**Host leftovers worth a tidy.** Core's `files.ts` still carries two feature doc comments with no code under them, from the extraction:
- `:36` "The identity card at the top of a feature directory", which now sits above `VERDICTS`;
- `:438` "Read `feature` … keeping only slugs".

## 2. How the host and plugins meet today

**Declaring and loading.**
- `navbook.json` `plugins` is data. Declaring never fetches or runs anything (spec 02 §2.12, spec 04 §4.3).
- The CLI activates every *installed* plugin, declared or not. Declaring only supplies settings (`cli/src/plugins/resolve.ts:89-99`).
- The server loads only *declared* plugins, plus `NAVBOOK_PLUGIN_PATH`, and refuses to start when one is missing (`server/src/plugins/resolve.ts:57-95`).
- This asymmetry matters for required dependencies: the two front ends would disagree about what "present" means.

**The manifest.**
- The `navbook` block in `package.json` (`PluginManifest`, `core/src/core/plugins.ts:175-199`) holds `short`, `spec`, `format { root, entityDirs, frontmatterKeys, grandfathered }`, `core { queryKeys, doctorChecks, commitScopes }`, `cli { commands, contributions }`, `server { schema, config, services }` and `web`.
- `engines.navbook` is checked against `PLUGIN_API_VERSION = "1.0.0"`.
- "Contributions are declared, not discovered" is enforced in the CLI: commands and completion come from manifests alone, and `host.command` / `host.contribute` refuse anything undeclared (`cli/src/plugins/runtime.ts:215-236`). `./core` loads only when `needsCoreFor` says so.
- The server imports every part eagerly.
- **Declared but unread:** `core.commitScopes` is merged (`core/src/core/extensions.ts:298`) and consumed by nothing, and `format.entityDirs` is routed by nothing.

**Core seams.**
- `CoreExtensions` holds `{ treeLocations, frontmatterKeys, queryKeys, doctorChecks, commitScopes }` (`extensions.ts:111-119`).
- It is passed *explicitly* to `parseTree` (`opts.ext`, `tree.ts:202`), never read from a global. That keeps core pure.
- `mergeExtensions` refuses every collision (`:227-305`).
- There is no per-entity `ext` on `dev`. Plugin data on an entity is its normalised frontmatter, plus `extraFiles`, which are preserved and not interpreted.

**CLI seams.**
- `host.command`, `host.contribute(on, { openFields, columns, jsonExtra, showSection, listCompletions })` and `host.completer` (`cli/src/plugins/host.ts:41-82`).
- A contribution may target another plugin's command (`program.ts:315-339`). That is the *only* plugin-to-plugin touch point today.

**Server seams.**
- The SDL is composed as `[host, ...plugins]` (`server/src/schema.ts:37-54`).
- A plugin may `extend` *any* host type. kb extends `Query`, `Mutation`, `Entity`, `Issue`, `Pr`, the filters and the inputs (`plugin-kb/schema.graphql`).
- The host API also offers `resolvers`, `service`, `onMutation`, `entityInput`, `entityExt` and `api.*` (`server/src/plugins/host.ts:83-176`).
- `JSON` is output-only and appears only on `Entity.ext`, `Issue.ext` and `Pr.ext`, keyed by `short` (`resolvers/entity.ts:87-90`). There is none on `Comment`, `Commit`, `ChangedFile` or `TrackerCommit`.

**Web seams.**
- Plugin layers are chosen at build time from `NAVBOOK_WEB_PLUGINS`.
- Slots (`web/app/composables/useNavbookSlots.ts`): `navLinks`, `panels {noun}`, `entityFields`, `formFields` (issue-new only), `filters`, `rowBadges`, `inboxGroups`, `cache`, `listings`.
- The PR page's tabs are a fixed list (`prs/[ref].vue:63-67`). There is no slot inside a tab, for a changed file, or for a timeline entry.
- The host generates client types from the host SDL only (`web/codegen.ts`), so a host component can never select a field a plugin added.

**In flight.**
- `feat/kw6afa4a-plugin-host-seams` adds `api.execute`, `api.schema()`, the write sites and an `overlays` slot.
- `feat/s86nic83-plugin-chat` builds on it: a plugin with no `./core` that adds a whole `Subscription` root.
- `feat/z9yqtsbv-plugin-tests`, independent of those two, raises `PLUGIN_API_VERSION` to 1.1.0. It adds `entityLocations { dir, kinds, build(files, entity, paths) }` (plugin directories *inside* an entity's directory), `EntityRecord.ext`, and `DoctorTools`.
- chat already "lights up" against kb only by calling the public GraphQL API through `execute`. That is the de facto cross-plugin surface today, and it type-checks nothing.

## 3. Tracker timeline × knowledge base: what a clean integration needs

**Today.**
- The summariser (`packages/core/src/core/activity.ts`) knows issues and PRs only.
- `locate()` (`:107`) returns no record for `specs/…`. A kb commit's `TrackerCommit` therefore has `kind: null`, and the timeline shows its subject verbatim, with its files under "Show diff". That is correct and degrades cleanly, but says nothing.
- My first version hard-coded `specs/` and a `docs(feature)` grammar in core. The rebase removed that, because spec 02 §2.12 says the host MUST NOT interpret a plugin's namespace. The host only ever sees kb data as generic frontmatter: an issue that joins a feature shows the fact chip `feature: web, server`, unlinked and unlabelled.
- **A latent bug arrives with `entityLocations`.** Files under `prs/<status>/<id>/tests/…` are attributed to the PR. With no main file and no comment, `deriveVerb` answers `edit`, so a recorded test run would read "Edited this pull request". The host must learn to hand files it doesn't own to their owner, not only top-level directories.

**What would make it light up cleanly.**

1. **A core seam: `trackerSummaries`.** Add a new `CoreExtensions` member, keyed by a directory the plugin already owns (a `treeLocations` dir or, with 1.1.0, an `entityLocations` dir). The shape follows the host's own two pure steps:
   - `reads(subject, files) → TrackerRead[]`
   - `summarise(subject, files, read) → PluginSummary | null`

   `summariseTrackerCommit` would take `ext: CoreExtensions`, as `parseTree` does. It routes each file to the owner of its path. The subject is only a tie-breaker:
   - A commit that touches a plugin's paths and no issue or PR goes to that plugin.
   - A mixed commit uses the record the subject names, and the others become secondary records.
   - The `docs(<scope>)` part of a subject can route to the plugin whose manifest lists that scope, which finally gives `commitScopes` a reader.
   - A plugin that throws loses its own summary only, as `entityExt` readers do, and the commit falls back to subject and files.
2. **Plugin facts on host records.** A companion hook, `trackerFacts(key, before, after) → TrackerFact | null`, for keys the plugin registered in `frontmatterKeys`. With it, kb turns the raw `feature` fact into "Joined feature `web`" / "Left `server`", with the slug as a link. Without kb it stays the generic chip it is today.
3. **A server type the host can render without a web slot.**
   - Widen `TrackerCommit` with a generic `record: TrackerRecord { namespace: String!, noun: String!, key: String!, label: String!, title: String, path: String }` next to (or instead of) `kind: Kind`. `path` is a web route the plugin owns, e.g. `/features/web`.
   - Give `TrackerFact` an optional `path` too.
   - The host's `TrackerActivity.vue` can then say "Added a document to feature `auth`" from data alone, with no plugin web code, and it degrades to today's sentence when `record` is null.
   - This beats `extend type TrackerCommit` from kb's SDL: the host's codegen boundary means the host component could never read the plugin's field, and each plugin would need its own renderer slot.
   - The sentence's lead words are English in the host (`web/app/utils/activity.ts:39`). The plugin should send a verb from a small shared vocabulary (`create`, `add`, `edit`, `delete`) plus its noun, rather than free text.
4. **Wiring.** `RevisionCache` is built with `{ repoRoot, navDir }` only (`server/src/server.ts:177`). It needs the runtime's merged `CoreExtensions`, which `TreeCache` already reads. The cache key stays `base..head` for the life of the process, because the plugin set is fixed at server start. A CLI view of the activity, if one ever exists, must load kb's `./core` lazily under the same rule `needsCoreFor` applies to query terms.
5. **Reverse direction: kb reusing the host's summary.** A feature's timeline (`plugin-kb/web/app/pages/features/[slug]/index.vue`, fed by `featureCommits`) lists bare commit rows today. kb could ask core for `summariseTrackerCommit` on the commits it already walks and show "Closed #ozzaoa36 as fixed" on the feature page. `core` is already handed to the plugin (`CorePluginHost.register`), so this needs no new seam, only the summariser to be public API. It is.
6. **Tests.** A server test that loads kb from `NAVBOOK_PLUGIN_PATH` and asserts the `record` of a `docs(feature): create`, a hand-written `add`, and an issue's `feature:` change. The same range without kb must give today's answer, `kind: null` and the subject. Plus an e2e test in the stack with kb, the one `NAVBOOK_WEB_PLUGINS` builds by default.

## What this says about this issue

- **The host-provided variant already needs the pieces listed here:**
  - a declared extension point the host owns (`trackerSummaries`);
  - data-driven rendering across the codegen boundary (`TrackerRecord`);
  - failure isolation per plugin;
  - a clean fallback when the provider is absent.

  Plugin-to-plugin optional dependencies are the same shape with a plugin as the provider. The seam should be the *same mechanism*, so a host extension point and a plugin extension point are declared, loaded and version-checked alike.
- **Two facts constrain "present".** The CLI (installed = active) and the server (declared = loaded) disagree about it. And the server loads eagerly while the CLI loads lazily. A required dependency needs one answer across all four parts before the "never half-loaded" rule can hold.
- **Use the dead manifest fields, or remove them.** `commitScopes` and `format.entityDirs` are declared and unread today. They are the natural metadata for "which plugin owns this commit or directory", which both this integration and dependency resolution need without importing plugin code.
- **Execute-based coupling.** kw6afa4a's `api.execute` lets a plugin call another through GraphQL, untyped and unversioned. A dependency mechanism should say whether that is the sanctioned surface (and then version the SDL a plugin depends on) or a stopgap.
