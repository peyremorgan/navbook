## Implementation plan

Two pieces: a mechanical rename, and the fixture that would have caught the reimplementation risk this issue is really about. The second is the larger and more valuable half.

### 1. The rename — `packages/core/src/core/validate.ts`

```diff
-/** D10: is a frontmatter timestamp implausible next to the commit that added it? */
-export function checkTimestampSkew(
+/**
+ * D10: is a frontmatter timestamp plausible next to the commit that added it?
+ *
+ * True when the two are within `thresholdHours` of each other. The threshold
+ * is the implementation's to choose — spec 04 §4.3 requires only that it be
+ * documented — and `TIMESTAMP_SKEW_HOURS` in `workspace/history-checks.ts` is
+ * where the reference one lives.
+ */
+export function timestampIsPlausible(
   frontmatterIso: Date,
   gitAuthoredIso: Date,
   thresholdHours: number,
 ): boolean {
```

Call sites in `packages/core/src/workspace/history-checks.ts` (lines 118 and 131) keep their polarity exactly as it is — they are already correct — and simply read the way they behave:

```ts
if (added && !timestampIsPlausible(created, added.authored, TIMESTAMP_SKEW_HOURS)) { … }
if (timestampIsPlausible(comment.date, added.authored, TIMESTAMP_SKEW_HOURS)) continue;
```

`packages/core/test/validate.test.ts:759` has a `describe("checkTimestampSkew")` block whose three assertions already read as plausibility (`true` for a small delta, `false` for a large one in both directions) — so only the name changes, which is itself evidence the tests were written against the behaviour and the comment against an intention.

It is an exported name from `@navbook/core`. Pre-1.0 at 0.3.0, so renaming outright is right; no deprecated alias.

### 2. Worth considering while in the file: a result rather than a boolean

`checkRevisionsAppendOnly`, ten lines above, returns `{ ok: true } | { ok: false; index: number; message: string }`. It has no polarity to get wrong, and it carries the reason — which is why D7's diagnostic can say "revisions list shrank from 3 to 2 entries" while D10's can only manage "more than 48h".

```ts
export function timestampSkew(
  frontmatterIso: Date,
  gitAuthoredIso: Date,
  thresholdHours: number,
): { ok: true } | { ok: false; deltaHours: number } {
  const deltaHours = Math.abs(frontmatterIso.getTime() - gitAuthoredIso.getTime()) / 3_600_000;
  return deltaHours <= thresholdHours ? { ok: true } : { ok: false, deltaHours };
}
```

which lets the D10 message say how far off it actually is — the one thing a reader of that warning wants and currently has to work out by hand:

```
'created: 2025-09-14T10:00:00Z' is 8784h from the commit that added it (2026-09-14)
```

This is optional and strictly better; if it is taken, the rename above is subsumed. If it is not, the rename stands on its own. I would take it — the message improvement is real and the shape already has a precedent in the same file.

### 3. The fixture — `doc/spec/fixtures/format/invalid/d10-timestamp-skew/`

This is the half that matters. `doc/spec/fixtures/` has cases for D1–D6 and D11–D15 and **none for D7, D9 or D10**, because those read git history. But the harness already supports what D10 needs: `history:` steps take a per-commit `date:`, documented in `doc/spec/fixtures/README.md`.

```yaml
spec-version: 1
description: D10 warns when a frontmatter timestamp is far from the commit that added it
history:
  - id: base
    branch: main
    apply: history/00-base
    message: "docs: initialize navbook"
    date: 2026-09-01T10:00:00Z
  - id: skewed
    branch: main
    apply: history/01-skewed
    message: "docs(issue): open #bqlybac0"
    date: 2026-09-01T11:00:00Z
run:
  checkout: main
  command: [doctor, --json]
expect:
  exit: 0
  diagnostics:
    - {check: D10, level: warning, path: .navbook/issues/open/bqlybac0-login-timeout/issue.md}
```

with `history/01-skewed/.navbook/issues/open/bqlybac0-login-timeout/issue.md` carrying `created: 2025-09-01T10:00:00Z` — a year off.

**A year, not three days, and deliberately.** Spec 04 §4.3 makes the threshold an implementation's choice: "Implementations MUST document the threshold they use; the reference implementation warns beyond **48 hours**." A fixture built around a three-day skew would pin 48 hours into the conformance suite and turn a documented choice into a required constant. A year is outside any threshold a reasonable implementation would pick, so the fixture asserts the *check* rather than our number.

`exit: 0` is the assertion that D10 is a warning — worth having, since nothing else in the suite proves a warning does not fail the command.

Worth a second fixture asserting the negative: an issue whose `created` matches its commit produces no D10. The `format/valid/` trees mostly use `init:` rather than `history:`, so this would be the first valid case with scripted commit dates — a small but real widening of what the suite covers.

### 4. What this does *not* cover

D7 and D9 remain unfixtured. Both are harder: D7 needs a `pr.md` rewritten across two commits with an edited revision entry, and D9 needs a branch whose head contains a pull request's revision head. Both are writable with the same `history:` mechanism, and both are out of scope here — worth their own issue rather than being smuggled in.

### 5. Order of work

1. Decide boolean-rename versus result-shape (step 2). Everything downstream depends on it.
2. Rename or reshape; update `history-checks.ts` and `validate.test.ts`.
3. The D10 fixture, then the valid counterpart; `pnpm test:conformance`.
4. `pnpm check` and the full suite.

### Risks

Very low. No behaviour changes unless step 2's message improvement is taken, in which case the D10 warning text changes — and nothing asserts that text today, which is the gap the fixture closes.

### Done when

No predicate in `core/` is named or documented as the opposite of what it returns, and `pnpm test:conformance` includes a case that a second implementation would fail if it got D10's polarity backwards.
