## Confirmed on `dev` at `1832db6`

The code is unchanged since the audit. `walk` still calls `readFileSync(childAbs, "utf8")` on every file under the root (`packages/core/src/workspace/workspace.ts:84-85`). `parseTree` still asks for content only through `files.get`, and only for four kinds of file: the marker (`tree.ts:241`), an entity file (`tree.ts:469` and `:519`), a comment, and a feature or spec file (`tree.ts:469` through `parseOrReport`). Everything that `classify` routes to `reserved` (`tree.ts:290-296`) or to an entity's or a feature's `extraFiles` (`tree.ts:364`, `:415`) is read and then dropped.

### Reproduction

This uses a throwaway repository with one issue, one feature, and one file in each of the three uninterpreted places:

```sh
git init -b main && nav init --commit
nav issue open "One issue" -m "Body." --commit
nav feature open "Auth" --slug auth -m "Signing in." --commit
mkdir -p .navbook/reports
node -e 'require("fs").writeFileSync(".navbook/reports/coverage.json", JSON.stringify({lines: "x".repeat(24 * 2 ** 20)}))'  # §2.12, top level
echo '{"passed":1}' > .navbook/issues/open/<id>-one-issue/reports.json                                                   # §2.12, per entity
node -e 'require("fs").writeFileSync(".navbook/specs/auth/diagram.png", Buffer.concat([Buffer.from("89504e470d0a1a0a", "hex"), Buffer.alloc(64, 0xff)]))'  # §2.11
git add -A && git commit -m "extension data"
```

`nav doctor` reports `No problems found.`, which is correct: all three files are allowed.

**Every command opens all three.** I ran `strace -f -e trace=openat` on the checkout's own CLI (`node packages/cli/src/main.ts`). `nav issue list`, `nav issue show <id>`, `nav feature list` and `nav doctor` each open the same three files:

```
.navbook/issues/open/dvbed9tn-one-issue/reports.json
.navbook/reports/coverage.json
.navbook/specs/auth/diagram.png
```

`issue list` loads with `comments: "none"`, so the comment scope is doing its job and the walk still reads the rest.

**What that costs.** I called `readNavTree(nav, { comments: "none" })` and then `parseTree`, in-process:

| | with the 24 MB file | without it |
|---|---|---|
| paths | 11 | 10 |
| characters held | 25,166,143 | 307 |
| `readNavTree` | 35.9 ms | 2.0 ms |
| RSS after | 124 MB | 100 MB |

For the whole command, `nav issue list` takes about 560 ms with the file and about 475–545 ms without it, over three runs each. That is noisy and dominated by startup, but it points the same way. The paths still come back correctly:

```
reserved:           ["reports/coverage.json"]
issue extraFiles:   ["issues/open/dvbed9tn-one-issue/reports.json"]
feature extraFiles: ["specs/auth/diagram.png"]
```

**The lossy decode is real.** The 72-byte `diagram.png` becomes a 72-character string, 65 of them U+FFFD, and `Buffer.from(text, "utf8")` does not reproduce the file. Nothing writes that string back today, as the audit says. But the string sits in the tree map as if it were the file's content.

### One correction to the first comment

The first comment says the server holds a large extension namespace "for the life of every request". That no longer applies. The server now caches the parsed `Repo` per `HEAD` (`TreeCache` in `packages/server/src/trees.ts`), and a `Repo` keeps paths, not the tree map. So on the server the read and decode cost is paid once per commit and per comment scope, not once per request, and the memory is a peak during the load rather than something held. The CLI pays the cost on every command.

### Plan

The lazy `NavTree` plan in the comment above still fits the code as it is. `parseTree`, `validateTree` and `commentRecords` use only `keys()` and `get()`. Every other caller of the type in `src/` either builds a `Map` or is `readNavTree` itself. I'll take the fix.
