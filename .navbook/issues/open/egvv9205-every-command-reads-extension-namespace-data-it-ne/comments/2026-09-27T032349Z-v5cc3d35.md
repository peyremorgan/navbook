### Repro

A fresh repository, one issue, plus data in all three uninterpreted places (§2.12 top-level namespace, §2.12 per-entity namespace, §2.11 image in a feature):

```sh
nav init --commit && nav issue open "One issue" -m body --commit
mkdir -p .navbook/reports .navbook/specs/auth
node -e 'require("fs").writeFileSync(".navbook/reports/coverage.json", JSON.stringify({lines:"x".repeat(24e6)}))'
printf -- '---\ntitle: Auth\n---\nx\n' > .navbook/specs/auth/feature.md
printf '\x89PNG\r\n\x1a\n\xff\xfe\x00\x01' > .navbook/specs/auth/diagram.png
echo '{"passed":3}' > .navbook/issues/open/<id>-one-issue/reports.json
strace -f -qq -e trace=openat -o s.log nav issue list; grep -o '\.navbook/[^"]*' s.log | sort -u
```

`nav issue list` and `nav doctor` both open every one of them:

```
.navbook/issues/open/y1yni7gw-one-issue/issue.md
.navbook/issues/open/y1yni7gw-one-issue/reports.json   <- never parsed
.navbook/navbook.json
.navbook/reports/coverage.json                         <- never parsed
.navbook/specs/auth/diagram.png                        <- never parsed
.navbook/specs/auth/feature.md
(+ every .gitkeep)
```

### Cost

`readNavTree(root, { comments: "none" })` (the read behind `nav issue list`), with the 24 MB file and without it:

```
with:    paths: 11, chars held: 24,000,178, readNavTree: 14.9 ms, maxRSS: 142 MB
without: paths: 10, chars held: 166,        readNavTree:  0.8 ms, maxRSS: 101 MB
```

Wall clock for the whole `nav issue list`, 3 runs each: 327–353 ms with the file, 300–314 ms without. That is about +30 ms and +41 MB for a file the command never looks at, and both grow linearly with whatever a plugin writes.

The binary half reproduces too. `tree.get("specs/auth/diagram.png")` returns `"�PNG\r\n\u001a\n��\u0000\u0001"`: 3 U+FFFD, so the bytes can't be recovered from what was read.

On the server, `TreeCache` (`packages/server/src/trees.ts`) holds the parsed `Repo`, not the `NavTree`, so the strings are garbage once `parseTree` returns. The cost is paid on each cache miss (every new HEAD and every scope widening), not held for the life of the process.

Going ahead with the lazy-`NavTree` plan from the previous comment.
