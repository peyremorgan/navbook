## Implementation plan

Taking the structural version rather than a predicate in `walk`. A predicate would be a second reader of the path shapes `classify` already routes, and two routers over one grammar is the drift this repository avoids everywhere else. Instead: **make the tree lazy, so `parseTree` reads exactly what it parses, by construction.**

### 1. The idea

`NavTree` is `ReadonlyMap<string, string>` today, and `parseTree` uses exactly two of a Map's operations — `keys()` and `get()`:

```
tree.ts:198   for (const path of [...files.keys()].sort())
tree.ts:223   const markerText = files.get(NAV_MARKER)
tree.ts:451   return parseFile(files.get(path) ?? "")
tree.ts:520   blobSha: blobSha(files.get(draft.entityFile) ?? "")
```

Widen the type to those two operations and a `Map` still satisfies it structurally — so every existing caller keeps working untouched — while `readNavTree` becomes free to return something that reads on demand.

### 2. The type — `packages/core/src/core/tree.ts`

```ts
/**
 * A Navbook directory as a set of paths whose contents can be asked for.
 *
 * Two operations rather than a `Map` because a caller may not want to have
 * read everything: `parseTree` asks for the content of the files it parses and
 * of no others, so a lazy implementation never opens an extension namespace
 * (§2.12) whose bytes nothing here interprets. A `Map<string, string>`
 * satisfies this, which is what keeps the git-backed callers unchanged.
 */
export interface NavTree {
  keys(): Iterable<string>;
  get(path: string): string | undefined;
}
```

Nothing else changes in `tree.ts`. `classify` still routes every path; only the *content* of the ones it routes to `reserved` and to `extraFiles` is never asked for.

### 3. The lazy reader — `packages/core/src/workspace/workspace.ts`

`walk` collects paths; a closure reads on demand and memoises, because `materialize` asks for the entity file and `blobSha` asks for it again.

```ts
export function readNavTree(navRoot: string, opts: ReadTreeOptions = {}): NavTree {
  const paths: string[] = [];
  if (existsSync(navRoot)) walk(navRoot, "", paths, opts.comments ?? "all");

  // Read on demand and remembered: `parseTree` asks for an entity file twice
  // (once to parse, once to hash), and never asks for the rest at all.
  const contents = new Map<string, string>();
  return {
    keys: () => paths,
    get(path) {
      if (!paths.includes(path)) return undefined;   // see note below
      let text = contents.get(path);
      if (text === undefined) {
        text = readFileSync(join(navRoot, ...path.split("/")), "utf8");
        contents.set(path, text);
      }
      return text;
    },
  };
}
```

`paths.includes` is O(n) and `parseTree` calls `get` once per entity — keep a `Set` alongside the array rather than scanning. Written out above only to show the shape.

`walk` loses its `files.set(...)` and pushes the path instead; `wanted(rel, comments)` stays exactly as it is, since skipping an out-of-scope `comments/` directory is still worth doing at the directory level rather than per file.

### 4. What this buys, precisely

- `.navbook/reports/coverage.json` and every other §2.12 top-level namespace: **path recorded, bytes never read.** `Repo.reserved` is unchanged, so "preserve what you do not understand" is still checkable.
- An entity's `<short>.*` or `<short>/` files (`extraFiles`): same.
- A feature directory's images and subdirectories (§2.11's "preserved untouched and MUST NOT be interpreted"): same — and this is where the UTF-8 hazard actually lived, since `readFileSync(png, "utf8")` was producing a string of U+FFFD for something nothing ever needed.
- Comments out of scope: already skipped; unchanged.

### 5. Errors move, slightly

`readFileSync` now throws from inside `parseTree` rather than during the walk. Today an unreadable file makes `readNavTree` throw and the command fails; after this, it throws when the file is parsed. Two places already handle a read that yields nothing — `parseOrReport` catches and records a structural problem — so the honest change is to let `get` return `undefined` on a read error rather than throw:

```ts
try { text = readFileSync(…); } catch { return undefined; }
```

`parseOrReport` then reports `parseFile("")` failing with "file must start with a '---' frontmatter delimiter", which is a worse message than the ENOENT would have been. Worth a small improvement while in there: have `parseOrReport` distinguish "no content" from "content that will not parse".

### 6. The other callers are unaffected, and that is the test

- `stagedRepo` (`ops/doctor.ts`) builds a `Map` from `git show :path` — still satisfies `NavTree`, still eager, correct as it is: it has already paid for the content by asking git for it.
- `scanRefsForOpenPrs` (`ops/pr.ts`) builds a `Map` from a batched `cat-file` — same, and it already reads only what is under one pull request's directory, which is the instinct this change brings to the filesystem path.
- `validateTree(files: NavTree)` — unchanged.

### 7. Tests

- **`packages/core/test/files.test.ts` / a new `navtree.test.ts`** — the behavioural assertion is about what is *not* read. Inject a counting reader, or simpler: put a file under `.navbook/reports/` that is not valid UTF-8 and assert `loadRepo` succeeds and lists it in `reserved`. Today that file is decoded lossily; after the change it is never opened.
- **A directory of one entity plus a large uninterpreted file** — assert `readNavTree(...).keys()` includes it and that parsing does not fault. A read-count assertion is better if the helper allows injecting `readFileSync`.
- The existing `wsctx`/`navroot`/`orphans` suites cover the walk itself and should pass untouched; if any of them depends on `readNavTree` returning a `Map`, that is the one place the type widening shows up.

### 8. Order of work

1. Widen `NavTree`; `pnpm --filter @navbook/core typecheck` should be clean immediately, which is the point of choosing this shape.
2. Rewrite `readNavTree` and `walk`.
3. Error handling in `get` and `parseOrReport`.
4. Tests; full suite; `pnpm bench` to confirm the 1 000-issue budget has not moved the wrong way.

### Risks

- **`Repo.reserved` must not shrink.** It is what `doctor` and the future plugin work read to say "there is data here I do not understand". The whole change is predicated on paths staying and only bytes going; a test asserting `reserved` for an unread file is the guard.
- **Server memoisation is unchanged.** `ctx.repo()` still memoises a parsed `Repo` per request; this reduces what building one costs, and touches nothing about when it is built.
- **A lazy read is a read at a later moment.** Under the server's mutex that is still inside the transaction, so there is no new window. Worth confirming that no caller holds a `NavTree` across a lock boundary — I believe none does, since `loadRepo` parses immediately.

### Done when

A repository with a 24 MB `.navbook/reports/coverage.json` shows that file in `Repo.reserved`, `nav issue list` never opens it, and a non-UTF-8 file in a feature directory is preserved without ever being decoded.
