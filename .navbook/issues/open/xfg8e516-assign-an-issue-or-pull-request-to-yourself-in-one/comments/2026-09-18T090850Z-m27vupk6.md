**What the fix decided.** The spelling question raised above turned out to be the whole of it. `viewerField` (`packages/web/app/utils/people.ts`) takes the spelling out of `people` rather than composing it from the token, matched on the address lowercased — which is the key `dedupePeople` merges on in core, so the client is picking among strings the server sent rather than deciding who is whom. The composed fallback is only reachable for an address that answer cannot hold yet, and an empty answer yields no button at all: one written from a guess, offered for the instant before the real answer lands, is worse than one that appears a moment late.

Membership is matched the same way, so the toggle still takes you off a list that spells you differently from the menu — the bare address `nav` writes against the named one the token claims. That is what `findPerson` and `togglePerson` are for, and what the new unit tests mostly cover.

**Verified.** 366 unit tests pass (296 before). The end-to-end suite runs 148, all green, including three new ones in `test-e2e/self-assign.spec.ts` that prove the round trip on the issue page, on the pull request page, and across a reload — each as an address that is in no fixture and no history, so an assignee bearing it afterwards can only be the button's doing. `nuxi typecheck` is clean; `biome check` leaves only the three `noVueDuplicateKeys` errors that are already on `dev`.

One thing worth knowing for anyone writing a test against this panel: the two pages show the same field differently. The issue page keeps the component's chips, which carry the whole `Name <address>`; the pull request page replaces them with the avatars it already showed, which carry only the name. Asserting on the address passes on one page and fails on the other.
