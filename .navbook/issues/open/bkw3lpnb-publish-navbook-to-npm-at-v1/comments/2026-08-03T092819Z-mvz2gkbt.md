Published. Live at `@navbook/cli@0.1.2` on npm, under a dedicated `navbook` org (not the original unscoped `navbook` name floated earlier — the org lets the team manage publish access, and the scope leaves room for a future `@navbook/core`).

The first two attempts each shipped a real bug, both found by verifying the actual installed artifact rather than trusting the publish command's exit code:

- **0.1.0**: the `bin` path `./dist/cli/main.js` has a leading `./` that npm's bin-path validator rejects. npm auto-corrected it out of the registry's normalized view with only a warning, not a hard failure — the package still installed and ran, because `bin-links` reads the literal `package.json` inside the tarball rather than the corrected metadata. Fixed by dropping the `./` prefix, confirmed via `npm publish --dry-run` showing no warning.
- **0.1.1**: `nav --version` still reported `0.1.0` — traced to `VERSION` in `src/cli/program.ts` being a hardcoded string literal, completely decoupled from `package.json`. Bumping the package version and republishing silently shipped a CLI lying about its own version. Fixed by reading `package.json` at runtime instead (`fileURLToPath(new URL(\"../../package.json\", import.meta.url))` — same relative depth from `src/cli/` in dev and `dist/cli/` after build), so this can't drift again.

Both `0.1.0` and `0.1.1` are marked deprecated on npm, pointing at `0.1.2`.

`0.1.2` is verified clean: pinned install, unpinned/`latest` install, `npx`, and a full `init`/`issue open`/`issue list`/`doctor` run all pass against the actual published package, not just a local build. README's install instructions already pointed at `@navbook/cli` and needed no changes.
