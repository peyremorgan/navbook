Fixed on `perf/server-reads`, in the order proposed above, with the cache last so that each earlier step could be measured on its own. The pull request that carries it closes this issue.

## Results

`packages/server/script/bench-reads.ts` (new in this branch) sends the web client's own five issue-page queries against a tree of any size. The figures below are for K=16, a 2 194-file tree about the deployed one's size, with every fetch slowed to 2.2 s. The baseline and the final branch were run back to back on the same machine, twice, because another session was loading it heavily. Medians of 5:

| issue page | baseline (`2239cd2`) | `perf/server-reads` (`1a60a61`) |
|---|---|---|
| warm | 896–1 213 ms | **91 ms** |
| first load after an idle pull interval | 2 897–3 215 ms | **103–110 ms** |
| `Issue` alone, warm | 314–456 ms | 18 ms |
| `Features` alone, warm | 275–374 ms | 20–21 ms |

The tree parse, checked on the production host itself, read-only, with the deployed core and the new one interleaved over the live tree (853 entities, 2 474 files):

| | deployed core | new core |
|---|---|---|
| `loadRepo`, all comments | 586 ms | 269 ms |
| `loadRepo`, no comments | 341 ms | 160 ms |
| `parseTree` only | 451 ms | 150 ms |

Both cores gave identical results for every entity, comment and feature. 95.7 % of the files were read by the fast path, and the rest went through `yaml` as before.

## What changed, step by step

1. **Background pull** (`dbf95fd`). The server fetches every pull interval outside the lock, and takes the lock only to merge. While that keeps up, reads never touch the network. Until its first success, and after a failure or a conflict, reads pull for themselves as before, so `SYNC_FAILED` and `SYNC_CONFLICT` still reach them. Fetches and pushes are queued behind each other, because two git processes updating one remote-tracking ref make the loser fail.
2. **One parse per request** (`c098935`). `issue`, `feature(s)` and a mutation's payload parse once, inside the transaction, and their fields reuse that parse. The fields therefore also describe the same tree as the record they belong to.
3. **Comment scoping** (`8597f40`). Records say whether their comments were read, and `withComments` reads one entity's. `issue` parses without comments and reads its own; `features` and link fields read none. This also fixes a wrong answer: `issues { comments }` returned `[]` for every row of a listing.
4. **Fast frontmatter reader** (`9663c21`). `flat-yaml.ts` reads the flat subset nearly every issue and comment uses, and leaves anything else to `yaml`. The `Document` is built only when an edit needs it. A differential test requires every frontmatter reader to answer as `yaml` does whenever the fast path reads a file. It covers this repository's tree, the conformance fixtures and a corpus of edge values; two deliberate bugs planted in the reader were both caught.
5. **Tree memo** (`1a60a61`). The parse is kept against HEAD, and a tree read with more comments serves a request for fewer. Every mutation drops it, at the start and again on failure. A watchdog runs `git status` on the Navbook directory every pull interval, off the request path; while it finds uncommitted changes, the cache is bypassed. A hand edit to the served clone is therefore seen within one interval rather than on the very next read. A pull interval of 0 turns the cache off.

Option 5 of the original list, the async walk, was dropped. On the production host it was slower than the synchronous one (240 ms against 118 ms).
