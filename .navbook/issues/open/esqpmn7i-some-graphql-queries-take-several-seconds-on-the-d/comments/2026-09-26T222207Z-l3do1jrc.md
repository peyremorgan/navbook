## Why exactly those four, and why they all show the same number

The row that matters is the concurrent one. `Issue`, `Issues`, `Features` and `People` all finish within a few milliseconds of each other, even though alone they cost between 0.4 and 0.9 s. Those four go through `sync.read` (`packages/server/src/sync.ts`), so they queue on the one `Mutex` (`packages/server/src/lock.ts`). Each body is synchronous (`loadRepo` is `readFileSync` plus `yaml`), so no response is written until the whole queue has drained. The latency a browser measures for any one of them is therefore the sum of all of them, plus the fetch when the pull interval has elapsed:

```
cold page ≈ fetch
          + Issue    (loadRepo(all) in findEntity + loadRepo(all) again in ctx.repo() for parent/subtasks)
          + Issues   (loadRepo(none))
          + Features (loadRepo + loadRepo again in ctx.repo() for issues/prs)
          + People   (loadRepo + cached git log)
```

That is six full parses of the tree for one page. `Viewer` escapes the lock and still reads 2.2 s on the warm run, because it waits for the event loop, which the synchronous parses block. So `/health`, and the refusal of a bad token, stall the same way.

Without network cost, the local fixture reaches 3.9 s at about 2 100 entities. Adding the production fetch (last measured here at 530 ms to GitHub, never measured to `git.infra.brickcode.tech`) crosses 4 s at a smaller tree, and so does a slower disk or CPU in the container. I could not measure production from this session: the API wants a token for every query. The two numbers that would pin it down are the deployed repository's file count (`find .navbook -type f | wc -l` inside `docker compose exec api sh`) and how long a `git fetch` takes from that container.

## What this adds to the options above

- **(1), a HEAD-keyed memo of the parsed tree, is the fix for this report.** With it, warm reads cost one `rev-parse` each, and the four queries stop paying for each other. (2), one load per request, alone would take the page from six parses to four. That still grows linearly with the tree, so it mitigates the problem without fixing it.
- **Mitigation without a code change:** raising `NAVBOOK_PULL_INTERVAL_MS` removes the fetch from most page loads. It does nothing for the warm number, which on the local fixture is already 2.8 s at 2 100 entities.
- **(5), keeping the loop free, is what makes the number honest.** As long as the parse is synchronous, even requests that need no tree (`Viewer`, `/health`) report the tree's cost.
