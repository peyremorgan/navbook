Production numbers, from Morgan (2026-09-26):

- The deployed tracker holds **2 106 files**.
- A `git fetch` of its repository takes **2.35 s**. This was measured from a client machine, not from inside the API container, so it is a close stand-in rather than the container's own figure.

At production size, the first page load after the pull interval has elapsed takes **3.4 s** on this machine. About 2.3 s of that is the fetch; the rest is the parse queue described above. All four reported queries show the same total. The last ~0.6 s to the reported 4 s+ is plausibly a container slower than this laptop.

This changes the ranking for this deployment. The fetch, not the parse, is two thirds of the slow page. Any page opened more than 10 s after the previous request pays it, in full, while holding the lock.

- **Now, without a code change:** raise `NAVBOOK_PULL_INTERVAL_MS` (e.g. `60000`). Most page loads then drop to the warm figure (about 1.3 s locally), at the cost of up to a minute of staleness for changes pushed from outside the server. The server's own mutations still pull before they write.
- **Option (4), fetching in the background instead of on the request path, becomes the first code change.** It removes the 2.3 s from every read, whatever the interval.
- **Option (1), the memo keyed on HEAD, is still what removes the remaining ~1.3 s,** and keeps it from growing with the tree.

One more production number would confirm the split: the time for a page that is reloaded straight away, inside the 10 s interval. If that is also above 4 s, the container parses about three times slower than this machine, and (1) moves back to first.
