Profiled on the production host itself (2026-09-26), inside `navbook-api-1` (image `navbook-server:2ebc8ce`, Node 24.21, Linux 4.15, 8 shared cores). Everything was read-only against the live clone at `/srv/navbook`: a script that loads the tree in place, and `git ls-remote` rather than a fetch, so nothing raced the server's own git calls. The script was removed afterwards.

The deployed tree has **850 entities, 2 458 files and 57 features**. Medians of 9 runs:

| | ms |
|---|---|
| `loadRepo` with all comments | **607** |
| `loadRepo` with pull-request comments only | 397 |
| `loadRepo` with no comments | 332 |
| reading the files only (`readNavTree`, all comments) | 118 |
| parsing only (`parseTree`, all comments) | **450** |
| the same files through an async walk, 16 or 64 reads at once | 240–250 |
| the same files through `git ls-tree` + `git cat-file --batch` | 183 |
| `git ls-remote origin`, from the container | 160 |
| `git log` of the whole history, which `people` walks when HEAD moves | 90 |

A CPU profile of ten full loads puts **74 % of a load in parsing**, and 45 % in the `yaml` library alone (`parser.js` 21 %, `lexer.js` 13 %, the rest in `compose` and `nodes`). File I/O is about 19 %, and GC 6 %. This is the opposite of the profile taken on a Mac laptop, where I/O dominated. The production CPU is about 4× slower per load, and its file system is faster relative to that CPU.

What this means for the options above:

- **Cheaper frontmatter parsing (option 6) is the biggest remaining lever that caches nothing.** The files' frontmatter is a small subset of YAML, so a fast path for that subset, with a fallback to `yaml` for anything else, should remove most of the 450 ms.
- **Loading only the comments a request needs (option 3) is worth more here than it looked:** 607 ms falls to 332 ms for every query that does not need every comment.
- **The async walk and reading from git objects (option 5 and a variant) are ruled out for latency:** both are slower than the synchronous walk on this machine.
- **The fetch costs less from inside the container than from a client:** `ls-remote` takes 160 ms, where the 2.35 s reported above was measured from elsewhere. A real fetch could not be timed without racing the server's own. The background pull on `perf/server-reads` removes it either way.
- **`people`'s history walk is negligible:** 90 ms, repeated only when HEAD moves (3 times in the last 24 h, 60 in the last 7 days). The same figures make the HEAD-keyed memo (option 1) a cache that almost always hits.

Estimated from these component timings, not measured end to end, the tree work an issue page queues behind the lock:

| version | tree work |
|---|---|
| deployed, `2ebc8ce` | ≈ 3.1 s: `issue` 2 × 607, `issues` 332, `features` 332 + 607, `people` 607 + 90, plus the fetch |
| `perf/server-reads` so far (background pull, one parse per request) | ≈ 2.2 s |

Seen in passing: the API container holds about 175 zombie `git` processes. `nav-server` runs as PID 1 and does not reap the helpers git leaves orphaned. `init: true` on the service in `compose.yaml` fixes that.
