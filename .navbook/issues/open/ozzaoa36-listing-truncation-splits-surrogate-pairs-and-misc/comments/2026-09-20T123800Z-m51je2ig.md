The standards and the state of the art, since "how wide is this string" is a solved problem with a known cost.

**What the width actually is.** [UAX #11, East Asian Width](http://www.unicode.org/reports/tr11/) assigns every character one of five classes, and the rule terminals implement is: Wide (W) and Fullwidth (F) occupy two columns, everything else one. The canonical implementation is Markus Kuhn's [`wcwidth.c`](https://www.cl.cam.ac.uk/~mgk25/ucs/wcwidth.c), which is what every port descends from — including [`wcwidth.js`](https://github.com/mycoboco/wcwidth.js), which already "converts surrogate pairs to Unicode code points to handle them correctly", i.e. it solves precisely the half of this bug that is doing damage.

**What a "character" is for cutting.** [UAX #29](https://unicode.org/reports/tr29/) grapheme clusters are the right unit, and Node 24 has them built in — no dependency:

```console
$ node -e 'console.log([...new Intl.Segmenter("en",{granularity:"grapheme"}).segment("👨‍👩‍👧")].length)'
1
$ node -e 'console.log([..."👨‍👩‍👧"].length)'
5
```

So `Intl.Segmenter` gets the ZWJ family right where `[...text]` counts five and `slice` cuts at two bytes. It is available unflagged in every runtime this project supports (`engines: node >= 24`), and `Intl.Segmenter` is the MDN-documented way to do this now — the [FormatJS polyfill](https://formatjs.github.io/docs/polyfills/intl-segmenter/) exists only for older environments.

**What is *not* available.** I checked for a built-in width helper first, because that would settle the dependency question:

```console
$ node -e 'console.log(typeof require("node:util").getStringWidth)'
undefined
```

`util.getStringWidth` is internal to Node's readline and not exported in 24. So the options are: an EAW table of our own (a generated file), the `string-width` package, or an approximation over `Intl.Segmenter` plus a handful of Unicode property escapes.

**The dependency question is real and cuts both ways.** Spec 05 §5.2 is firm that "every dependency added to the core is a liability for the Rust rewrite (behavior to reproduce) and MUST be justified". This code is in `cli/` rather than `core/`, so that rule does not literally bind it — but `truncate` is presentation, and a Rust `nav` will need the same answer to lay out the same table. Rust's ecosystem has `unicode-width`, which is the same UAX #11 table, so parity is achievable either way; what would not be achievable is parity with a hand-rolled approximation that only we have. That argues for either a real table or a documented, deliberately simple rule — not for something in between.

**Suggested split.** The code-point slice is a one-line, no-dependency, no-debate fix for the invalid-UTF-8 half, and is worth landing on its own. The column-width half is a separate decision with a real trade-off, and could reasonably be its own issue.

A unit test is the cheap part — nothing exercises `truncate` today (`grep -rn truncate packages/cli/test` finds no hits):

```ts
it("never cuts a character in half", () => {
  for (let width = 1; width <= 8; width++) {
    const cut = truncate("😀😀😀😀", width);
    assert.equal(Buffer.from(cut, "utf8").toString("utf8"), cut, `width ${width}`);
  }
});
```
