Confirmed on `dev` at b01f9b0, with the CLI against this repository (the deployment serves another repository, so `epo4xcgf` is not here; #icroff4l, assigned to Claude, stands in for it).

## Repro

```console
$ nav issue list assignee:noreply@anthropic.com
ID         STATUS  TITLE                                          LABELS  ASSIGNEE
#icroff4l  open    Signing out of the web client leaves the ...   bug     Claude <noreply@anthropic.com>

$ nav issue list 'assignee:Claude <noreply@anthropic.com>'
No issues match this query.

$ nav issue list 'author:Claude <noreply@anthropic.com>'
No issues match this query.

$ nav pr list status:merged reviewer:morgan.peyre@brickcode.tech      # ro4yvdyq, kpz5ow8j, ...
$ nav pr list status:merged 'reviewer:Morgan PEYRE <morgan.peyre@brickcode.tech>'
No pull requests match this query.
```

In the web client: **Issues** → filter bar → **Assignee** → pick anyone from the menu. The URL gains `assignee=Name+%3Cemail%3E` and the listing reads "No issues match this filter".

## Why

The server's `people` query renders each person with `formatPerson` (`packages/server/src/resolvers/query.ts`):

```ts
return mergePeople(authored, named, [ctx.viewer]).map(formatPerson);
```

`pages/issues/index.vue` and `pages/prs/index.vue` pass that list to `EntityFilterBar` as the `assignees`/`authors`/`reviewers` menus, and `utils/filter-params.ts` sends the picked value through as `EntityFilter.assignees` unchanged. The server maps it to `query.assignees` (`resolvers/map.ts`), and `matchesQuery` calls `personMatches` in `packages/core/src/core/person.ts`:

```ts
const needle = queryValue.trim().toLowerCase();   // "morgan peyre <morgan.peyre@brickcode.tech>"
...
const email = (person?.email ?? personField).trim().toLowerCase();
if (email === needle) return true;                // never: the needle carries the name
if (needle.includes("@")) return false;           // so every named value ends here
```

The field is parsed as a person but the query value isn't, so a named value can equal no address. `awaiting:` goes through the same function (`core/review.ts`). Spec 04 §4.3 writes these terms as `assignee:EMAIL`, which is why it hasn't come up from the CLI. The web client is the first front end whose values come from a list of `Name <email>` strings.

The inbox (`useInbox.ts`) isn't affected: it sends the viewer's bare address as `$me`.

## Fix

Parse the query value with `parsePerson` in `personMatches`. When it is a well-formed address, named or bare, compare addresses. Otherwise keep the domain-fragment rule. Spec 04's table says a named address is accepted and matched by its address.
