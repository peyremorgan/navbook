## Implementation plan

Small change, but the whole point is that it must hold under a shell whose options we do not control, so the plan is mostly about picking a form that cannot be broken by the next thing appended after it.

### 1. The block — `packages/cli/src/install/hook.ts`

```diff
 const BODY = `${MARKER_BEGIN}
 # Validate staged Navbook files. Only a format violation (exit 2) blocks the
 # commit; warnings never do, and a clone without nav installed is unaffected.
 # Commit with --no-verify, or delete this block, to skip the check.
+#
+# The status is captured rather than tested on the next line: this block is
+# appended to whatever hook was already here, and under 'set -e' a bare
+# 'nav doctor --staged' would end the hook on exit 1 — an operational error,
+# not a format violation — before the test below ever ran.
 if command -v nav >/dev/null 2>&1; then
-  nav doctor --staged
-  if [ $? -eq 2 ]; then
+  navbook_status=0
+  nav doctor --staged || navbook_status=$?
+  if [ "$navbook_status" -eq 2 ]; then
     exit 1
   fi
 fi
 ${MARKER_END}`;
```

Three things decided deliberately:

- **`|| navbook_status=$?` rather than moving the call into the `if`.** Both suspend `set -e` — `bash(1)`: "The shell does not exit if the command that fails is … part of any command executed in a `&&` or `||` list except the command following the final `&&` or `||` … part of the test following the `if` or `elif` reserved words". The `||` form keeps the three-way status readable, which matters because the block has to distinguish 0, 1 and 2 rather than just succeed or fail.
- **Not `[ … ] && exit 1`.** When the test is false that list's status is 1, and if the navbook block is the last thing in the hook, that becomes the hook's exit status — blocking every commit instead of none. The installer appends, and something else may append after us, so the block cannot assume its position either way. The full `if` has no such edge.
- **A prefixed variable name.** The block runs in the same shell as somebody else's hook; `status` is a plausible name for them to be using. `navbook_status` cannot collide by accident.

Not chosen: `set +e` at the top of the block. It would be robust against `set -eu -o pipefail` too, but it silently changes the shell for everything appended *after* our block, which is the same discourtesy in the other direction.

### 2. Is `set -u` a problem too?

No, and worth confirming rather than assuming: `navbook_status=0` is assigned before it is read, and `command -v` needs no variable. The block is clean under `set -u` and under `set -o pipefail` as written.

### 3. Test — `packages/cli/test/cli/install.test.ts`

The existing tests assert the block is appended and removed exactly; none runs the resulting hook. Add one that does, in the `describe("the pre-commit hook")` block:

```ts
it("does not block a commit when doctor fails for a reason that is not a format violation", () => {
  // A hook that already existed and, like most, uses `set -e`.
  writeFileSync(repo.path(HOOK), "#!/bin/sh\nset -e\necho existing\n", "utf8");
  chmodSync(repo.path(HOOK), 0o755);
  repo.nav(["install", "--hooks", "-y"]);

  // Make `nav doctor --staged` exit 1 — an operational error, not exit 2.
  repo.git(["rm", "-r", "-q", "--cached", ".navbook"]);
  rmSync(repo.path(".navbook"), { recursive: true, force: true });
  writeFileSync(repo.path("file.txt"), "x\n", "utf8");
  repo.git(["add", "file.txt"]);

  const result = repo.git(["commit", "-m", "add a file"]);
  assert.equal(result.code, 0, result.stderr);
  assert.match(repo.git(["log", "-1", "--format=%s"]).stdout, /add a file/);
});
```

and its mirror, which is the half that must keep working:

```ts
it("still blocks a commit on a format violation, under set -e", () => {
  // …same set -e hook, but stage a malformed issue.md so doctor exits 2
  assert.notEqual(result.code, 0);
});
```

The second test is the one that would catch an over-correction — a fix that swallows exit 2 along with exit 1 would pass the first test alone.

### 4. Existing hooks are not rewritten

Anyone who ran `nav install --hooks` before this lands keeps the old block; the installer's `if (existing.includes(MARKER_BEGIN)) return;` means a re-run is a no-op. That is the right behaviour for an installer and should not change. Two consequences worth deciding on:

- **`nav doctor` could notice.** It already reads the environment for D9/D10; a check that the installed block is the current one would be new scope and arguably outside "check the tree against the specification". My reading is no — spec 04 §4.3 scopes doctor to the tree, and the `X-` namespace is for extensions, not for the installer.
- **A line in the release notes is enough**: "re-run `nav uninstall --hooks && nav install --hooks` to pick up the fixed pre-commit block." Cheap, honest, and the uninstaller already removes exactly the marked section.

### 5. Order of work

1. Change `BODY`, run `pnpm --filter @navbook/cli test` — the snapshot-ish tests that match the block's text will fail and want updating.
2. Add the two behavioural tests.
3. `pnpm check`.

### Risks

Very low. The block is self-contained, the change is three lines, and the failure mode of getting it wrong is caught by the second test above.

### Done when

The repro in this issue gives `commit exit=0 head=add a file` in both the `set -e` and the plain case, and a staged format violation still blocks in both.
