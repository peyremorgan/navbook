## Against the ask

"Exposing the core lib's read & write operations" is covered:

- **Reads:** `issues`, `issue`, `prs` (with `allRefs` for the cross-branch
  scan), `pr`, `features`, `feature`, `doctor`, `viewer`, `reviewPolicy`,
  `people`.
- **Writes:** `openIssue`, `updateIssue`, `closeIssue`, `reopenIssue`,
  `updatePr`, `addComment`, `linkIssue`, `unlinkIssue`, `createFeature`,
  `updateFeature`, `addSpec`, `updateSpec`.

The operations core exposes but the schema does not — `openPr`, `executePrMerge`,
`executeEntityDelete`, `initWorkspace`, `doctor --fix`, feature/document rename
and delete — are excluded on purpose, not missing: they are checkout-centric
maintainer actions per spec 06 §6.3, and both `schema.graphql` and the package
README say so where a reader will meet them. Nothing about the format is
reimplemented server-side; clients send fields and core composes the files.

Beyond the ask, it also carries OIDC bearer identity mapped onto `author:`
(the non-committer gateway of §6.2), the pull/commit/push sync loop under one
lock with `SYNC_CONFLICT` surfaced rather than resolved, machine-readable
`extensions.code` on every failure, a Dockerfile wired into `compose.yaml`, and
resolver types generated from the schema and committed with a `codegen:check`
gate in CI.

## Not blockers for this ticket

The follow-up work already has its own tickets and none of it falls inside this
issue's scope: #gkbu9yhp (an authorization policy — today any token the issuer
signs for the audience may write), #d8l5m6ub (publish the container images,
describe a Kubernetes deployment), #hc9g6iog and #i6nzbn1d (web client OIDC
discovery and resource indicators). The two documented limits worth carrying
forward — git runs synchronously, so a slow fetch or push blocks concurrent
requests, and two clients editing one issue are last-write-wins rather than
detected — are stated in the README and, if either is to be acted on, deserve
tickets of their own rather than holding this one open.
