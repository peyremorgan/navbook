Confirmed on `dev` (e163c39), black-box through the server test harness.

## Repro

A test using `test/helpers/harness.ts` from `packages/server`:

1. `openIssue` with title `Original`.
2. Two clients read it (`issue(ref:) { title }`) — both see `Original`.
3. A sends `updateIssue({ ref, title: "A's title" })` — lands, `docs(issue): edit #…`.
4. B sends `updateIssue({ ref, title: "B's title" })` from the page rendered in step 2.

Observed: step 4 returns `200` with no `errors`, and a second `docs(issue): edit` commit. The issue now reads `B's title`; A's title exists only in `git log`:

```
9b016c1 docs(issue): edit #rm7hh118   ← B, from a stale page
616ba53 docs(issue): edit #rm7hh118   ← A
41c8295 docs(issue): open #rm7hh118
```

Introspection confirms there is nothing for B to have sent: `Issue` has no `baseSha` (fields: `id slug kind status path archived title author created labels assignees milestone features body comments rank deadline resolution duplicateOf parent subtasks`), and `UpdateIssueInput` is `ref title body labels assignees milestone features rank deadline`. Same for `Pr` / `UpdatePrInput`.

## Where it is in the code

- `packages/server/src/resolvers/mutation.ts`, `patchEntity`: reads the file, `applyEntityPatch`, validates, writes, `applyEntityEdit`. No precondition of any kind between the read and the write beyond the lock and the pull.
- `packages/server/src/patch.ts`, `applyEntityPatch`: field-scoped, which is why *different* fields already survive each other, as the description says.
- What exists for features: `packages/core/src/ops/feature.ts` `assertUnchanged` (called by `editFeature`/`editSpec` with `EditOptions.baseSha`, raising `stale-content`), and `packages/server/src/resolvers/feature.ts` `hashOf`, which batches `git hash-object` per feature record in a `WeakMap`.
- Web: `useFeatureMutations.ts` passes `STALE_CONTENT` through as `handledCodes` and `staleContent()` reads it; `SpecEditor.vue` keeps the draft and shows what the file says now. `useIssueMutations.updateIssue` swallows every failure, and `pages/issues/[ref].vue` / `pages/prs/[ref].vue` send `buildEntityPatch`'s output with no hash.
- `packages/server/README.md` line 172 still says two clients editing one issue are last-write-wins.

## Notes for the fix

- `EntityRecord` keeps no raw file text (`parsed` is the YAML reading), so the hash comes from `git hash-object` as it does for features, and is best taken under `sync.locked()` the way `Feature.commits` is, so a directory mid-move never hashes to nothing.
- Per-field comparison: the base version is `git cat-file blob <baseSha>` in the clone; the current one is the file after the pull. Compare only the keys the patch names (`title`, `body`, `labels`, `assignee`, `reviewer`, `feature`, `milestone`, `rank`, `deadline`), reading list keys through core's readers so `assignee: A` and `assignee: [A]` do not count as a move. A sha the clone cannot resolve is stale by definition.
- The refusal can carry the moved keys in `extensions.moved`, the same way `REPARENT_REQUIRED` carries `currentParentId`, so the client can say which field it was.
