Investigation (2026-09-27), on dev at `2a881d1`. The experiments ran in the production image `navbook-server:rcsql1v9`: git 2.54.0, tini `-s`, no git config set. **Partly confirmed, and the mechanism needs correcting.**

| Claim | Result |
|---|---|
| Background git work outlives the drain, and `docker stop` SIGKILLs it | **Reproduced end to end** with the real image, entrypoint and `nav-server` |
| A killed job can leave a lock in the volume | **Reproduced** for `commit-graph-chain.lock`. For `packed-refs.lock`, the effect was reproduced with a planted lock; a real kill did not land in its window |
| A stale lock makes the next start's ref updates fail | **Reproduced for `packed-refs.lock`, and it is worse than described:** every read and write fails with `GIT_ERROR` until someone deletes the lock by hand |
| Background work running beside the server makes its updates fail with "cannot lock ref" | **Not reproduced**: 900 operations, 0 failures |
| (new) A killed repack leaks a partial pack as big as the repository | **Reproduced**: 150 MB, never cleaned up |

## Correction: it is `maintenance`, not `gc`

With default config, git 2.54's `commit`, `fetch` and `merge` start `git maintenance run --auto --quiet --detach`, not `gc --auto`. A trace over 120 commits (GIT_TRACE2_EVENT) shows the tasks it actually runs:

```
120  git maintenance run --auto --quiet --detach
 16  git repack -d -l --cruft --cruft-expiration=2.weeks.ago --quiet --write-midx
  8  git repack -d -l --geometric=2 --quiet --write-midx
 17  git multi-pack-index write --stdin-packs …
  1  git commit-graph write --split --reachable --no-progress
```

With many loose refs it also runs `git pack-refs --all --prune --auto`. After fetching 40 new branches, the next run packed them (12 loose refs did not trigger it). The server's clone has one loose ref per branch on origin, so this does happen.

So `gc.pid` and `gc.log` never come into play. The setting that matters is `maintenance.autoDetach`, not `gc.autoDetach` (see the options below).

## 1. It outlives the drain (real image, real `docker stop`)

The server ran as in production: `docker run` of `navbook-server:rcsql1v9` with the real entrypoint, a clone on a bind mount, and `NAV_SERVER_PULL_INTERVAL_MS=1000`. 7,000 loose objects were added to the clone, standing in for months of small commits and fetches. The server's own background fetch then started maintenance. Just before `docker stop`:

```
PID   PPID  PGID  SID   COMMAND
    1     0     1     1 /sbin/tini -s -- /entrypoint.sh
    7     1     7     1 node /app/node_modules/.bin/nav-server
  175     1   175   175 git maintenance run --auto --quiet --detach
  176   175   175   175 git repack -d -l --cruft --cruft-expiration=2.weeks.ago --quiet --write-midx
  177   176   175   175 git pack-objects … .git/objects/pack/.tmp-176-pack --all --reflog --indexed-objects
```

The maintenance run has its own session (SID 175) and has been handed to tini (PPID 1). `docker stop` took 1.67 s. The server logged `received SIGTERM, finishing in-flight work` and exited, and the kernel killed the repack partway through. Left in the volume:

```
.git/objects/pack/tmp_pack_BhOOJi      150116916 bytes   (the whole repository, half-written)
.git/objects/bitmap-ref-tips_nda6C1
```

Three later starts, each running maintenance to completion, left both files in place. **Every stop that lands during a repack leaks disk equal to the size of the repository.**

## 2. What a kill leaves, by step

I SIGKILLed every git process in the container the moment each file appeared:

| Killed while | Left behind |
|---|---|
| `pack-objects` writing | `objects/pack/tmp_pack_*` (garbage), `objects/bitmap-ref-tips_*` |
| `multi-pack-index write` | `objects/bitmap-ref-tips_*` |
| `commit-graph write` | **`objects/info/commit-graphs/commit-graph-chain.lock`** and `tmp_graph_*` |
| `pack-refs` | not caught in 3 tries even with 20,000 refs. `packed-refs.lock` is held only while the new file is written, about 1 ms; removing the loose refs afterwards is the slow part, and it runs after the lock is released |

## 3. What the stale locks break

**`commit-graph-chain.lock` (from a real kill): low impact, and silent.** The server's `commit`, `fetch --prune`, `push` and `merge --ff-only` all succeed. Every later maintenance run dies at the commit-graph step:

```
$ git maintenance run --auto
fatal: Unable to create '…/.git/objects/info/commit-graphs/commit-graph-chain.lock': File exists.   (exit 1; the detached run's commit-graph child exits 128)
```

Repacking comes before it and still works, so loose objects do not pile up. The commit graph just stops updating for good, which makes history walks slower as the repository grows. Nobody is told, because the detached run's stderr goes nowhere.

**`packed-refs.lock`: a full API outage, until someone intervenes.** This was simulated by planting the file that a SIGKILL between lock and rename leaves. I ran the real `nav-server` through `test/helpers/harness.ts`: refs packed, lock planted, then one branch deleted on origin, as happens whenever a merged PR's branch is removed.

```
read, nothing deleted upstream:   ok {"issues":[]}
write, nothing deleted upstream:  ok {"openIssue":{…,"commit":{"pushed":true}}}
read #1 after the upstream delete: ERROR GIT_ERROR "a git command failed on the server"
read #2 after the upstream delete: ERROR GIT_ERROR
write after the upstream delete:   ERROR GIT_ERROR
read after deleting the lock by hand: ok
```

```
nav-server: background pull failed, reads will pull for themselves: git fetch --quiet --prune origin failed (exit 1):
  error: could not delete reference refs/remotes/origin/fix/b: Unable to create '…/.git/packed-refs.lock': File exists.
nav-server: background pull recovered            ← only after `rm .git/packed-refs.lock`
```

- It behaves the same with the production background pull (`pullIntervalMs` 1000) and with read-time pulls (0). Once the background pull fails, `RepoSync.read` pulls for itself, and `write` always pulls. Both then fail on the same `fetch --prune` (`packages/core/src/git/remote.ts:46`).
- Until a branch is deleted on origin, everything works and nothing looks wrong. Each `git commit` just takes about 1.2 s longer and prints the lock error on stderr.
- A restart does not clear it, and the entrypoint deliberately does not repair a clone.

**Likelihood:** low. It needs a stop, a `pack-refs` run and a window of about 1 ms to coincide, and `pack-refs` only runs after roughly 40 or more new branches have piled up as loose refs. **Impact:** everything is down until an operator runs `docker compose exec api rm .git/packed-refs.lock`.

## 4. "Cannot lock ref" while maintenance runs beside the server: not reproduced

I ran 300 rounds, each deleting one branch on origin and adding one, then running `fetch --prune`, a commit and a push: 900 server-like operations. Beside them, `git pack-refs --all --prune` ran back to back, far more often than auto maintenance ever runs it. None of the 900 operations failed. The two failures were on the `pack-refs` side (`cannot lock ref 'refs/heads/main': is at … but expected …`): when the two race, `pack-refs` gives way and skips that ref. Git's retry timeouts (`core.packedRefsTimeout` 1 s, `core.filesRefLockTimeout` 100 ms) absorb the overlap.

## Options, updated

- **`maintenance.autoDetach=false`** through the entrypoint's `git_config`. Verified in the image: the fetch then runs `git maintenance run --auto --quiet --no-detach` inline, and nothing is left running once it returns. The cost: with 7,000 loose objects in the 150 MB test repository, that fetch took **7.7 s**, holding the network mutex the whole time.
  - It stays inside `NAV_SERVER_GIT_TIMEOUT_MS` (30 s) here, but not necessarily on a larger clone.
  - A timeout's SIGTERM reaches only the parent git (`packages/core/src/git/exec.ts:160`, `child.kill`), so the maintenance child would carry on as an orphan. Killing the process group (`spawn(…, { detached: true })` plus `process.kill(-pid)`) would close that gap.
- **`maintenance.auto=false`**, with the server running `git maintenance run --auto --no-detach` itself, under `RepoSync`'s lock and its own timeout, between operations.
- **Leaving it and cleaning up at start** is still against the entrypoint's no-repair rule. A narrow version is defensible, though: remove only `packed-refs.lock`, `commit-graph-chain.lock` and `tmp_pack_*`/`tmp_graph_*`/`bitmap-ref-tips_*`, and only after `nav-server` is certain nothing else runs in the container. These are git's own lock and temp files, not conflicted work.

Whichever is chosen, the tini reaping from #rcsql1v9 stays as a backstop.
