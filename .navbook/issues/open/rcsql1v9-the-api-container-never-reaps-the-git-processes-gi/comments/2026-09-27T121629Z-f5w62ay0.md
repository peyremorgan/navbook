### Repro (local, image `navbook-server:2ebc8ce`, Node as PID 1 as in production)

A small script run as `docker run --rm --entrypoint node -v ./t.js:/t.js:ro navbook-server:2ebc8ce /t.js`. It uses git 2.54.0 with **default config**: it makes 3 commits in a fresh repo, clones it, then runs a `git fetch` and a `git pull` in the clone:

```
after-default-commits-and-clone zombies=3
after-fetch zombies=7
```

A second run set `gc.auto=1` and added a `sh -c 'sleep 1 & exit 0'` orphan. Run without an init:

```
PID   PPID  STAT COMMAND
    1     0 S    node /t.js
   21     1 Z    [git]
   25     1 Z    [git]
   29     1 Z    [git]
   32     1 Z    [sleep]
zombies=4
```

The same script with `docker run --init …`:

```
    1     0 S    /sbin/docker-init -- node /t.js
    7     1 S    node /t.js
zombies=0
```

So the default config is enough. After each commit or fetch, git starts its maintenance or gc job in the background and returns without waiting for it. That background process is handed to PID 1, and Node never waits on it. Navbook's own spawns in `packages/core/src/git/exec.ts` (`spawnSync` and `spawn`) are waited on, so the server itself is not leaking.

### Code pointers
- `packages/server/docker/entrypoint.sh` (last line): `exec nav-server "$@"`, so Node is PID 1
- `packages/server/Dockerfile:88`: `ENTRYPOINT ["/entrypoint.sh"]`, with no init in the image (the only package added at line 52 is `apk add --no-cache git ca-certificates`)
- `compose.yaml:18`: the `api:` service, with no `init: true`

### Fix options (pick one, or combine)
1. `init: true` on `api` in `compose.yaml`. This is one line and covers Compose only.
2. Put an init in the image: `RUN apk add --no-cache tini` and `ENTRYPOINT ["/sbin/tini", "--", "/entrypoint.sh"]`. This covers Compose and the Kubernetes example in #d8l5m6ub.
3. Stop git from starting background jobs at all: in `entrypoint.sh`, after the clone, run `git config gc.autoDetach false` and `git config maintenance.autoDetach false`. The auto job then runs inside the git command Navbook waits on. Downside: occasionally a slower request.
