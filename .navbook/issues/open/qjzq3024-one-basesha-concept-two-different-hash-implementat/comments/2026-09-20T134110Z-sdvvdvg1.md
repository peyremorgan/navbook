## Implementation plan

Decision taken: **unify on core's `blobSha`**. Features and documents move off `git hash-object`; the entity side is already there. The schema stops calling the value "the blob hash", because after this it is Navbook's own token rather than git's.

The argument that settles it is the one in `tree.ts` and repeated in `resolvers/entity.ts`: the hash is taken *of the exact text the record was parsed from*, so a record and its hash can never disagree. Asking git means a second read of the file, and the window between the two is exactly what the server's mutex exists to close. Moving the feature side onto the same rule removes a subprocess, removes a cache, and makes the concurrency story one story instead of two.

### 1. Carry the hash on the records — `packages/core/src/core/tree.ts`

`EntityRecord.blobSha` exists; `FeatureRecord` and `SpecRecord` do not have one.

```diff
 export interface SpecRecord {
   fileName: string;
   path: string;
+  /** The git-shaped hash of this file's text, exactly as it was parsed. */
+  blobSha: string;
   parsed: ParsedFile;
   …
 }

 export interface FeatureRecord {
   slug: string;
   dirPath: string;
   filePath: string;
+  /** The git-shaped hash of `feature.md`'s text, exactly as it was parsed. */
+  blobSha: string;
   …
 }
```

and in `materializeFeature`, beside the existing fields:

```diff
   specs.push({
     fileName,
     path,
+    blobSha: blobSha(files.get(path) ?? ""),
     parsed: specParsed,
     …
   });
…
   return {
     slug: draft.slug,
     dirPath: draft.dirPath,
     filePath: draft.featureFile,
+    blobSha: blobSha(files.get(draft.featureFile) ?? ""),
     …
   };
```

Note this interacts with #egvv9205's lazy tree: both ask `files.get` for a file they already parse, which is why that plan memoises reads.

### 2. The stale check gets simpler — `packages/core/src/ops/feature.ts`

`assertUnchanged` currently shells out to git for the file on disk. With the hash on the record it compares two values it already holds — and, importantly, the record was loaded *inside* the write transaction by `findFeature`, so it is current by construction.

```diff
-function assertUnchanged(
-  ws: WsCtx,
-  filePath: string,
-  describe: string,
-  baseSha: string | undefined,
-): void {
-  if (baseSha === undefined) return;
-  const current = hashObject(ws.repoRoot, absPath(ws, filePath));
-  if (current !== null && current === baseSha) return;
+/**
+ * Refuse a write whose author was looking at an older version of the file.
+ *
+ * Compared against the hash the record carries, which is of the text this
+ * very load parsed — so there is no second read to disagree with the first,
+ * and no window between the check and the write.
+ */
+function assertUnchanged(current: string, describe: string, baseSha: string | undefined): void {
+  if (baseSha === undefined) return;
+  if (current === baseSha) return;
   wsFail("stale-content", `${describe} changed since you opened it`, [
     "reload it and apply your change to what it says now",
   ]);
 }
```

Call sites become `assertUnchanged(feature.blobSha, …)` and `assertUnchanged(spec.blobSha, …)`. The `ws` and `absPath` arguments go, and with them the last reason `ops/feature.ts` imports from `git/`.

### 3. The resolver loses a cache — `packages/server/src/resolvers/feature.ts`

Delete `HASHES`, `hashesOf` and `hashOf` outright — roughly 45 lines, including the `WeakMap` keyed by record and the comment explaining why it had to be keyed that way. That subtlety ("two writes to one feature in a single request would otherwise have the second reported with the first's hashes") disappears with the cache, because a fresh record now carries a fresh hash as a matter of course.

```diff
-  baseSha: (feature, _args, ctx) => hashOf(ctx, feature, feature.filePath),
+  baseSha: (feature) => feature.blobSha,
…
-  baseSha: ({ feature, spec }, _args, ctx) => hashOf(ctx, feature, spec.path),
+  baseSha: ({ spec }) => spec.blobSha,
```

Both then match `sharedFields`' `baseSha: (parent) => record(parent).blobSha` exactly, which is the consistency this issue is about.

### 4. Say what it is — `packages/server/schema.graphql`

Four fields claim to be "the blob hash". After this they are not git's, and the schema should stop implying a client could look one up:

```diff
   """
-  The blob hash of `issue.md` as it now stands.
+  A token for the version of `issue.md` this was read from.
+
+  Opaque: its only contract is that handing it back unchanged identifies the
+  same text. It is shaped like a git blob hash and is not one — git applies
+  `.gitattributes` filters and end-of-line conversion that this does not, so
+  the two differ in a repository that configures either.

   Hand it back as `baseSha` when editing a field from a rendered value, and an
   edit made against an older version of that field is refused rather than
   landed on top of somebody else's …
   """
   baseSha: String!
```

and the same on `Pr.baseSha`, `Feature.baseSha`, `Spec.baseSha` (the latter two currently cross-reference `Issue.baseSha`, so they can keep doing that and inherit the correction).

Regenerate both codegen outputs — the types do not change, but `codegen:check` compares the whole file including descriptions.

### 5. Amend `hash.ts`'s own justification

```diff
- * A blob's hash is SHA-1 over `blob <byte length>\0<content>`, and that is
- * what `git hash-object` prints for a file in a repository with no clean
- * filters — the default, and what every clone Navbook makes for itself is.
+ * SHA-1 over `blob <byte length>\0<content>` — git's shape, which makes the
+ * value recognisable and lets a caller resolve it with `cat-file` when the
+ * repository happens to store its objects the same way. It is deliberately
+ * *not* asked of git: `git hash-object` applies `.gitattributes` filters and
+ * end-of-line conversion, so its answer depends on configuration, while this
+ * one is a function of the text alone. What this names is a version of some
+ * text, not an object in a store.
```

### 6. The fallback path in `mutation.ts` is where the two worlds still meet

`assertFieldsUnmoved` resolves an unrecognised `baseSha` with `blobContent` — `git cat-file blob <sha>` — to compare fields against the version the client actually saw. That only works where core's hash and git's coincide, which is the default configuration and not all of them.

It already fails safe: an object the store does not hold reads as `null` and the write is refused as stale. Keep it, and make the comment say what it is — a best-effort recovery that works in the common configuration — rather than implying it always resolves. This is the one place the "not git's hash" change has a visible consequence, and it is a degradation from "we can tell you which field moved" to "reload and try again".

### 7. `hashObjects` / `hashObject` become unused

The only remaining callers are tests. Options:

- **Keep them.** They are a correct, batched wrapper over `git hash-object` and a future caller may want git's real answer.
- **Remove them.** `@navbook/core` is 0.3.0 and pre-1.0, so dropping two exports is cheap now and expensive later.

My recommendation is to **keep them and add one sentence** to `index-ops.ts` saying they are git's hash and `core/hash.ts` is Navbook's token, so the next reader does not have to work out which to reach for. Two functions that look interchangeable and are not is how this issue happened; a comment is the cheapest fix for that.

### 8. Tests

- **`packages/core/test/feature-ops.test.ts`** — four places (16, 276, 298, 310) import and call `hashObject` to build a `baseSha`. They become `blobSha(readFileSync(path, "utf8"))`, or better, read it off the record the test already has.
- **New, in the same file** — the property this change actually buys: load a feature, mutate the file on disk behind the tool's back, and assert that a write carrying the record's `baseSha` is still accepted (the record and its hash agree) while one carrying a hash of the *old* text is refused. That is the thing the git-based version could get wrong.
- **A non-default git configuration** — set `core.autocrlf=true` or a `.gitattributes` clean filter in a fixture repository, then round-trip a feature edit and an entity edit with `baseSha`. Both should now behave identically; before this change they would not. This is the regression test for the issue as filed.

### 9. Order of work

1. `tree.ts` record fields; `pnpm --filter @navbook/core typecheck`.
2. `ops/feature.ts` `assertUnchanged` and its two call sites.
3. `resolvers/feature.ts` — delete the cache.
4. Schema descriptions + both codegens.
5. `hash.ts` and `index-ops.ts` comments.
6. Tests, including the non-default-git one.

### Risks

- **`baseSha` values in flight across the change.** A browser holding a page rendered before the deploy hands back a git-computed hash afterwards. In the default configuration the two are identical and nothing happens; in a filtered repository the save is refused as stale, which is the safe direction and is what a reload fixes.
- **The value is no longer resolvable with `cat-file` in a filtered repository.** Only `assertFieldsUnmoved`'s recovery path cares, and it already degrades correctly.

### Done when

All four `baseSha` fields come from `blobSha`, `resolvers/feature.ts` runs no subprocess, a feature edit and an issue edit behave identically under `core.autocrlf=true`, and nothing in the schema calls the value a git blob hash.
