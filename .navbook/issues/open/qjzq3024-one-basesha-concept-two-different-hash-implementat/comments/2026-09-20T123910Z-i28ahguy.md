Confirming the two external facts this rests on, since the whole argument is about what git does rather than what we do.

**`git hash-object` applies filters by default.** From [its documentation](https://git-scm.com/docs/git-hash-object): given a path, `.gitattributes` clean filters and end-of-line conversion are both applied, and `--no-filters` exists precisely to turn that off — "Hash the contents as is, ignoring any input filter that would have been chosen by the attributes mechanism, including the end-of-line conversion." The page states the consequence outright: "As a result of applying filters, the actual blob put into the object database may differ from the given file." `--path` exists so a caller can say which filters apply to content that is not at that path.

So the divergence is not theoretical: `blobSha(text)` is `git hash-object --no-filters --stdin`, and `hashObjects(cwd, paths)` is `git hash-object <path>`. Those are two different commands, and we call each of them "the blob hash".

**SHA-256 repositories are a real thing people have.** `extensions.objectFormat` has been in git for years; the [hash function transition](https://git-scm.com/docs/hash-function-transition) is the design document, and as of 2026 the format works and the gap is forge support rather than git itself — Bitbucket and JGit (so Gerrit) are the usual laggards, while GitHub and GitLab have moved. Anyone self-hosting, which is the audience this project is built for, can have one today. Git 3.0 makes it more visible still.

**Two smaller notes on the fix.**

- If the entity side moves to git, remember that `EntityRecord.blobSha` is also computed for records built from *blobs* rather than from disk — `scanRefsForOpenPrs` parses a pull request straight out of a ref, and `stagedRepo` out of the index. There is no working-tree path to hash in either case. The `blobSha` those records carry today is at least well-defined; a git-based one has to be absent, and the schema's `baseSha: String!` would need to become nullable or the resolver has to return `""`, which `resolvers/feature.ts` already does for a file git could not hash ("Empty is the safe answer: … a value that can never match is refused").
- The current asymmetry has one accidental virtue worth not losing: `blobSha` is taken of *the exact text the record was parsed from*, so a record and its hash can never disagree — the comment in `tree.ts` makes that argument, and `resolvers/entity.ts` repeats it ("a field resolver runs after its parent's transaction has let go, and a hash taken then could name a version the rest of the payload does not"). Any move to `git hash-object` reintroduces a second read, and the window it opens is exactly what the server's mutex is for. That is an argument for the *other* direction — making the feature side match the entity side — and it is stronger than it first looks.

A test would show the divergence immediately: set a clean filter or `core.autocrlf` in a fixture repository, then round-trip an entity edit and a feature edit with `baseSha`. Neither half is covered under a non-default git configuration today.
