## The data is already fetched, and thrown away

`PrDetail` spreads `PrListItem`, which spreads `EntityCore` (`packages/web/app/graphql/fragments.ts:62` and `:146`). That is where `labels`, `assignees`, `milestone` and `features` come from, and it is why the page can render them as text at all. So the query needs no change to fix this: every value an editor would start from is already in the cache, and the mutation the page already calls returns the same fragment. The gap is entirely between the fragment and the template.

## When the README became wrong

`git log -S` dates the two halves:

- `1581c51` (2026-09-03) wrote the `packages/web/README.md` sentence. On that day the page was read-only — `git show 6461b05:packages/web/app/pages/prs/[ref].vue` has no `UPDATE_PR`, and `mutations.ts` had no `updatePr` at all. "Updating a pull request is not here" was simply true of the client, and the "API does not expose them" clause was borrowed from the server README's verb list (`9eaf70b`, 2026-09-01) where it refers to `nav pr update`.
- `9baae42` (2026-09-07, "show who owes a review, and ask for one") added `updatePr` to the client and scoped it to reviewers only, with the "Only `reviewers` is editable here" comment at line 121. It touched twelve web files and neither README.

So the sentence was accurate when written and became false four days later, when the client began doing the thing the sentence says the API forbids. That is the mechanism: a client-side "not here" and an API-side "not exposed" were written as one clause, and the first half changed without the second being re-read.
