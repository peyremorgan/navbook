Confirmed, and the documentation half has a root cause worth writing down: two different things are both called "update".

## The API does support it

`updatePr` is not a special resolver. `packages/server/src/resolvers/mutation.ts:179` hands straight to the same `patchEntity` that `updateIssue` uses one line above it, which applies `applyEntityPatch` generically and then validates with `validatePr`:

```ts
updateIssue: (_parent, { input }, ctx) =>
  run(async () => {
    const { result, pushed } = await patchEntity(ctx, "issue", input);
    ...

updatePr: (_parent, { input }, ctx) =>
  run(async () => {
    const { result, pushed } = await patchEntity(ctx, "pr", input);
```

There is a server test that patches a pull request's milestone and expects it to land — `packages/server/test/server/pr.test.ts:365`, inside "clears the request with an empty list, and leaves it alone when unmentioned":

```ts
assert.deepEqual(await reviewers(`milestone: "v2"`), ["alice@example.com", "bo@example.com"]);
```

It is asserting that reviewers survive an unrelated patch, but the patch it sends is a milestone edit on a pull request, and it succeeds. So the field is exercised in CI today.

## The client is where it stops

`packages/web/app/pages/prs/[ref].vue` builds the full seven-field `before`, then hands the builder exactly one field, and says so:

```ts
/*
 * Only `reviewers` is editable here, so the patch is built against a `before`
 * that names only what this page can change [...]
 */
async function saveReviewers(reviewers: string[]): Promise<void> {
  ...
  const built = buildEntityPatch(before, { reviewers });
```

Labels, assignees and milestone are rendered as plain `<section>` blocks at lines 285–304, each behind a `v-if` on the value being non-empty — so on a pull request with no labels there is not even an empty control to reveal that labels exist. The title and body have no editor at all; there is no `EditableText` or `FieldEditor` on the page (`grep` finds neither).

Nothing else is missing. `EntityEdit` in `app/utils/patch.ts` already declares every field, `buildEntityPatch` already diffs all of them and already handles `reviewers` as the pull-request-only one, and the generated `UpdatePrInput` already types all seven. The work is wiring, not logic.

## Repro

```sh
pnpm --filter @navbook/web dev:stack
```

Open <http://localhost:3000/prs>, pick any pull request. The sidebar shows Reviewers with an edit affordance; Labels, Assignees and Milestone render as text with none, and the title is static. Then, against the same stack at <http://localhost:4000/graphql>:

```graphql
mutation { updatePr(input: { ref: "<that ref>", labels: ["needs-docs"] }) { pr { labels } commit { subject } } }
```

It returns the new labels and commits. The browser will show them after a refetch — it just has no way to ask for them.

## Root cause of the README error

`packages/server/README.md` is correct where it says pull request "`merge`, `open` and `update`" are not exposed. Those are CLI verb names, and `nav pr update` is a different operation from patching metadata — it appends a revision pinning the current HEAD:

```console
$ nav pr update --help
Usage: nav pr update [options] <id>

append a revision pinning the current HEAD
```

Patching a pull request's fields is `nav pr edit` in the CLI, and `updatePr` in the API. Both exist.

`packages/web/README.md` then cites that sentence in prose, where "updating ... a pull request" no longer reads as a verb name but as the ordinary English word — and in that reading it is false. The fix is to stop borrowing the verb vocabulary into a sentence that is not about verbs.

## Not locked in by a test

`packages/web/test-e2e/pull-requests.spec.ts` asserts nothing about labels, assignees or milestone being read-only, so nothing has to be reworded to change the behaviour.
