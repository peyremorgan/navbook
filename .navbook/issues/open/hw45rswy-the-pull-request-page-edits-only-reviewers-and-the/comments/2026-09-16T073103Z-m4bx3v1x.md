## Plan

**Recommendation: land `#zhbkqxr1` rather than start over.** The branch does what the design below asks, merges onto today's `dev` without conflict, and carries regression tests that fail on the unfixed page. What follows is the design the fix should satisfy, so it can be reviewed against something other than itself, then the review checklist, then the landing steps.

### Design

The pull request page becomes the issue page minus what a pull request does not have, and plus what only it has. Concretely:

1. **One `save(change, wrote)` over `buildEntityPatch`**, replacing `saveReviewers`. The `before` it compares against is a `computed<EntityEdit>` built from the fetched pull request, with all seven fields. Keep the one-field-at-a-time rule from the issue page: `updatePr` tells an absent key from an explicit null, so sending the whole form would rewrite frontmatter nobody touched. A `PatchError` (empty title or body) is a toast, not a request. A null patch is a no-op, because the server refuses an empty patch and a closed editor must not send one.

2. **Title and description as `EditableText`**, with `required`, exactly as the issue page has them. The `<h1 data-testid="pr-title">` stays inside the slot so nothing that reads it today breaks.

3. **Labels, Assignees, Features and Milestone as `LabelEditor`s**, in that order, in the aside, below Reviewers. `single` on Milestone, `link-to="/features/"` on Features. Assignees keep the avatar rendering the page already had via the `#display` slot, and must then say "None" themselves, because a display slot suppresses the component's own empty text. Drop the `v-if` on the value being non-empty: an empty field with no control is the bug.

4. **Suggestions from where the issue page gets them**: a cached `PRS_QUERY` with `{ filter: {}, allRefs: false }` for labels and milestones (the format has no registry for either; that is also the cache entry a bare `/prs` fills, since an empty filter is sent as `{}`), `FEATURES_QUERY` for features, `usePeople()` for assignees and reviewers.

5. **`disabled` on `EditableText`**, worded and behaving as `LabelEditor`'s does, so that a `PRECONDITION` refusal withdraws every editor rather than only the one that was refused. The refusal is about the branch and is the same answer for all of them.

6. **Out of scope, on purpose**: `rank` and `deadline` (spec 02 §2.5, an issue's alone), and nothing on the server. `UpdatePrInput`, `patchEntity` and `validatePr` are already right; a fix that touched `packages/server` would be fixing the wrong side.

7. **Documentation**: the `packages/web/README.md` paragraph separates "the API does not expose it" (opening, appending a revision, merging, deleting) from what the client does. Name `nav pr update` as appending a revision and say that patching the fields is `nav pr edit` and `updatePr`, so the next reader does not make the same inference. The "Pull requests" summary paragraph and `.navbook/specs/web/client.md` say "read, reviewed and edited". The page's header comment stops saying "Read apart from commenting".

8. **Tests**, all end-to-end in `packages/web/test-e2e/pull-requests.spec.ts`, because the page's behaviour is the thing under test: edit a label and a milestone on `bbbb0001` and reload to prove the write landed rather than the cache being told; retitle in place; and extend the existing unserved-branch test to assert every `edit-*` control is gone, not just `edit-reviewers`. Fresh values per run (`Date.now()`), since the suite shares one repository. No unit test is warranted: `buildEntityPatch` is already covered for all seven fields in `test/nuxt/patch.test.ts`.

### Review checklist for `#zhbkqxr1`

I read the diff against the design above. It matches on every point. Things worth a reviewer's eye rather than mine, since the branch is also authored as `Claude` and `selfReview` is on in `navbook.json`:

- The two new e2e tests and the widened unserved-branch assertion were, per the pull request, run against the unfixed page and fail there. That claim is checkable by cherry-picking only the spec change onto `dev` and running the suite.
- `save` reports `refreshListings()` on every field, not only reviewers. Labels and milestone change listing rows, so that is right, but it is one more listing fetch per edit than before.
- Milestone and label suggestions come from pull requests alone. Milestones usually span issues too, so a reviewer may want the issue listing merged in. Not blocking; every menu accepts a value not in it.
- `EditableText` for the body is `required`. `validatePr` requires a body, so that matches the server; worth a glance if anyone expects an empty description to be allowed.

### Landing

```sh
git checkout dev && git pull
nav pr show zhbkqxr1                       # after: git checkout fix/hw45rswy-pr-editable-fields
pnpm check && pnpm test                    # on the branch
pnpm --filter @navbook/web build && pnpm --filter @navbook/web test:e2e
nav pr review zhbkqxr1 --approve -m "..."  # by a reviewer who is not the author
git checkout dev && nav pr merge zhbkqxr1 --commit
nav issue close hw45rswy --resolution fixed --commit
```

The review must be recorded by someone other than the branch's author; on this repository that is @morgan.peyre@brickcode.tech, who is already asked. Merging carries the pull request's discussion into `dev`'s history, and the close commit on `dev` is what finally ends this issue.

### If it is not landed

Should the branch be declined, the steps above are the implementation in full and should take an afternoon: steps 1 to 5 are one file and one prop, 7 is prose, 8 is forty lines of Playwright. There is no smaller correct fix. Making only the sidebar editable would leave the title and body as the same bug with fewer fields, and correcting only the README would document a limitation the code has no reason for.
