Worth recording the underlying git behaviour in the spec text, because the setting is doing more work than "a nicety" and the exact default matters.

From [git's `merge` configuration documentation](https://git-scm.com/docs/merge-config), `merge.directoryRenames` decides "what happens at merge time to new files added to a directory on one side of history when that directory was renamed on the other side":

- `false` — detection is off, and such new files are **left behind in the old directory**.
- `true` — the new files are **moved into the new directory**.
- `conflict` — **a conflict is reported for such paths**.
- **The default is `conflict`.**

That is precisely the pair spec 03 §3.3.1 describes: a comment added on one branch while the issue is closed (its directory renamed) on another. Under the default, git places the comment correctly and *then* marks the path unmerged, which is why §3.3.1 says "the content is already correct; `git add` on the path and a commit finish it". Setting `true` removes the stop.

Two details that belong in whatever text gets written:

- **`merge.renames` overrides it.** Git's documentation is explicit: "If `merge.renames` is false, `merge.directoryRenames` is ignored and treated as false." Anyone who has turned rename detection off for performance on a large repository gets the worst case — the comment left in the old directory, silently — and `nav install` setting `merge.directoryRenames=true` will not help them. That is a genuine limit of the advice and is not currently stated anywhere.
- **Local, not global, is the right scope and is worth saying why.** The alias is a property of the person (they type `git nav`), so it is `--global`. This is a property of the repository (its tree is laid out so that a directory rename means a status change), so it is `--local`. `install.ts` already does this correctly; the spec should say it, because a reimplementer reading only spec 04 has nothing to tell them which scope to use.

Spec 03 §3.3.1 also notes the behaviour was "verified against git 2.43". The defaults above have been stable since directory rename detection landed in 2.18, so the advice holds, but a version note beside the flag in spec 04 would match §3.3.1's own care.
