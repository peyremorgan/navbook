### Repro

Checkout's own CLI (`node packages/cli/src/main.ts`), in a fresh repository with `HOME` and `GIT_CONFIG_GLOBAL` pointed at a scratch directory so nothing global is touched:

```console
$ nav init
$ git config --local merge.directoryRenames      # exit 1: unset
$ nav install -y
nav install will:
  git config --global alias.nav !nav   (enables 'git nav <cmd>')
  git config --local merge.directoryRenames true   (lets a comment racing a close merge cleanly)
  append the navbook block to …/repo/.git/hooks/pre-commit
  write bash completions to …/home/.local/share/bash-completion/completions/nav
$ git config --local merge.directoryRenames
true
$ nav uninstall -y
nav uninstall will:
  git config --global --unset alias.nav
  git config --local --unset merge.directoryRenames
  …
```

So a bare `nav install` does four things, and spec 04 lists three.

### The git behaviour, checked on git 2.55.0

The plan's two extra facts hold on a current git. The test is a minimal version of the race in 03 §3.3.1: `issues/open/abc/` already holds `comments/1.md`, one branch adds `comments/2.md`, and `main` moves the directory to `issues/closed/abc/`. Then `git merge comment` on `main`:

| Local config | `git merge` exit | Where `2.md` lands | Status |
|---|---|---|---|
| (default, i.e. `conflict`) | 1 | `issues/closed/abc/comments/2.md` | `UA`: placed correctly, stops to ask |
| `merge.directoryRenames=true` | 0 | `issues/closed/abc/comments/2.md` | clean |
| `…=true` + `merge.renames=false` | 0 | `issues/open/abc/comments/2.md` | clean, **and wrong** |

The last row is the bad one. The merge succeeds, and the comment stays behind in `open/` beside no `issue.md`. The user sees nothing until `nav doctor` flags the stray directory. So the `merge.renames` caveat in step 3 of the plan is a correctness warning, not a footnote, and it goes in spec 03 §3.3.1 as planned.
