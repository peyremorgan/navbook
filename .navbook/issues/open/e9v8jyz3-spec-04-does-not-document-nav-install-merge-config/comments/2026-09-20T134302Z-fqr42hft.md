## Implementation plan

Documentation only, in one file, with one judgement call to make along the way.

### 1. The synopsis and the bullet — `doc/spec/04-cli.md` §4.3, "Setup"

```diff
-- `nav install [--alias[=NAME]] [--hooks] [--completions[=SHELL]] [-y]` — set
-  up environment integrations:
+- `nav install [--alias[=NAME]] [--hooks] [--merge-config] [--completions[=SHELL]] [-y]`
+  — set up environment integrations:
   - `--alias[=NAME]` — run `git config --global alias.<NAME> '!nav'`
     (see 4.1). `NAME` defaults to `nav`.
   - `--hooks` — install the `pre-commit` hook described in 4.5.
+  - `--merge-config` — run `git config --local merge.directoryRenames true`,
+    which is the SHOULD of [03 §3.3.1](03-merge-and-branches.md): it is what
+    makes a comment racing a close merge cleanly rather than stopping to ask.
+    Local rather than global, because it is a property of a repository whose
+    tree is laid out so that a status change is a directory rename, and not a
+    property of the person running the command.
   - `--completions[=SHELL]` — completions for `SHELL` …

-  With no flags, `nav install` sets up everything: alias (default name), hook,
-  and completions (installed, not printed).
+  With no flags, `nav install` sets up everything: alias (default name), hook,
+  merge config, and completions (installed, not printed).
```

### 2. The `uninstall` bullet, immediately below

```diff
-- `nav uninstall [--alias[=NAME]] [--hooks] [--completions] [-y]` — remove
+- `nav uninstall [--alias[=NAME]] [--hooks] [--merge-config] [--completions] [-y]` — remove
   what `install` set up (no flags: everything it may have installed), with
   the same confirm-or-`--yes` behavior.
```

The parenthetical already covers it semantically; the flag list should match the command's.

### 3. The judgement call: how much git behaviour belongs in spec 04

Spec 03 §3.3.1 already explains *why* the setting matters and is the right home for that. What spec 04 should add is the part a reimplementer needs and cannot infer, and there are two facts worth stating that are currently nowhere:

- **The default is `conflict`, not `false`.** Git's own documentation: `false` leaves new files behind in the old directory, `true` moves them into the new one, `conflict` reports a conflict for such paths — and "Defaults to `conflict`". That is precisely why §3.3.1 can say the content is already placed correctly and the merge merely stops to ask. A reimplementer who assumed the default was `false` would describe the wrong failure.
- **`merge.renames=false` disables it entirely.** Git: "If `merge.renames` is false, `merge.directoryRenames` is ignored and treated as false." So anyone who turned rename detection off — a thing people do on very large repositories — gets the worst case silently, and `nav install --merge-config` will not help them. This is a genuine limit of the advice and is stated in neither document.

My recommendation: put the default in spec 04's new bullet (one clause), and put the `merge.renames` caveat in **spec 03 §3.3.1**, where the advice lives and where a reader is already being told to configure something. A note at the end of that subsection:

```markdown
This setting has no effect where rename detection itself is off: git ignores
`merge.directoryRenames` and treats it as false when `merge.renames` is
`false`. A repository that has turned rename detection off for performance
therefore gets the unrepairable case of 3.3.1 for *every* comment racing a
close, not only the first one.
```

### 4. Not in scope

- **No code.** `install.ts` and `program.ts` are correct; this is the spec catching up with them.
- **No change to the `--local` scope.** It is right, and step 1 now says why.
- **No new flag.** `nav install --merge-config` already exists and behaves as the new text describes — I verified the selective and no-flag paths both reach it.

### 5. A version note, matching §3.3.1's care

§3.3.1 says its behaviour was "verified against git 2.43". Directory rename detection landed in git 2.18 and the three values and their default have been stable since, so the advice holds for every git this project supports (`nav install` itself needs nothing newer). Worth one clause rather than a paragraph.

### 6. Tests

None. This is prose, and there is no mechanism that could assert the spec's flag list matches the CLI's — which is precisely why it drifted. The nearest thing to a guard would be a test that `nav install --help` mentions every flag spec 04 lists, and that inverts the dependency the wrong way: the spec should lead.

What is worth doing instead is a **review habit**, and it is cheap to write down: a change that adds a flag to `program.ts` touches `doc/spec/04-cli.md` in the same commit. Worth a line in the contributing section if one ever gets written.

### 7. Order of work

One commit: `doc(spec): document nav install --merge-config`. Spec 03's caveat can ride along or go separately; they are independent.

### Done when

`doc/spec/04-cli.md` §4.3 lists every flag `nav install` accepts, says what a bare `nav install` does in four items rather than three, and a reader who has met the SHOULD in §3.3.1 finds it confirmed rather than absent.
