## Confirmed on `dev` at `6cf8d86`

Reproduced over HTTP against a real server and clone, using the server test suite's own harness (`startHarness` from `packages/server/test/helpers/harness.ts`), in a repository with three open issues and no pull requests:

```
query { issues { title } }
  -> {"issues":[{"title":"Three"},{"title":"Two"},{"title":"One"}]}, errors: []
query { issues(filter: { reviews: [PENDING] }) { title } }
  -> {"issues":[{"title":"Three"},{"title":"Two"},{"title":"One"}]}, errors: []   <- every issue
query { issues(filter: { reviews: [APPROVED] }) { title } }
  -> {"issues":[]}, errors: []
query { issues(filter: { awaiting: ["a@b.com"] }) { title } }
  -> {"issues":[]}, errors: []
query { issues(filter: { reviewers: ["a@b.com"] }) { title } }
  -> {"issues":[]}, errors: []
query { prs(filter: { deadline: [OVERDUE] }) { id } }
  -> errors: [{"message":"'deadline' describes an issue; pull requests have no deadline","extensions":{"code":"INVALID_INPUT"}}]
```

The CLI, over the same tree, refuses:

```console
$ node packages/cli/src/main.ts issue list review:pending
nav: 'review:' describes a pull request; issues have no reviews
$ echo $?
1
```

### Where it lives now

The audit's line numbers have moved. `issues` now goes through the `listed()` helper, and there is still no guard:

- `packages/server/src/resolvers/query.ts:59-60`: `issues` calls `listed(ctx, "issue", toQuery(args.filter, today(ctx)))` without checking anything.
- `packages/server/src/resolvers/query.ts:71-78`: `prs` has the hand-written `deadline` guard, the mirror that `issues` lacks.
- `packages/server/src/resolvers/map.ts:111-127`: `toQuery` copies `reviewers`, `reviews` and `awaiting` into the core `Query` whichever noun asked.
- `packages/server/schema.graphql:378-381`: the doc on `EntityFilter.reviewers` claims "`issues` rejects them rather than matching nothing".

### The web client sends one of these terms today

As the plan says, `queryToFilter` in `packages/web/app/utils/filter-params.ts` reads `reviewers: queryValues(query.reviewer)` without the gate that `deadline` gets (`keys.deadlines ?? []`), and `toEntityFilter` passes it through. So `/issues?reviewer=alice@example.com` sends `issues(filter: { reviewers: ["alice@example.com"] })` and shows an empty list. `EntityFilterBar` has no reviewer control on the issues page (the `reviewers` prop is absent there), so nothing on screen explains why the list is empty.

### Fix

I'm taking the implementation plan above: split `EntityFilter` into `IssueFilter` and `PrFilter`, so that GraphQL validation refuses the term before any resolver runs, and gate `?reviewer=` in the web client.
