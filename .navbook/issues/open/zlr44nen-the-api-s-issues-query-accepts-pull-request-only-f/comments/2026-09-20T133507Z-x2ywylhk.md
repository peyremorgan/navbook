## Implementation plan

Taking the structural fix rather than the runtime guard: split `EntityFilter` into `IssueFilter` and `PrFilter` so GraphQL's own validator refuses a pull-request term on `issues`. No resolver code is needed for the refusal, and no future term can be forgotten. It is a breaking schema change, so the work reaches codegen, the web client and the tests.

### 1. Schema — `packages/server/schema.graphql`

Replace `input EntityFilter` with two inputs. GraphQL has no input composition, so the seven shared keys are written twice; that duplication is the price of the guarantee and is worth a comment saying so.

```graphql
"""
Which issues to list.

Terms are ANDed across keys. Within a key the semantics follow the field:
single-valued fields OR their terms, multi-valued fields AND theirs (spec 04).

Deliberately separate from `PrFilter` rather than one input with keys that
apply to one noun: spec 04 §4.3 requires a term describing the other kind to
be refused rather than to match nothing, and two inputs make that the
validator's job instead of a check a resolver has to remember.
"""
input IssueFilter {
  status: [Status!]
  labels: [String!]
  assignees: [String!]
  authors: [String!]
  milestones: [String!]
  features: [String!]
  text: [String!]
  "Where the issue stands against its deadline; any one of them matches."
  deadline: [DeadlineState!]
}

"Which pull requests to list. The twin of `IssueFilter`; see it for the shared keys."
input PrFilter {
  status: [Status!]
  labels: [String!]
  assignees: [String!]
  authors: [String!]
  milestones: [String!]
  features: [String!]
  text: [String!]
  reviewers: [String!]
  reviews: [ReviewDecision!]
  awaiting: [String!]
}
```

and on `Query`:

```graphql
issues(filter: IssueFilter): [Issue!]!
prs(filter: PrFilter, allRefs: Boolean! = false): [Pr!]!
```

The prose on `EntityFilter.reviewers` that claims "`issues` rejects them rather than matching nothing" moves onto `IssueFilter`'s doc block as the reason the split exists — it was describing behaviour that did not exist, and after this it describes the type.

### 2. Server — `src/resolvers/map.ts`

`toQuery` becomes two functions, each reading only its own keys. One generic function over a union would compile, but it would also re-open the door: a key present on the union is a key something can read.

```ts
/** The keys both nouns share, which is most of them. */
function baseQuery(filter: IssueFilter | PrFilter | null | undefined, today: string): Query {
  const query = emptyQuery();
  query.today = today;
  if (!filter) return query;
  if (filter.status) query.status = filter.status.map(toCoreStatus);
  if (filter.labels) query.labels = [...filter.labels];
  if (filter.assignees) query.assignees = [...filter.assignees];
  if (filter.authors) query.authors = [...filter.authors];
  if (filter.milestones) query.milestones = [...filter.milestones];
  if (filter.features) query.features = [...filter.features];
  if (filter.text) query.text = [...filter.text];
  return query;
}

export function toIssueQuery(filter: IssueFilter | null | undefined, today: string): Query {
  const query = baseQuery(filter, today);
  if (filter?.deadline) query.deadline = filter.deadline.map((s) => DEADLINE_IN[s]);
  return query;
}

export function toPrQuery(filter: PrFilter | null | undefined, today: string): Query {
  const query = baseQuery(filter, today);
  if (filter?.reviewers) query.reviewers = [...filter.reviewers];
  if (filter?.reviews) query.reviews = filter.reviews.map((d) => DECISION_IN[d]);
  if (filter?.awaiting) query.awaiting = [...filter.awaiting];
  return query;
}
```

### 3. Server — `src/resolvers/query.ts`

`issues` gains nothing; it just calls `toIssueQuery`. The interesting part is that **`prs` loses code**: its hand-written `deadline` guard becomes unreachable, because `deadline` is no longer a field of `PrFilter` and the request is refused before a resolver runs.

```ts
issues: (_parent, args, ctx) =>
  run(() => ctx.sync.read(() => listEntities(ctx.ws, "issue", toIssueQuery(args.filter, today(ctx))))),

prs: (_parent, args, ctx) =>
  run(() =>
    ctx.sync.read((): PrParent[] => {
      const query = toPrQuery(args.filter, today(ctx));
      if (args.allRefs) { … }
      return listEntities(ctx.ws, "pr", query).map((entity) => ({ entity, refs: [] }));
    }),
  ),
```

Delete the `invalidInput("'deadline' describes an issue…")` throw and the now-unused import if nothing else uses it.

### 4. Codegen

```sh
pnpm --filter @navbook/server codegen
pnpm --filter @navbook/web codegen
```

Both outputs are committed and CI runs `codegen:check`, so this is not optional. The server's `resolver-types.ts` gains `IssueFilter`/`PrFilter` and drops `EntityFilter`; the web's `src/generated/gql/` regenerates from the same SDL.

### 5. Web client

Four files, and one of them is a live bug rather than a rename.

- **`app/graphql/queries.ts`** — `query Issues($filter: IssueFilter)` and `query Prs($filter: PrFilter, $allRefs: Boolean!)`. `INBOX_QUERY` needs no change: its filters are inline literals and already use the right keys per noun (`awaiting` only on `prs`).
- **`app/utils/filter-params.ts`** — `toEntityFilter` splits into `toIssueFilter` and `toPrFilter`, each emitting only its own keys.
- **`app/utils/filter-params.ts`, `queryToFilter`** — this is the live bug. `reviewers: queryValues(query.reviewer)` is parsed **ungated**, unlike `deadline`, which is gated by `keys.deadlines ?? []`. So `/issues?reviewer=alice@example.com` populates `filter.reviewers` today and `toEntityFilter` sends it on the `Issues` query. That request silently matches nothing now and becomes a hard validation error after this change. Gate it the way deadlines are gated:

  ```ts
  export interface FilterKeys {
    statuses: readonly Status[];
    deadlines?: readonly DeadlineState[];
    /** Whether this listing has reviewers at all; only a pull request does. */
    reviewers?: boolean;
  }
  …
  reviewers: keys.reviewers === true ? queryValues(query.reviewer) : [],
  ```

  and `pages/prs/index.vue` passes `reviewers: true` while `pages/issues/index.vue` does not.
- **`app/composables/useEntityFilter.ts`** — `variables: ComputedRef<EntityFilter>` cannot be one type any more. Take the projection as an argument rather than hard-coding it:

  ```ts
  export function useEntityFilter<T>(keys: FilterKeys, toVariables: (f: FilterState) => T): EntityFilterHandle<T>
  ```

  with the two pages passing `toIssueFilter` / `toPrFilter`. That keeps one composable and makes the noun explicit at the call site.

### 6. Tests

- **`packages/server/test/server/read.test.ts:346`** — the existing `prs`/`deadline` case still belongs, but now asserts a *validation* failure rather than `INVALID_INPUT`. Yoga reports an unknown input field as `GRAPHQL_VALIDATION_FAILED` with a message naming the field, so:

  ```ts
  it("refuses the deadline filter on pull requests, which are not scheduled", async () => {
    const response = await h.gql(`query { prs(filter: { deadline: [OVERDUE] }) { id } }`);
    assert.equal(errorCode(response), "GRAPHQL_VALIDATION_FAILED");
    assert.match(response.errors[0]?.message ?? "", /deadline/);
  });
  ```

- **the counterpart, beside it** — the same three assertions for `issues` with `reviewers`, `reviews` and `awaiting`. This is the regression test for the finding itself.
- **`packages/web/test/nuxt/filter-params.test.ts`** — four places touch `reviewers` (lines 66, 79, 161, 234) and will need the new `FilterKeys` flag; the round-trip cases for an issues listing should now assert that `?reviewer=` is *dropped*, which is the gating change above.

### 7. Order of work

1. Schema + codegen, both packages. Everything downstream is then a type error, which is the point.
2. Server resolvers and `map.ts` until `pnpm --filter @navbook/server typecheck` is clean.
3. Server tests.
4. Web: `filter-params.ts`, then `useEntityFilter`, then the two pages, then `queries.ts`.
5. `pnpm check` and the full suite.

### Risks

- **It is a breaking API change.** Any client outside this repository sending `filter: EntityFilter` breaks. `@navbook/web` is the only known one and is versioned in lockstep, so the blast radius is this repository — worth a line in the release notes all the same.
- **`?reviewer=` on an issues URL.** Anyone who has bookmarked one gets a hard error where they used to get an empty list. The gating change makes the parameter inert rather than fatal, which is the right migration; without it, this change turns a silent bug into a visible one for those users.

### Done when

`query { issues(filter: { reviews: [PENDING] }) { id } }` is refused by validation with no resolver involved; `nav issue list review:pending` and the API give the same answer; and `EntityFilter` appears nowhere in the repository.
