Prior art, for the record: this is a known API-design question and the settled answer is the one spec 04 already gives.

WPGraphQL argued it out in [wp-graphql#4338](https://github.com/wp-graphql/wp-graphql/issues/4338), in the same words this issue uses — silently narrowing "makes it difficult for clients to distinguish between 'you aren't allowed to ask for this' and 'nothing matched', making bugs hard to track down". Payload and Directus both reject a filter on a field the caller cannot read rather than emptying the result. The shape of the mistake is identical here; only the reason differs (the field does not exist on this noun, rather than the caller not being allowed to see it).

Two things specific to us make the silent version worse than usual:

1. **It is not "matches nothing", it is "matches everything".** The other systems' failure mode is an empty list, which at least looks like an answer somebody can question. `reviews: [PENDING]` returning every issue looks like a populated, correct result. A client building a "needs review" panel out of it would ship.
2. **We have a second front end that disagrees.** The CLI refuses the term at parse time. Anyone cross-checking the API against `nav issue list` — which spec 06 §6.3 explicitly invites, "a reader of the API and a reader of `nav --json` are looking at the same thing" — finds two different answers to one question.

The test gap is one case. `packages/server/test/server/read.test.ts:346` already asserts the `prs`/`deadline` refusal; the counterpart goes beside it:

```ts
it("refuses the review filters on issues, which have no reviews", async () => {
  for (const term of ['reviewers: ["a@b.com"]', "reviews: [PENDING]", 'awaiting: ["a@b.com"]']) {
    const response = await h.gql(`query { issues(filter: { ${term} }) { id } }`);
    assert.equal(errorCode(response), "INVALID_INPUT");
    assert.match(response.errors[0]?.message ?? "", /describes a pull request/);
  }
});
```

On the schema side there is a structural option worth weighing, though it is a breaking change: splitting `EntityFilter` into `IssueFilter` and `PrFilter` makes the whole class of mistake unrepresentable — GraphQL's own validator refuses an unknown input field, so no resolver code is needed and no future term can be forgotten. The cost is that the two inputs duplicate the seven shared keys, and `EntityFilter` is currently what lets one filter serve both nouns. The runtime guard is the smaller change; the split is the one that cannot regress.
