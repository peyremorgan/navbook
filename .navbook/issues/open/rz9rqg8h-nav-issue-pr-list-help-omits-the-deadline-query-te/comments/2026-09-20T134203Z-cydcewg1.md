## Implementation plan

Add the line, then remove the reason it was missing. One vocabulary is currently written down in four places and `deadline:` reached three of them; the structural half makes a fifth omission impossible.

### 1. The line itself — `packages/cli/src/program.ts`

```diff
   awaiting:EMAIL              asked to review it and has not yet; PRs only
+  deadline:overdue|none       overdue: due before today (UTC), strictly;
+                              none: no deadline at all. Issues only
   WORD or "some phrase"       case-insensitive substring of the title,
                               description, or any comment body
-Same-key terms OR for single-valued fields (status, author, milestone, review)
+Same-key terms OR for single-valued fields (status, author, milestone, review,
+deadline)
 and AND for multi-valued ones (label, assignee, feature, reviewer, awaiting).
```

`deadline` belongs in the **first** list: `matchesDeadline` uses `query.deadline.some(...)`, and the comment there gives the reason — "asking for both the overdue and the undated is a question with an answer, unlike two labels naming different things".

Land this on its own first. It is the user-visible fix and it should not wait behind a refactor.

### 2. The structural half — one table, three consumers

**Core owns the grammar, the CLI owns the words.** Putting English help text in `core/` would be wrong — spec 05 §5.2 scopes it to "pure functions: parse/serialize/validate/query/plan" and the wording is presentation. So core exports the shape and the CLI supplies the prose, with a test holding them together.

`packages/core/src/core/query.ts`:

```ts
/** One term of the query grammar of spec 04 §4.3. */
export interface QueryTerm {
  key: string;
  /** The noun it describes, when only one has it; both when absent. */
  only?: EntityKind;
  /**
   * How several terms of this key combine.
   *
   * Single-valued fields OR — requiring two different statuses at once could
   * never match — and multi-valued ones AND, which is forge convention.
   */
  combines: "and" | "or";
}

export const QUERY_TERMS: readonly QueryTerm[] = [
  { key: "status", combines: "or" },
  { key: "label", combines: "and" },
  { key: "assignee", combines: "and" },
  { key: "author", combines: "or" },
  { key: "milestone", combines: "or" },
  { key: "feature", combines: "and" },
  { key: "reviewer", only: "pr", combines: "and" },
  { key: "review", only: "pr", combines: "or" },
  { key: "awaiting", only: "pr", combines: "and" },
  { key: "deadline", only: "issue", combines: "or" },
];
```

and the three things that are currently written by hand become derivations:

```ts
const KEYED_TERM = new RegExp(`^(${QUERY_TERMS.map((t) => t.key).join("|")}):(.*)$`);
const PR_ONLY_TERMS = QUERY_TERMS.filter((t) => t.only === "pr").map((t) => t.key);
const ISSUE_ONLY_TERMS = QUERY_TERMS.filter((t) => t.only === "issue").map((t) => t.key);
```

Every key is `[a-z]+`, so the regex needs no escaping — worth a comment saying so, since that is a property of the table rather than of the code.

### 3. The CLI renders the help from it — `packages/cli/src/program.ts`

```ts
/** What each term means, in the words `--help` uses. Keyed by `QUERY_TERMS`. */
const TERM_HINTS: Record<string, { syntax: string; hint: string }> = {
  status: { syntax: "status:open|closed|merged", hint: "entity status (path); 'merged' is PR-only" },
  label: { syntax: "label:L", hint: "L is among the entity's labels" },
  …
  deadline: { syntax: "deadline:overdue|none", hint: "overdue: due before today (UTC), strictly; none: no deadline at all" },
};

function queryHelp(): string {
  const rows = QUERY_TERMS.map((term) => {
    const { syntax, hint } = TERM_HINTS[term.key] ?? { syntax: `${term.key}:VALUE`, hint: "" };
    const only = term.only === undefined ? "" : term.only === "pr" ? "; PRs only" : "; issues only";
    return `  ${syntax.padEnd(27)} ${hint}${only}`;
  });
  const ors = QUERY_TERMS.filter((t) => t.combines === "or").map((t) => t.key).join(", ");
  const ands = QUERY_TERMS.filter((t) => t.combines === "and").map((t) => t.key).join(", ");
  return [
    "Query terms AND together. Terms:",
    ...rows,
    `  ${"WORD or \"some phrase\"".padEnd(27)} case-insensitive substring of the title,`,
    `  ${"".padEnd(27)} description, or any comment body`,
    `Same-key terms OR for single-valued fields (${ors})`,
    `and AND for multi-valued ones (${ands}).`,
    "The default query is status:open.",
  ].join("\n");
}
```

The `; PRs only` / `; issues only` suffix now comes from the same field the *parser* uses to refuse the term, so the help cannot claim one thing while `parseQuery` does another.

Three hand-kept lists become one call. This is the file that already had `deadline:` correctly, which is a good sign the derivation matches reality.

### 5. Spec 04 §4.3's table stays hand-written

It is the normative document and should be prose a person wrote, not generated output. What keeps it honest is a test rather than a build step — see below.

### 6. Tests

`packages/cli/test/cli/help.test.ts`, deriving from the table rather than repeating it:

```ts
it("documents every term the parser accepts", () => {
  const help = repo.nav(["issue", "list", "--help"]).stdout;
  for (const term of QUERY_TERMS) {
    if (term.only === "pr") continue;
    assert.match(help, new RegExp(`\\b${term.key}:`), `'${term.key}:' is missing from the help`);
  }
});

it("offers every term it documents, and no others", () => {
  const offered = repo.nav(["__complete", "issue", "list"]).stdout.split("\n");
  for (const term of QUERY_TERMS.filter((t) => t.only !== "pr")) {
    assert.ok(offered.includes(`${term.key}:`), `'${term.key}:' is not offered`);
  }
  assert.ok(!offered.includes("reviewer:"), "a PR-only term is offered on issues");
});
```

and the mirror for `nav pr list`. These are the tests that would have caught this issue, and they catch the next term too.

One more worth adding in `packages/core/test/query.test.ts`: every key in `QUERY_TERMS` is accepted by `parseQuery` for the noun that has it and refused for the noun that does not — which pins the table against the parser rather than against a list somebody typed.

### 7. Order of work

1. The help line and the closing paragraph. Commit; that closes the issue as reported.
2. `QUERY_TERMS` in core; derive the regex and the two `only` lists; `pnpm --filter @navbook/core test`.
3. `program.ts` renders from it; `complete.ts` derives from it.
4. The three tests.

### Risks

- **The help text's exact bytes change** once it is generated — column alignment in particular. `help.test.ts` asserts the shape of the help surface, so check whether any assertion is byte-exact rather than a `match`.
- **A generated help block can read worse than a written one.** If the rendering comes out stilted, the right answer is to keep `QUERY_HELP` hand-written and keep only the *test* that every term appears in it. That gets most of the guarantee for none of the machinery, and is a reasonable place to stop if step 3 turns out ugly.

### Done when

`nav issue list --help` documents `deadline:`, `nav pr list --help` does not, neither offers a term its parser would refuse, and adding a term to `QUERY_TERMS` without documenting it fails the suite.
