The line is worth adding, but the reason it was missed is the more interesting half.

One vocabulary is currently written down in four places:

| Where | What it holds |
|---|---|
| `core/src/core/query.ts` | `KEYED_TERM`, `PR_ONLY_TERMS`, `ISSUE_ONLY_TERMS` — what the parser accepts |
| `cli/src/program.ts` | `QUERY_HELP` — what `--help` prints |
| `cli/src/commands/complete.ts` | `QUERY_KEYS`, `PR_QUERY_KEYS`, `ISSUE_QUERY_KEYS` — what the shell offers |
| `doc/spec/04-cli.md` | the normative table |

`deadline:` was added to three of them. Four copies is how the fifth one gets forgotten, and it will be forgotten again the next time a term is added — the next candidate being whatever the plugin work contributes to a listing.

Building `QUERY_HELP` from the same constants the parser and the completion use would make this class of drift impossible, and it is a small change: the descriptions are the only part that has to be written by hand, so a single table of `{ term, hint, appliesTo }` in `core` could feed all three consumers. `complete.ts` would then stop carrying its own copy as well, which is the second bug this prevents rather than the same one twice.

A test is the cheaper version of the same guarantee, and `packages/cli/test/cli/help.test.ts` is the place for it:

```ts
it("documents every term the parser accepts", () => {
  const help = repo.nav(["issue", "list", "--help"]).stdout;
  for (const term of ["status:", "label:", "assignee:", "author:", "milestone:",
                      "feature:", "deadline:"]) {
    assert.match(help, new RegExp(term.replace(":", ":")), `'${term}' is missing from QUERY_HELP`);
  }
});
```

Deriving that list from `KEYED_TERM`'s source rather than repeating it would make the test itself drift-proof, which is the version worth writing.

One small correctness note for whoever writes the help line: `deadline`'s terms **OR**, unlike `label`/`assignee`/`feature` which AND — `matchesDeadline` uses `query.deadline.some(...)`, and the comment there explains why ("asking for both the overdue and the undated is a question with an answer, unlike two labels naming different things"). So `deadline` belongs in the first list of the closing paragraph, beside `status`, not the second.
