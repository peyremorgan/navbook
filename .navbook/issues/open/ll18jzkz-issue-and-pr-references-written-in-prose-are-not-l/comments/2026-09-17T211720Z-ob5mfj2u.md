Confirmed, and two things turned up while confirming that change what the fix
has to look like.

**The server already names the kind.** The worry in the description was that
resolving an id costs two requests, since nothing in the text says whether it
names an issue or a pull request. It does not: `issue(ref:)` on a pull
request's id answers `WRONG_KIND` — `#bbbb0001 is a pull request` — rather than
refusing outright (`packages/core/src/workspace/resolve.ts`, `wrong-kind`). So
the common case is one question. The second one is only needed for `NOT_FOUND`,
which is the pull request living on a branch the server has fetched but is not
standing on: `pr(ref:)` scans branches, `issue(ref:)` does not.

That settles the choice in favour of a resolver route over a new
`reference(ref:)` query on the server. The schema does not need to grow a field
to answer something it already answers.

**An id must contain a digit**, and leaving that out is not a detail. Spec 02
§2.2 requires it and says why: "the mandatory digit keeps English words from
being mistaken for IDs". `PROSE_REF` in `packages/core/src/core/refs.ts` only
describes the shape; `extractProseRefs` filters it through `isId`, which is
where the digit is checked. A client matching the regex alone would linkify
`#deadline`, `#reverted` and `#manifest` — every eight-letter hashtag anybody
writes — into links to nothing. I had exactly that bug before checking the two
readings against each other, which is now a unit test rather than a habit.
