Investigated and reproduced. Not a duplicate of #t4mwvm2j, though that issue is probably how the reviewer got here.

## Correction to the report

`nav` does not write onto the pull request's source branch. It writes into the checked-out tree and, with `--commit`, runs `git commit` on whatever HEAD is. Nothing in core, the CLI or the server moves HEAD or updates a ref. The only `checkout` is the path-limited `git checkout <ref> -- <path>` that `nav pr close` uses to copy a directory in. Git's refusal to update a branch checked out elsewhere happened before `nav` ran, not inside it.

## Most likely sequence

1. From the reviewer's checkout, `nav pr review <id>` said `no pull request matches`, because the pull request is only on `feat/pdf-extra` (#t4mwvm2j).
2. `git switch feat/pdf-extra` was refused: `'feat/pdf-extra' is already used by worktree at …`.
3. The reviewer detached instead (`git switch --detach feat/pdf-extra` or equivalent), which put the pull request in the tree.
4. `nav pr review <id> --commit` committed onto the detached HEAD, reported `Committed docs(pr): review #<id>`, and exited 0.

## Reproduction

A repository with `feat/pdf-extra` carrying an open pull request and checked out in a second worktree. From the main checkout, `git switch --detach feat/pdf-extra`, then `nav pr review <id> --comment -m … --commit`. The result is the same with 0.2.0 and with the current source, including the uncommitted fix for #t4mwvm2j:

- the review commit is contained in no branch (`git branch -a --contains HEAD` lists only the detached HEAD);
- the author's worktree still has `docs(pr): open` at its tip;
- nothing on stdout or stderr mentions that HEAD was detached.

## The gap

`nav pr open` and `nav pr merge` already refuse a detached HEAD. The `--commit` path every other verb goes through (`runPlan` in `core/workspace/commit-flow.ts`) does not check. So every committing verb has this hole, issues included. Pull requests are where it bites, because detaching is the obvious way to reach files on a branch that another worktree holds.

The #t4mwvm2j fix removes the reason to detach, since the refusal now names the worktree that has the branch. It does not catch this case: once HEAD is detached at the source branch, the pull request is in the tree and nothing refuses.

## Suggested fix

- `--commit` refuses on a detached HEAD, checked once in `runPlan` next to `assertNoUnrelatedStaged` and before any file is written, as `open` and `merge` already do.
- When HEAD sits at the tip of a branch checked out in another worktree, the refusal names it: `HEAD is detached at 'feat/pdf-extra', which is checked out in <path>; run the command there`.
- Without `--commit`, writing and staging on a detached HEAD can stay allowed: nothing is lost until someone commits, and that commit is theirs to place.

Open question: refuse or warn. Refusing is consistent with `open` and `merge`. A warning would still let an unreachable commit be made, and the report shows how much work recovering one takes.
