The rule is documented and the behaviour is demonstrable in one line, so there is no ambiguity about the cause.

`bash(1)`, on `-e`:

> Exit immediately if a pipeline (which may consist of a single simple command), a list, or a compound command exits with a non-zero status. **The shell does not exit if the command that fails is part of the command list immediately following a `while` or `until` reserved word, part of the test following the `if` or `elif` reserved words, part of any command executed in a `&&` or `||` list except the command following the final `&&` or `||`, any command in a pipeline but the last** (subject to the state of the `pipefail` shell option), **or if the command's return value is being inverted with `!`.**

The same rule is in POSIX's `set` special built-in, so this is not a bash-ism — the hook has `#!/bin/sh` and the behaviour is identical there:

```console
$ /bin/sh -c 'set -e; f() { return 1; }; if f; then echo cond-true; else echo "cond-false (shell survived)"; fi; f; echo "NOT REACHED"'
cond-false (shell survived)
$ echo $?
1
```

The failing command inside the `if` condition is survivable; the same command standing alone ends the shell. That is exactly the difference between where `nav doctor --staged` sits today and where it needs to sit.

Two notes on the fix:

- **Careful with `[ "$status" -eq 2 ] && exit 1` as the last command of the block.** When the test is false, the `&&` list's status is 1, and that becomes the hook's exit status if nothing follows it — which would block every commit instead of none. The full `if` avoids that; so does a trailing `exit 0`, but only if the navbook block is genuinely last, which it cannot assume since the installer appends and a later tool may append after it.
- **`set -e` in hooks is not an exotic thing to run into.** It is the first line of most hand-written hooks, and the frameworks people layer on top — husky in particular, which writes a shell wrapper — encourage it. Anyone who has a hook at all before running `nav install --hooks` is a plausible reporter of this.

There is a wider point worth recording while the file is open: `command -v nav` means the check is silently skipped whenever `nav` is not on `PATH`, which is the normal state inside GUI git clients and some IDE integrations that do not source a login shell. That is deliberate — "a clone without nav installed is unaffected" — but it does mean the hook's protection is absent exactly where people are least likely to notice. Not a defect, and not this issue; worth a line in the block's comment.
