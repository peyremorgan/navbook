**Acceptance cases**
- [ ] `nav plugin list` in a repository that declares `@navbook/plugin-x` with an empty store lists it as "declared, not installed" and prints the store path.
- [ ] `nav plugin install` with no answer on stdin prints the exact `npm install --ignore-scripts …` command, asks `[y/N]`, and on EOF or "n" changes nothing and exits non-zero.
- [ ] `nav plugin install lodash -y` is refused (wrong name prefix, no `navbook-plugin` keyword) and the store is unchanged.
- [ ] `nav plugin install kb` expands the name to `@navbook/plugin-kb`, then tries `navbook-plugin-kb`. `list` shows the full name.
- [ ] `nav plugin remove X` leaves `navbook.json` byte-for-byte unchanged.
- [ ] No command ever runs npm just because of a name in `navbook.json`. Test: a marker declaring a package, with `PATH` pointing to a fake `npm` that records calls; `issue list`, `doctor` and `--help` make zero calls.
- [ ] With `NAVBOOK_PLUGIN_PATH=<dir>` pointing to a fixture plugin whose `./cli` entry throws on import: `nav --help` lists its noun, `nav __complete` offers it, and `nav issue list` succeeds. The plugin is imported only when its own command runs.
- [ ] A plugin that declares the noun `issue`, or a noun an earlier plugin already took, is skipped with a message naming the plugin. Built-in commands are unaffected.
- [ ] A plugin with an incompatible `engines.navbook` is skipped with a one-line reason. Other commands still work.
- [ ] Performance budget (05 §5.2): a cold `nav issue list` on a 1,000-issue repo with 5 fixture plugins installed stays under 500 ms, and within noise of the same run with no plugins.
- [ ] `--commit` and the staged-changes guard apply to a plugin mutation that returns a `Plan` passed through `runPlan`.
