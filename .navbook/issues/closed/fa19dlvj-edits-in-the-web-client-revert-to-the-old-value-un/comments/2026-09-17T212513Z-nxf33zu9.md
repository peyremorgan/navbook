Confirmed against the built bundle and a real stack (`test-e2e/helpers/stack.ts`: fixture repo with an origin, dev issuer, `nav-server`), driven by Playwright with the GraphQL endpoint intercepted through `page.route`.

## Repro

1. Open `/issues/aaaa0001`, click the pencil beside **Assignees**, pick `second@example.com`, click **Save**.
2. Hold the `UpdateIssue` response for 4 s (or use a deployed tracker, where fetch + commit + push takes that long on its own).
3. Watch the sidebar.

What the sidebar section showed, sampled after the Save click (`text` is the section's inner text; `spinners` counts `.animate-spin` / `aria-busy` inside it):

```
unmocked save (local origin): chips updated after 494 ms

t+93 ms    text: 'ASSIGNEES A Person <person@example.invalid> first@example.com'  spinners: 0  saveButton: 0
t+802 ms   (same)
t+1516 ms  (same)
t+2228 ms  (same)
t+2941 ms  (same)
t+3652 ms  (same)
t+4460 ms  text: '... first@example.com second@example.com'   ← only now
```

The one spinner on the whole page during those 4 s was on `comment-submit`: the issue page hands `mutations.busy` to every control, so the write's only visible sign is on a button that has nothing to do with it.

4. Then answer `UpdateIssue` with a GraphQL error (`SYNC_PUSH_REJECTED`, which is what a rejected push produces) after adding `third@example.com`:

```
after failure:  text: '... first@example.com second@example.com'   (reverted)
retry buttons on page: 0
editor reopened; what it holds: "A Person <person@example.invalid>, first@example.com, second@example.com"
third@example.com still in the draft? false
```

A toast says "The remote refused the push — origin rejected refs/heads/main" for 8 s and that is all: the address that was typed is gone.

## Where it comes from

- `app/components/LabelEditor.vue` — `save()` emits the draft and sets `editing = false` in the same tick. The read-only branch renders `props.values`, which is the cached entity, so nothing on screen changes until the mutation's payload is written to the cache. The Save button carries `:loading="props.saving"` but is unmounted before `saving` becomes true.
- `app/components/EditableText.vue` and `app/components/FieldEditor.vue` — same two lines, same effect, for title, description, rank and deadline (and feature title/summary).
- `app/composables/useIssueMutations.ts` `updateIssue` — swallows every failure but `STALE_CONTENT` and returns `null`; the caller in `pages/issues/[ref].vue` `save()` has nothing left to offer because the draft went with the editor. `pages/prs/[ref].vue` `save()` does the same with its own `useMutation`.
- `app/plugins/03.apollo.ts` — the error link's toast is the only report, and a toast has no Retry.
- `app/composables/useStaleEdit.ts` + `StaleEditAlert.vue` already do the right thing for one failure code: keep the edit, show it, offer "Save mine over it" / "Leave theirs". That is the shape the generic failure needs too.

## Audit of every write in the client

| Write | Where | Shown at once? | In-flight indicator | On failure |
|---|---|---|---|---|
| Labels, assignees, features, milestone (`LabelEditor`) | issue page, PR page | **No**, old chips until response | **none** in the section | toast; draft lost; no retry |
| Reviewers (`LabelEditor` with display slot) | PR page | **No** | **none** | toast; draft lost |
| Title, description (`EditableText`) | issue page, PR page | **No** | **none** | toast; draft lost, except `STALE_CONTENT` (kept by `useStaleEdit`) |
| Feature title, summary (`EditableText`) | feature page | **No** | **none** | toast; draft lost, stale is a toast + refetch |
| Rank, deadline (`FieldEditor`) | issue page | **No** | **none** | toast; draft lost |
| Spec document (`SpecEditor`) | spec page | editor stays open until `baseSha` moves | Save button spinner, at once | draft kept in editor; stale shown inline. Fine. |
| Comment, review (`CommentForm`, `ReviewForm`) | both detail pages | comment appears only on response | submit button spinner, at once | draft kept; toast. Acceptable, retry is clicking again |
| Close issue (modal) | issue page | n/a | button spinner | `confirmClose` sets `closing = false` after the await whatever happened, so the modal closes and the typed resolution is lost |
| Reopen, link subtask, reparent | issue page | n/a | button spinner (shared `busy`) | toast; dialog stays. Fine. |
| Unlink subtask (`SubtaskTree`) | issue page | **No**, row stays until refetch | **none**, the unlink button has no loading state | toast |
| Reorder by drag or keyboard (`useInboxReorder`) | inbox | yes, preview held while in flight | none visible; `sr-only` announcement; handles inert | row springs back; announcement only; no retry |
| New issue, new feature, add document | forms and modals | n/a, navigates on success | button spinner, at once | form stays. Fine. |

So the bug is a family: the three in-place editors (`LabelEditor`, `EditableText`, `FieldEditor`) on four pages, plus the close modal, unlink and the inbox reorder to a lesser degree. Comment, review and spec saves already keep the draft and show a spinner because their editor stays open.

## Fix shape

One composable that owns a pending edit per field: the page shows the pending value over the cached one until the response, a `saving` flag that becomes visible only after a delay of 1750 ms, and a kept failure per field with the server's message, Retry and Discard. `useStaleEdit` is nearly that already for one error code; generalising it to every failure and handing the pending value back to the editors covers the whole table above.
