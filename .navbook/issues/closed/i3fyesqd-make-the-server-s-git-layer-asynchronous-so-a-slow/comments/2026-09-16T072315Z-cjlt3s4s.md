Confirmed. The whole process wedges for as long as a push takes, and nothing that is not a git command escapes it: not the GraphiQL page, not a 401 for a request with no token.

## Repro

A bare origin whose `pre-receive` hook sleeps stands in for the slow remote. Start a server on a clone of it, fire one mutation, and 400 ms later (once it is past fetch and commit, into the push) send three unrelated requests at once:

```sh
# hooks/pre-receive on the bare origin
#!/bin/sh
sleep 3
exit 0
```

```
baseline, nothing in flight:
GET /graphql (GraphiQL page)       HTTP 200  30 ms
POST without a token               HTTP 401  21 ms

while a mutation is pushing to an origin whose pre-receive sleeps 3s:
GET /graphql (GraphiQL page)       HTTP 200  2798 ms
POST without a token               HTTP 401  2801 ms
authenticated read (issues)        HTTP 200  2860 ms
mutation finished after 3266 ms
```

Every probe is answered at the moment the push returns, and not a millisecond before. The unauthenticated POST is the telling one: it never reaches a resolver, never touches the lock, and still waits 2.8 s, because the event loop itself is parked inside `spawnSync`. The GraphiQL page is static HTML and waits just the same. The script is `test/helpers/harness.ts` plus the hook; it takes nothing but a bare repo.

## Where it is

- `packages/core/src/git/exec.ts` — `gitRun` is `spawnSync("git", …)`, and every git function in core goes through it or `git`/`gitMaybe` on top of it.
- `packages/core/src/git/remote.ts` — `fetchRemote` and `pushBranch` are the two that reach the network, and the only ones whose duration is not bounded by the local disk.
- `packages/server/src/sync.ts` — `RepoSync.read`/`write`/`locked` run their body inside `Mutex.run`, and `pull`, `merge` and `pushWithRetry` call `SyncGit` synchronously from within it. `SyncGit` is the injection seam the issue names.
- `packages/server/src/lock.ts` — the `Mutex` whose header comment already describes this ticket.
- `packages/server/README.md` documents the limit in so many words ("git runs synchronously, so a slow fetch or push blocks concurrent requests"), and `test/server/concurrency.test.ts` says in its header that the lock's guarantee is currently free and those tests are what would notice when it stops being.

## Two things the repro adds to the ticket

1. **There is no timeout of any kind today.** Nothing in `gitRun` passes `timeout` to `spawnSync`, and the server sets only `GIT_TERMINAL_PROMPT=0`. A push to a remote that accepts the TCP connection and never answers holds the process until git's own transport gives up, which for HTTPS can be never. So the fourth point of the ticket (a `--git-timeout-ms` that kills the child and reports `SYNC_FAILED`) is not an extra: without it, going async only moves the hang from "the process" to "the lock", and every read and write still queues behind it forever while health probes cheerfully report the server alive.
2. **Fetch is on the read path.** With `--pull-interval-ms 0` (what the sync tests use) every read fetches, so a slow remote is felt on reads too, not only on writes. With the default 10 s window it is once per window per read, plus every mutation.

## Shape of the fix, as I read the code

`SyncGit` is already an interface with eleven methods; making each return a promise, `RepoSync.pull`/`merge`/`pushWithRetry` `async`, and `Mutex.run` unchanged is the whole server side. The bodies passed to `read`/`write`/`locked` stay synchronous, which is what the ticket asks for. In core, a `gitRunAsync` beside `gitRun` (same env, same `ENOENT` message, plus an optional `timeoutMs` that sends `SIGKILL` and reports the kill as a distinct error) and async twins of the eleven functions. The unit matrix in `test/unit/sync.test.ts` carries over with `async` fakes. What is worth adding is the ordering test the concurrency suite says it is waiting for: a fake whose push is a promise that resolves later, with a read queued behind it, asserting the read runs after the push completes and not interleaved.
