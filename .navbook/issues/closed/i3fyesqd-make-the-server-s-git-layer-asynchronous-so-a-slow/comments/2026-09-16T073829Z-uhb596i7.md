Fixed on `feat/async-git-layer`, which this close travels with. The ticket asked to close on a number, so here is the same repro as above run against the branch's server — an origin whose `pre-receive` sleeps 3 s, one mutation pushing, three requests fired together 400 ms in:

| request | before | after |
|---|---|---|
| GET /graphql (GraphiQL page) | 2798 ms | 5 ms |
| POST with no token (401) | 2801 ms | 7 ms |
| authenticated `{ issues }` | 2860 ms | 2870 ms |

The last row is the design: a read takes the lock and runs on the tree the mutation left, and it now sees the issue the mutation filed. The other two never touch the clone and no longer wait for it.

What landed, against the four points of the ticket:

1. `gitRunAsync` / `gitAsync` / `gitMaybeAsync` beside the blocking runner in `packages/core/src/git/exec.ts`, and `…Async` twins of the eleven operations, sharing their arguments and their reading of git's output with the blocking forms.
2. `SyncGit` is promise-returning; `pull`, `merge` and `pushWithRetry` are `async`; `Mutex.run` is untouched and the unit matrix runs on async fakes, plus a test of a read queued behind a push still in flight.
3. Operation bodies stay synchronous.
4. `--git-timeout-ms` / `NAV_SERVER_GIT_TIMEOUT_MS`, default 30 s, 0 for none. A stopped call fails its own request with `SYNC_FAILED`; a stopped push says `keptLocalCommit: true`, and the next push carries the commit. `SIGTERM` first so git removes its lock files, `SIGKILL` 2 s later if needed.

And the edge the ticket flagged: `drain()` is exercised against a push that has not returned, in the unit suite and by a `SIGTERM` mid-push in `test/server/responsiveness.test.ts`.
