Confirmed on `dev` at e163c39, against the live provider (2026-09-16) and against oidc-client-ts 3.5.0, the version the web client resolves.

```console
$ curl -sS -o /dev/null -w '%{http_code}\n' https://auth.brickcode.tech/.well-known/openid-configuration
200
$ curl -sS https://auth.brickcode.tech/.well-known/openid-configuration | jq -r .issuer,.jwks_uri
https://auth.brickcode.tech/api/auth
https://auth.brickcode.tech/api/auth/jwks
$ curl -sS -o /dev/null -w '%{http_code}\n' https://auth.brickcode.tech/api/auth/.well-known/openid-configuration
404
```

The client's `UserManager` is built with `authority: config.oidc.issuer` and nothing else about discovery (`app/plugins/02.auth.ts`), and oidc-client-ts derives the document's address from it. Driving the library's own `OidcClient` from Node, with the settings the plugin uses, shows the failure and the way out:

```console
== as today: authority = oidc.issuer
   metadataUrl resolved to: https://auth.brickcode.tech/api/auth/.well-known/openid-configuration
   FAIL Not Found (404)

== with metadataUrl
   metadataUrl resolved to: https://auth.brickcode.tech/.well-known/openid-configuration
   OK  issuer=https://auth.brickcode.tech/api/auth
       authorization_endpoint=https://auth.brickcode.tech/api/auth/oauth2/authorize
```

The `metadataUrl` setting is honoured as-is; `authority` is only appended with `/.well-known/openid-configuration` when `metadataUrl` is absent (`OidcClientSettingsStore` constructor).

## Two things worth knowing for the fix

- **The client never checks the ID token's `iss` against `authority`.** `_validateIdTokenAttributes` in oidc-client-ts checks `sub`, `nonce`, `auth_time` and `azp`, and nothing else; `authority` is otherwise only the key of the session-storage entry and a value compared with the one stored in the sign-in state. So the "issuer" the client is told is, in practice, nothing but the base of the discovery URL. The `iss` check that matters is the server's: `verifyToken` in `packages/server/src/auth.ts` passes `issuer` to `jwtVerify`, and `discoverJwksUrl` builds `<issuer>/.well-known/openid-configuration` exactly as the client does, so the server hits the same 404 unless `--oidc-jwks-url` is given.
- **The workaround that follows from that is blocked by `compose.yaml`.** Outside Compose the pair works today: client `issuer: https://auth.brickcode.tech` (discovery at the host root), server `--oidc-issuer https://auth.brickcode.tech/api/auth --oidc-jwks-url https://auth.brickcode.tech/api/auth/jwks`. Inside Compose one `NAVBOOK_OIDC_ISSUER` feeds both `NAV_SERVER_OIDC_ISSUER` (line 31) and the client's `NAVBOOK_OIDC_ISSUER` (line 68), so the two cannot be told different things without editing the file. Which is a reason to keep the two halves' keys in step in whatever the fix adds.

## Where it lands

- `app/utils/config.ts`: `OidcConfig` and `parseConfig`, which is where a present-but-empty value has to be refused by name; `test/nuxt/config.test.ts` covers the shape.
- `app/plugins/02.auth.ts`: pass `metadataUrl` alongside `authority`.
- `docker/config.sh` only knows `required()`; an optional key needs a second helper that emits the line or nothing, and the heredoc has to stay valid JSON either way.
- `compose.yaml`, `.env.example`, and the identity-provider section of `packages/web/README.md`.
- `test-e2e/helpers/stack.ts` and `script/dev-issuer.ts`: the development issuer serves its document under its issuer, so nothing there exercises the new key unless the issuer learns to serve it elsewhere.
