## Confirmed on `dev` (`22f6be6`), git 2.55.0

Reproduced with the two real functions rather than by reading: one script imports `blobSha` from `packages/core/src/core/hash.ts` (what `Issue.baseSha`/`Pr.baseSha` serve) and `hashObject` from `packages/core/src/git/index-ops.ts` (what `Feature.baseSha`/`Spec.baseSha` serve and `ops/feature.ts` checks), and hashes one committed file both ways in four throwaway repositories.

```js
// hash.mjs <repo> <file>
const text = readFileSync(`${repo}/${file}`, "utf8");
console.log("core blobSha (entity side):  ", blobSha(text));
console.log("git hashObject (feature side):", hashObject(repo, `${repo}/${file}`));
console.log("blob git stored at HEAD:      ", git("rev-parse", `HEAD:${file}`));
```

| Repository | `blobSha` (entities) | `hashObject` (features) | blob at `HEAD` |
|---|---|---|---|
| default | `04c18dcc…` | `04c18dcc…` | `04c18dcc…` |
| `core.autocrlf=true`, CRLF on disk | **`7c102c4d…`** | `04c18dcc…` | `04c18dcc…` |
| `*.md filter=up` (clean = `tr a-z A-Z`) | **`04c18dcc…`** | `33c7beea…` | `33c7beea…` |
| `git init --object-format=sha256` | **`04c18dcc…`** (40 hex) | `10eeb00a…d77113` (64 hex) | `10eeb00a…d77113` |

The file is `title: x\nbody\n` in every case (CRLF on disk in the second). So the same bytes get one "blob hash" from the entity half and another from the feature half as soon as the repository has anything other than the default configuration. The SHA-256 row also shows the shape split the issue predicts: one `String!` field, 40 characters on two types and 64 on the other two.

To rerun it by hand:

```sh
git init -q r && cd r && git config core.autocrlf true
printf 'title: x\r\nbody\r\n' > a.md && git add a.md && git commit -qm a
node --input-type=module -e '
  import { readFileSync } from "node:fs";
  import { blobSha } from "<navbook>/packages/core/src/core/hash.ts";
  import { hashObject } from "<navbook>/packages/core/src/git/index-ops.ts";
  console.log(blobSha(readFileSync("a.md", "utf8")), hashObject(process.cwd(), process.cwd() + "/a.md"));'
```

(`hashObject` wants an absolute path, or a path relative to `cwd`. A path relative to the caller's directory reads as unreadable and returns `null`, which the feature op then treats as "changed". That is the right failure direction, and the current callers all pass `absPath`.)

## One consequence the write-up understates

The "Why this is low" section says the one place the two worlds touch fails safe. It does, but under `core.autocrlf=true` it fails *every time there is a concurrent edit*, not only in SHA-256 repositories. `assertFieldsUnmoved` (`packages/server/src/resolvers/mutation.ts:593-617`) resolves an unmatched `baseSha` with `blobContent(repoRoot, baseSha)`. With a CRLF checkout, that `baseSha` is `blobSha` of the CRLF text on disk (`7c102c4d…` above), which is not an object in the store (the store holds the LF blob `04c18dcc…`). So `base === null` and the edit is refused as "read from a version this server does not have", even when the concurrent change touched a different field. The field-level merge silently degrades to whole-file optimistic locking. Nothing is lost, but it is the case the recovery path exists for. The server's own clone never has this configuration, while a CLI checkout can.

## Where the code stands

The implementation plan above still matches `dev` line for line:

- `packages/core/src/core/tree.ts:93` has `EntityRecord.blobSha`, set at `:519` from `files.get(draft.entityFile)`. `SpecRecord` (`:111`) and `FeatureRecord` (`:130`) carry no hash, and `materializeFeature` (`:418`) already holds the text it would hash.
- `packages/core/src/ops/feature.ts:281-295` is the only core caller of `hashObject`. `editFeature` (`:250`) and `editSpec` (`:267`) call it just after `findFeature`, so the record they hold was loaded in the same transaction and is current.
- `packages/server/src/resolvers/feature.ts:19-63` is the `HASHES` `WeakMap` plus `hashesOf`/`hashOf`: the only server caller of `hashObjects`, and the only subprocess in the `Feature`/`Spec` projections besides `commits`.
- No other production code calls `hashObjects`/`hashObject`, so after the move they are left with test callers only (point 7 of the plan).

Going ahead with the plan as written: unify on `blobSha`, and describe `baseSha` as an opaque version token.
