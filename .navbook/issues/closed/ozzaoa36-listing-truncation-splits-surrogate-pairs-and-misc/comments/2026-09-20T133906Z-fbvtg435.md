## Implementation plan

Both halves, with `string-width` as the measure. That makes the widths exact rather than approximate, at the cost of the CLI's first non-trivial runtime dependency — which is a decision worth recording in the spec, not just in `package.json` (step 5).

### 1. The dependency — `packages/cli/package.json`

```diff
   "dependencies": {
     "@navbook/core": "workspace:*",
     "commander": "^14.0.2",
-    "picocolors": "^1.1.1"
+    "picocolors": "^1.1.1",
+    "string-width": "^8.2.2"
   }
```

`string-width@8.2.2` is ESM, `engines: node >= 20`, MIT, and brings two transitive dependencies: `strip-ansi@^7.1.2` and `get-east-asian-width@^1.5.0` — the latter being the generated UAX #11 table, which is the part we actually want and the part nobody should hand-roll. Three packages in total.

It goes in `@navbook/cli`, never `@navbook/core`. Spec 05 §5.2's rule — "Every dependency added to the core is a liability for the Rust rewrite … and MUST be justified" — binds core, and `render/` is presentation that the Rust CLI will write against `unicode-width` (the same UAX #11 data) rather than port from here.

### 2. Measuring — `packages/cli/src/render/table.ts`

```ts
import stringWidth from "string-width";

/**
 * How many terminal columns a cell occupies.
 *
 * Not code points: UAX #11 gives East Asian Wide and Fullwidth characters two
 * columns and combining marks none, so a Japanese title counted by code point
 * is padded to half the space it takes and every column after it shifts.
 * `string-width` carries the generated table; `ambiguousIsNarrow` is its
 * default and the right reading for a modern terminal.
 */
function displayWidth(text: string): number {
  return stringWidth(text);
}
```

That one change fixes `pad` as well, since both read `displayWidth` — which is why the two halves cannot be landed separately even though they are separate faults.

### 3. Cutting — the other half, and `string-width` does not do it

`string-width` measures; it has no "take the first N columns". The cut has to walk grapheme clusters and accumulate:

```ts
const GRAPHEMES = new Intl.Segmenter("en", { granularity: "grapheme" });

/**
 * Truncate to `width` columns, marking the cut with a single ellipsis.
 *
 * By grapheme cluster, not by code unit: `slice` cuts between the halves of a
 * surrogate pair and produces a lone surrogate, which is not valid UTF-8 — and
 * it takes a ZWJ sequence apart into the people it is made of. By column, not
 * by count, for the reason `displayWidth` is: the ellipsis has to leave room
 * for itself, and a wide character needs two.
 */
export function truncate(text: string, width: number): string {
  if (width <= 0) return "";
  if (displayWidth(text) <= width) return text;
  if (width === 1) return "~";

  const budget = width - 1; // the ellipsis takes one column
  let used = 0;
  let out = "";
  for (const { segment } of GRAPHEMES.segment(text)) {
    const cost = stringWidth(segment);
    if (used + cost > budget) break;
    used += cost;
    out += segment;
  }
  return `${out}~`;
}
```

Two properties worth noting, because they are the ones a test should pin: the result is never wider than `width`, and it is always well-formed UTF-8. The result may be *narrower* than `width - 1` when a wide character does not fit in the last column — correct, and the reason the loop breaks rather than slices.

### 4. Tests — `packages/cli/test/cli/` (new `render.test.ts`)

Nothing exercises `truncate` today. A unit file is the right home, since this is pure:

```ts
describe("truncate", () => {
  it("never cuts a character in half", () => {
    for (const text of ["😀😀😀😀", "👨‍👩‍👧 team", "認証が失敗する", "éclair"]) {
      for (let width = 1; width <= 12; width++) {
        const cut = truncate(text, width);
        assert.equal(Buffer.from(cut, "utf8").toString("utf8"), cut, `${text} @ ${width}`);
      }
    }
  });

  it("never exceeds the width it was given", () => {
    for (const text of ["😀😀😀😀", "認証が失敗する", "plain ascii text"]) {
      for (let width = 1; width <= 12; width++) {
        assert.ok(stringWidth(truncate(text, width)) <= width, `${text} @ ${width}`);
      }
    }
  });

  it("keeps a ZWJ sequence whole or drops it", () => {
    // 👨‍👩‍👧 is one grapheme of two columns: at width 3 it fits beside the
    // ellipsis, at width 2 it does not and nothing of it is kept.
    assert.equal(truncate("👨‍👩‍👧 team", 3), "👨‍👩‍👧~");
    assert.equal(truncate("👨‍👩‍👧 team", 2), "~");
  });
});
```

And one listing-level case in `packages/cli/test/cli/issue.test.ts`, since the path people actually hit is a narrow table rather than the function: open an issue titled with an emoji and a CJK phrase, render with `COLUMNS` small, assert the output round-trips through UTF-8 and that every row is the same width.

### 5. The spec sentence this changes — `doc/spec/05-implementation.md` §5.2

> **Dependencies:** deliberately minimal. A YAML parser (`yaml`) in the core and an argument parser in the CLI; no framework.

That sentence is already approximate — the CLI also carries `picocolors` — and adding `string-width` makes it wrong enough to be worth mending. Suggested:

```diff
-- **Dependencies:** deliberately minimal. A YAML parser (`yaml`) in the core
-  and an argument parser in the CLI; no framework.
+- **Dependencies:** deliberately minimal. A YAML parser (`yaml`) in the core;
+  an argument parser, a colour library and a Unicode width table in the CLI;
+  no framework. The CLI's three are presentation rather than format, which is
+  why they are there and not in the core: a second implementation reproduces
+  the format function-for-function and is free to lay out its own tables.
```

That last clause is the justification the rule asks for, and it is the honest one.

### 6. Rust parity

Worth writing down here so the rewrite does not have to rediscover it: `unicode-width` is the same UAX #11 data, and `unicode-segmentation` gives grapheme clusters. The algorithm above ports directly. The conformance suite does not and should not assert table layout — spec 05 §5.4's fixtures are about the format — so parity here is a matter of the two CLIs looking the same, not of passing a test.

### 7. Order of work

1. Add the dependency; `pnpm install` and check the lockfile diff is the three packages and nothing else.
2. `displayWidth`, then `truncate`.
3. `render.test.ts`; then the listing-level case.
4. Spec 05 §5.2 sentence.
5. `pnpm check`, full suite, `pnpm test:conformance` (unaffected, but it renders tables).

### Risks

- **Column output shifts for non-ASCII titles.** That is the fix, but any test asserting exact table bytes for such a title will move. I found none — the non-ASCII in the CLI tests is in test names and comments only.
- **`shrinkToFit` arithmetic is unchanged** and still reasons in the same units, since it only ever adds and subtracts `displayWidth` results. Worth re-reading once with wide characters in mind, but I see no change needed.
- **ESM-only dependency.** Everything here is already `"type": "module"`, so no issue; noted only because `strip-ansi@7` is the version that dropped CJS and it is a common trip-up in mixed builds.

### Done when

`truncate("😀😀😀😀", 2)` no longer produces a lone surrogate, a table with a CJK title has aligned columns, and `nav issue list` piped to a file is well-formed UTF-8 for every title the tracker can hold.
