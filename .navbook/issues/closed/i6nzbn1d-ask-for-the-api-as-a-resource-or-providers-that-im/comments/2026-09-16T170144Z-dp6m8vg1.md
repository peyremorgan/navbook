Confirmed, against the sources of `@better-auth/oauth-provider` 1.5.6 and `oidc-client-ts` 3.5.0 (the version in the lockfile). One more finding changes the fix: **putting `resource` in the `UserManager` settings is not enough, because refreshes still leave it out.**

## Better Auth reads `resource` at the token endpoint, on every grant

`dist/index.mjs`:

```js
async function checkResource(ctx, opts, scopes) {
	const resource = ctx.body.resource;            // token request body only
	const audience = typeof resource === "string" ? [resource] : resource ? [...resource] : void 0;
	if (audience) {
		if (scopes.includes("openid")) audience.push(`${ctx.context.baseURL}/oauth2/userinfo`);
		const validAudiences = new Set([...opts.validAudiences ?? [ctx.context.baseURL], /* userinfo */]);
		for (const aud of audience) if (!validAudiences.has(aud)) throw new APIError("BAD_REQUEST", {
			error_description: "requested resource invalid", error: "invalid_request" });
	}
	return audience?.length === 1 ? audience.at(0) : audience;
}
async function createUserTokens(ctx, opts, ...) {
	const audience = await checkResource(ctx, opts, scopes);
	const isJwtAccessToken = audience && !opts.disableJwtPlugin;
```

`createUserTokens` is what both `handleAuthorizationCodeGrant` (line 569) and `handleRefreshTokenGrant` (line 724) return, so the rule applies to the code exchange **and** to every refresh. Nothing from the authorization request is carried over. The token endpoint's schema takes `resource: z.string().optional()`, so it has to be one string, not a list.

## Where oidc-client-ts puts each setting

- `settings.resource` goes on the **authorization URL** only (`SigninRequest.create`, `searchParams.append("resource", r)`).
- `settings.extraTokenParams` is stored in the signin state and spread into the **code exchange** (`_processCode` → `exchangeCode({ ..., ...state.extraTokenParams })`).
- A **refresh** takes neither from settings. `UserManager.signinSilent(args)` passes only `requestArgs.resource` and `requestArgs.extraTokenParams`. Both callers in our app pass no arguments: `useAuth().renew()` (`packages/web/app/composables/useAuth.ts:52`) and the library's own `SilentRenewService` (turned on by `automaticSilentRenew: true`) both call `signinSilent()`.

## Repro

A Node script drives the plugin's exact `UserManager` settings against a stub provider. The stub logs every token request and applies Better Auth's rule (a JWT only if the body has `resource`):

```
== current settings (extraQueryParams: { audience })
GET /authorize => { audience: 'navbook', resource: null }
POST /token => { grant_type: 'authorization_code', redirect_uri, code, code_verifier, client_id: 'navbook-web' }
  code exchange handed back: opaque-string
POST /token => { grant_type: 'refresh_token', refresh_token, scope, client_id: 'navbook-web' }

== settings + resource: 'navbook', extraTokenParams: { resource: 'navbook' }
GET /authorize => { audience: 'navbook', resource: 'navbook' }
POST /token => { grant_type: 'authorization_code', ..., resource: 'navbook', client_id: 'navbook-web' }
  code exchange handed back: eyJ.jwt
POST /token => { grant_type: 'refresh_token', refresh_token, scope, client_id: 'navbook-web' }   <- no resource
```

So the settings-only fix works for about an hour. Then the first renewal swaps the JWT for an opaque token, and every operation gets `UNAUTHENTICATED` again.

Steps against a real deployment:
1. Configure the client with `oidc.audience` set to one of the provider's `validAudiences`, and sign in.
2. Paste the access token from `sessionStorage` (`oidc.user:<issuer>:<client>`) into jwt.io. It is not a JWT.
3. Every GraphQL request gets `UNAUTHENTICATED` / "the bearer token was not accepted" (`packages/server/src/auth.ts:71`), and the UI gives no reason.

## What the fix needs, beyond the issue text

- `resource` on the refresh too. Every `signinSilent` call has to pass it, including the one inside `SilentRenewService` that we don't control. A small `UserManager` subclass whose `signinSilent` defaults `resource` covers both callers.
- The dev issuer should read `resource` on the token request for both grants, the way Better Auth does, not only on `/authorize`. Otherwise the e2e suite can't catch a refresh that drops it.
