Landed across every layer, with the shape the issue described.

`reviewer:` on `pr.md` is the whole request, and nothing records it answered — spec 02 §2.7 now says why: a key the reviewer's own commit had to clear would put every review into the file the author is editing, and manufacture the conflict of §3.3 out of two actions that do not contradict each other. Verified rather than assumed: a review racing a metadata edit merges clean, and two people editing `reviewer:` at once conflicts, which is the honest cost of the trade.

Everything outstanding is derived against the latest revision, so appending one asks everybody again by construction. `verdict: comment` joins the vocabulary as the review that judges nothing, and `nav pr review` writes it when no flag names a verdict.

`nav pr request`, three query terms, `updatePr` with the derived fields, and in the browser a reviewers panel, a decision badge and an "awaiting me" switch.

Three faults turned up on the way and were fixed here rather than left:

- `nav pr request` wrote whatever it was handed, so asking a team by name left a file the next `nav doctor` called broken.
- The client labelled the *first* revision as the latest, though `revisions:` is append-only.
- The end-to-end fixture bound its review to a SHA the pull request never recorded, which is a D6 fault.

Covered by 34 unit tests on the derived state alone, plus CLI, API and browser suites, and five conformance fixtures — among them the one that pins the subtlest rule: a pull request's author approving their own change counts for nothing.
