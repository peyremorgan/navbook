Confirmed on `dev` at b94e0bf, from the code and against the live deployment. (The prompt that reported this named #en1bjq9j, which is the closed merge/sync-source issue; nothing about logout was filed on any ref, so this issue is new.)

## Repro

1. Sign in on https://tracker.infra.brickcode.tech/ through `auth.brickcode.tech`.
2. Account menu → **Sign out**. The page reads "You are signed out" — the token is gone from `sessionStorage`.
3. **Sign in again**. The browser goes to `https://auth.brickcode.tech/api/auth/oauth2/authorize?...`, which still has its session cookie, redirects straight back to `/auth/callback` with a code, and the same account is signed in. No login form, no account picker.

## Why

`logout` in `packages/web/app/composables/useAuth.ts` deliberately never talks to the provider:

```ts
async logout() {
  // `removeUser` rather than `signoutRedirect`: ending the session at the
  // provider is the provider's business, and one without an end-session
  // endpoint would refuse anyway.
  await manager.removeUser();
  await navigateTo(SIGNED_OUT);
},
```

The `/signed-out` page (`app/pages/signed-out.vue`) was added to keep the provider from signing the person back in immediately, but it only puts that off by one click: its button calls `auth.login('/issues')`, a normal `signinRedirect`, and the provider's cookie does the rest.

The comment's premise doesn't apply to this deployment. The provider behind `config.json` advertises an end-session endpoint:

```console
$ curl -s https://tracker.infra.brickcode.tech/config.json | jq .oidc.discoveryUrl
"https://tracker.infra.brickcode.tech/oidc/openid-configuration"
$ curl -s https://tracker.infra.brickcode.tech/oidc/openid-configuration | jq '{issuer, end_session_endpoint, backchannel_logout_supported}'
{
  "issuer": "https://auth.brickcode.tech/api/auth",
  "end_session_endpoint": "https://auth.brickcode.tech/api/auth/oauth2/end-session",
  "backchannel_logout_supported": true
}
$ curl -s 'https://auth.brickcode.tech/api/auth/oauth2/end-session'
{"error":"invalid_request","error_description":"No active session is available for logout"}
```

`oidcSettings` in `app/utils/oidc.ts` already sets `post_logout_redirect_uri: origin`, but nothing ever uses it.

The e2e test "stays signed out after signing out" (`test-e2e/auth.spec.ts`) passes anyway, because `script/dev-issuer.ts` keeps no browser session: every `/authorize` shows the form. The test checks that the token is gone, not that the provider forgot the person.

## What Better Auth needs for RP-initiated logout

Read from `@better-auth/oauth-provider@1.7.5` (`rpInitiatedLogoutEndpoint`, `dist/authorize-*.mjs`):

- **`id_token_hint`** whose `sid` matches the browser's current session. The session is then deleted, the cookie cleared, and the browser redirected with no prompt. Without a hint, or with one for a different session, Better Auth shows its own confirmation page first. oidc-client-ts's `signoutRedirect` sends the stored `id_token` as the hint automatically.
- **`enableEndSession: true`** on the OAuth client (`enable_end_session`). Without it the endpoint answers `invalid_client` / "The client is not allowed to initiate logout".
- **`post_logout_redirect_uri` registered exactly** in the client's `postLogoutRedirectUris`. Otherwise the session still ends, but the browser stays on Better Auth's "logged out" page ("The requested post-logout redirect was not registered.") and never returns to the tracker.

The last two are configuration on the `auth.brickcode.tech` side for client `T1y-iamUXb2zretUpY1bN2TCJHu1fATi`. I can't see from here whether they're set.

## Fix direction

In `logout`, when the provider's metadata has an `end_session_endpoint`, call `signoutRedirect` with `post_logout_redirect_uri` set to `<origin>/signed-out`. It removes the stored user first, sends `id_token_hint`, and the provider returns to the page that already exists. A provider without the endpoint keeps the current `removeUser` + navigate. Two details:
- `extraQueryParams` (`audience`) is a default oidc-client-ts also puts on the end-session URL, so pass it empty there.
- The `/signed-out` page should consume the `state` the provider sends back, so it doesn't sit in the address bar or in storage.

The dev issuer should gain an end-session endpoint too, so the e2e flow goes through it. The web README should list `enableEndSession` and the registered post-logout URI among what the provider has to do.
