The plugin system is in, and proved by two probe plugins rather than by the knowledge base.

**What landed.** A plugin is an npm package; a repository declares which it uses in `navbook.json`; each machine installs them explicitly. Contributions are declared in the package's `navbook` key, and a host builds its command tree, help, completions and schema from that alone.

- **core** (364f286) reads both documents, and accepts registrations: tree locations, frontmatter keys, query terms, doctor checks, commit scopes. It still knows no plugin's name and loads nothing.
- **cli** (5032b34) has the per-user store, the four `nav plugin` verbs, and commands built from manifests. An installed plugin costs a listing it does not contribute to nothing at all — measured, not assumed.
- **server** (463ee61) merges plugin SDL and resolvers into one schema, validates `NAV_SERVER_<SHORT>_*` at startup, runs services for as long as the process, and emits one event per committed mutation. That is where the chat bridges go.
- **web** (7d616be) merges a plugin's Nuxt layer at build time and gives it somewhere to appear: nav links, detail panels, form fields, filter chips, row badges, inbox groupings.
- **deployment** (eebb45a) carries `NAVBOOK_PLUGINS` into both images as a build argument, since a plugin is part of an image rather than something a restart can change.

**What did not.** #dgure4qm, extracting the knowledge base, which that issue explains.

**One departure from the plan**, recorded in 780c315: D13 and D14 keep their numbers rather than becoming `X-kb-1`/`X-kb-2`. The conformance fixtures assert check codes and every implementation must pass them, so renaming would have forked the suite between this implementation and the Rust rewrite, which will have features built in long before it has plugins.
