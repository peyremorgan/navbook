Confirmed on dev at `2a881d1` (after the plugin merge), in this repository with 312 files indexed under `.navbook/`.

```console
$ GIT_TRACE=trace.log node packages/cli/src/main.ts doctor --staged
$ grep 'trace: built-in' trace.log | sed -E 's/.*built-in: git ([a-z-]+).*/\1/' | sort | uniq -c
      1 ls-files
      1 rev-parse
    312 show
$ time node packages/cli/src/main.ts doctor --staged     # three runs
3093 ms, 3454 ms, 3673 ms       (nav --version alone: ~340 ms)
```

The cause is unchanged since the issue was filed: `stagedRepo` (`packages/core/src/ops/doctor.ts:121`) calls `stagedContent` (`packages/core/src/git/index-ops.ts:17`, `git show :<path>`) once per indexed path, and the hook runs it on every commit (`packages/cli/src/install/hook.ts`, `nav doctor --staged || navbook_status=$?`).

**Plan for the fix, covering both parts of the suggestion:**

- One `git cat-file --batch-check` over `:<path>` gives each staged blob's name, type and size. A path with no blob at stage 0 (a staged deletion, the `stagedPaths` fallback) answers `missing` and is left out, exactly as a failing `git show` left it out.
- One `git cat-file --batch` reads every blob up to 1 MiB. Anything larger is read on its own, and only when `parseTree` asks for it. So a large report under §2.12, or an image, is listed in `reserved` and never read.
- `catBlobs` swallows a failed batch and returns `{}`. That is tolerable for the ref scan, but the hook would then judge an empty tree and pass it. The staged reader throws instead.
- A path containing a newline (legal in git) cannot go through the line-based batch, so it is read with `git show` on its own.
