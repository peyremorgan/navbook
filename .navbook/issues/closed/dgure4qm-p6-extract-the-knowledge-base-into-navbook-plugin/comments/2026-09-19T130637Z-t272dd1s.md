Not started. P0 through P5 landed (364f286 through eebb45a); this phase did not.

I began it — the package skeleton, the manifest declaring every contribution, and the `specs/` tree location ported behind a registered seam — and removed that work rather than commit it half-done. An extraction is all-or-nothing: core, the CLI, the server and the web client all hold feature code, and a tree where half of it has moved is a tree where features are defined twice and the registration collides with the built-in.

What it needs, in the order it wants doing:

1. **core** — port `ops/feature.ts` (374 lines) and remove the feature parts of `tree.ts`, `files.ts`, `ops.ts`, `query.ts`, `validate.ts`, `json.ts` and `workspace/resolve.ts`.
2. **cli** — move `commands/feature.ts` (288 lines) and the wiring in `program.ts` and `complete.ts`.
3. **server** — move `resolvers/feature.ts`, the four feature mutations, the `patch.ts` handling and every `Feature`/`Spec`/`Commit` line of `schema.graphql`, with the plugin taking its own codegen over both SDLs.
4. **web** — around 25 files, and the deepest coupling: the `ENTITY_CORE` fragment carries `features`, the inbox facets by them, `filter-params` and `patch` know the key, and both detail pages edit it. The slots added in P4 are what it lands on.
5. **fixtures** — 12 conformance cases move, and the harness needs a `plugins:` field; they keep asserting D13 and D14, which is why those numbers did not change.
6. **the rest** — a pack step in the server Dockerfile for a workspace plugin, the release workflow, and this repository's own `navbook.json` declaring the plugin.

Nothing found while starting it contradicts the design. The seams the earlier phases added are the ones this needs, and the two probe plugins already exercise every one of them.
