Confirmed on `dev` at `1f34c63`, with the checkout's own CLI (`node packages/cli/src/main.ts`) in a throwaway repository: one feature `auth` and one issue filed against it, so two commits touch it.

```console
$ nav feature show auth --commits 10 | tail -3
recent commits (2):
  88b0544b  docs(issue): open …
  efc1afec  docs(feature): create auth

$ nav feature show auth --commits 2.5 | tail -2      # exit 0
recent commits (0):
  none
```

`abc`, `-1` and the empty string all exit 0, and each one drops the commits section entirely. That is the same output as `--commits 0`, which is the one value that should drop it. So the bug covers more than the two values in the report: every non-count value is silently read as either "omit the history" or "no history".

### One more flag with the same bug

The report says every other numeric flag already refuses. `--depth` and `--rank` do. `nav id -n/--count` does not: it parses with `Number.parseInt`, so the value is truncated before `mintIds` validates it, and only an argument with no leading digits gets refused:

```console
$ nav id -n abc
nav: --count must be a positive integer     # exit 1
$ nav id -n 2.5                             # exit 0, two IDs
rdwjnt3t
liqbp6fq
$ nav id -n 3abc                            # exit 0, three IDs
fm87ygrh
eeyysz8y
cczta173
```

That is the rounding the `--rank` comment in `program.ts` warns about. It confirms the plan's step 2: move `--count` onto the shared parser with a minimum of 1.

### The server

`Feature.commits(limit: Int! = 100)` is the API side of the same thing. GraphQL's `Int` already rules out fractions and garbage, so the only bad value that can arrive is a negative one. `commits(limit: -1)` reaches `featureCommits`, hits `if (limit <= 0) return []` (`packages/core/src/ops/feature.ts:108`), and answers `[]`. `Pr.commits` refuses the same argument with `INVALID_INPUT` (`packages/server/src/resolvers/entity.ts:142-143`, pinned by `pr-changes.test.ts` "rejects a limit that is not a count"). I'll apply the same check to `Feature.commits` in the same PR, since the fix is two lines.
