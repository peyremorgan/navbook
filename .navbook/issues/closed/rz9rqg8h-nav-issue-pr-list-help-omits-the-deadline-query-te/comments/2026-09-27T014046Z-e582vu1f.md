## Confirmed on `dev` at `22f6be6`

I reproduced this with the checkout's own CLI (`node packages/cli/src/main.ts`), not the globally installed `nav`:

```console
$ nav issue list --help | grep -c deadline:
0
$ diff <(nav issue list --help | sed -n '/^Query terms/,$p') <(nav pr list --help | sed -n '/^Query terms/,$p') && echo identical
identical
$ nav issue list deadline:none        # works, lists every undated issue
$ nav __complete issue list           # status: label: assignee: author: milestone: feature: deadline: …
$ nav __complete pr list              # status: label: … reviewer: review: awaiting:   (no deadline:)
$ nav pr list deadline:none
nav: 'deadline:' describes an issue; pull requests have no deadline      (exit 1)
$ nav issue list reviewer:x@y.z
nav: 'reviewer:' describes a pull request; issues have no reviews        (exit 1)
```

Code pointers:

- `packages/cli/src/program.ts:62-77` defines `QUERY_HELP`, one string with nine terms and no `deadline:`.
- `packages/cli/src/program.ts:396` appends it to **both** `list` commands (`addSharedVerbs`), so the issue and PR help pages are byte-identical.
- `packages/core/src/core/query.ts:50-57` holds `KEYED_TERM`, `PR_ONLY_TERMS` and `ISSUE_ONLY_TERMS`, the parser's vocabulary.
- `packages/cli/src/commands/complete.ts:19-23` holds `QUERY_KEYS`, `PR_QUERY_KEYS` and `ISSUE_QUERY_KEYS`, a third hand-kept copy. It is correct per noun, and `packages/cli/test/cli/issue.test.ts:782-783` tests that.
- `doc/spec/04-cli.md:444` has the normative row, and `:457` has the rule that `nav pr list` MUST reject the term.

## One more thing the repro shows

Because the one block is shared, the help is wrong per noun in both directions, not just silent about `deadline:`. `nav issue list --help` advertises `reviewer:`, `review:` and `awaiting:`, and the issue parser refuses all three with exit 1. Once `deadline:` is added to the same block, `nav pr list --help` would advertise a term its parser refuses. The completion backend already solves this by offering each noun only its own terms. The help should do the same. That matches the "Done when" in the implementation plan above: `nav pr list --help` should not show `deadline:`, and neither page should offer a term its parser would refuse.

## Plan

I'm following the implementation plan in this thread:

- Add a `QUERY_TERMS` table in core and derive `KEYED_TERM`, `PR_ONLY_TERMS` and `ISSUE_ONLY_TERMS` from it.
- Render the help per noun from that table. The CLI keeps the wording.
- Derive the completion keys from the same table.
- Add tests that every term the parser accepts for a noun is documented and completed for that noun, and that no term it refuses is.
