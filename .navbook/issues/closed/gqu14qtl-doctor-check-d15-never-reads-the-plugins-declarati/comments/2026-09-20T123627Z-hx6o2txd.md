Two things worth adding.

**A fixture is the deliverable, not just the code.** `doc/spec/fixtures/format/invalid/` already holds `d15-review-policy/` and `d15-merge-policy/`; a `d15-plugins/` beside them is what actually holds a second implementation to the same answer, and it is the part that cannot be inferred from the prose. Worth covering all four shapes in one tree, since §2.12 says D15 reports one diagnostic per fault:

- `"plugins": ["@navbook/plugin-kb"]` — an array
- `"plugins": { "@navbook/plugin-kb": true }` — a value that is not an object
- `"plugins": null`
- a well-formed `plugins` alongside a malformed `review`, to pin that both are named

**On how strict to be about the value.** §2.12 says each value "MUST be an object carrying whatever settings that extension reads", and immediately afterwards: "Settings under a name are committed, shared and non-secret … An extension that needs a credential reads it from the environment." That second sentence is a constraint on authors rather than on validators — there is no way for `doctor` to tell a credential from a setting — so D15 should check the shape and stop there. Validating the *contents* of a plugin's settings is the plugin's business, which is what the `X-<short>-<n>` check namespace in spec 04 §4.3 exists for.

The precedent here is worth naming because Navbook is deliberately unlike it: npm and Cargo both tolerate unknown keys in a manifest silently, and both have paid for it — a mistyped `files` or a mistyped `[features]` key is a class of bug people hit repeatedly, because nothing tells them. §2.10's rule is the opposite and is better: "tools MUST ignore keys they do not recognize, and MUST NOT reject a marker for carrying them", but a key the spec *does* define must be well-formed or reported. D15 is what makes that rule real, and `plugins` is currently outside it.

Related: the `nav plugin` verbs and `@navbook/plugin-kb` are documented and unimplemented on `dev` — filed separately, since that one is tooling and this one is the format.
