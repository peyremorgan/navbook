Confirmed and profiled. I could not reach the production host or its API from this session (both are blocked for me), so the numbers below come from `nav-server` started in-process against a fixture built from this repository's own `.navbook/`, copied K times with remapped ids, and queried with the exact `Issue` document from the report. The harness is in `prof/` beside this issue (`_prof.ts`, `_issue.graphql`, `_cpusum.ts`; run it from `packages/server` with `K=25 MODE=sweep node _prof.ts`).

## Where the time goes

Every read is `sync.read(body)`: take the one process-wide mutex (`packages/server/src/lock.ts`), fetch and merge the remote if the last fetch is older than `--pull-interval-ms` (10 s by default, `packages/server/src/sync.ts:207-232`), then run `body`. For `issue(ref)` the body is `findEntity` (`packages/server/src/resolvers/query.ts:47`), which is `loadRepo(ws)` (`packages/core/src/ops/entity.ts:142`): walk the whole Navbook directory, `readFileSync` every file **including every comment of every entity**, parse every frontmatter with `yaml`, hash every entity file (`packages/core/src/workspace/workspace.ts:53-96`, `packages/core/src/core/tree.ts:183`). Then the `parent` and `subtasks` fields call `ctx.repo()` (`packages/server/src/resolvers/entity.ts:96-104`), which is a second, independent `loadRepo(ws)` of the same tree (`packages/server/src/context.ts:92`), because the query resolver's load is not handed to the context memo. So one `Issue` request parses the tree twice, and all of it is synchronous on the event loop.

CPU profile of the warm path at K=25 (673 entities, 1 858 files), inclusive time:

| where | share |
|---|---|
| `loadRepo` | 63 % |
| of which `readNavTree` (fs walk + `readFileSync`) | 33 % |
| of which `parseTree` → `parseDoc` → `yaml.parseDocument` | 31 % (yaml alone 21 %) |
| first load, from `findEntity` | 26 % |
| second load, from `ctx.repo()` | 25 % |
| `spawnSync` git (harness seeding + `git hash-object` free: hashes are computed in JS) | 12 % |

The other queries the issue page fires at the same time do the same thing: `issues` loads the tree (without comments), `features` loads it once for the list and once more through `ctx.repo()` for each feature's `issues`/`prs` fields, `people` loads it for `treePeople` plus a cached `git log`. They all queue behind the same mutex, so a page load is the sum of four or five full parses, and the first of them also pays the fetch.

## Measurements

Local origin (fetch ≈ 20 ms), default 10 s pull interval, `Issue` query alone then the five queries the issue page fires concurrently (`Viewer`, `Issue`, `Issues`, `Features`, `People`):

| tree | `loadRepo(all)` | `Issue` warm | page load, first request after idle | page load, warm |
|---|---|---|---|---|
| 41 entities / 106 files (this repo) | 30–40 ms | 60–80 ms | 220 ms | 190 ms |
| 276 entities / 763 files | 150–200 ms | 340 ms | 1.06 s | 1.03 s |
| 680 entities / 1 858 files | 350–470 ms | 570–720 ms | 2.45 s | 1.8 s |

The cost is linear in the number of files, about 0.2 ms per file per load, and each request pays it twice. Spec 05 §5.2 budgets 500 ms for a cold 1 000-issue `nav issue list`; the server spends more than that on one `Issue` page at 700 issues.

Simulated network fetch of 800 ms (origin reached through `ext::` with a `sleep`; a real `git fetch` from this machine to GitHub takes about 530 ms, the production fetch to `git.infra.brickcode.tech` I could not measure):

| scenario | `Issue` | page load |
|---|---|---|
| 41 entities, first request after 10 s idle | 960 ms | 1.07 s |
| 276 entities, first request after 10 s idle | 1.32 s | 1.92 s |
| 41 entities, `--pull-interval-ms 0` (every read fetches) | 940–980 ms each | 3.6 s (each query pays its own fetch, serialized) |

So "several seconds" is the expected outcome of the current design on a repository of a few hundred issues behind a remote a few hundred milliseconds away: fetch + N × (walk + parse everything) serialized behind one lock.

## Options

Ordered by value for effort; the first two together remove almost all of the parse cost.

1. **Memoize the parsed tree across requests, keyed on HEAD.** The server owns its clone, checks it clean at startup, and only `RepoSync` moves it (fetch/merge, commit). `AuthorCache` (`packages/server/src/people.ts`) already does exactly this for `git log`: remember the result against the sha it was read at, and the sha is the whole invalidation. A `Repo` memo keyed on `resolveSha(HEAD)` taken inside the read transaction, dropped on every write, is the "derived, disposable, uncommitted" index spec 06 §6.6 allows. Reads between changes then cost one `git rev-parse` instead of a full parse. This is the fix that makes page loads cheap.
2. **One load per request.** Have `Query.issue`/`Query.issues`/`Query.features` load the tree under the transaction and seed `ctx.repo()`'s memo with it (or resolve the ref against `ctx.repo()` directly) instead of loading once in `findEntity` and again in the field resolvers. Halves `Issue` and `Features` even without (1).
3. **Read only the comments the request needs.** `findEntity` asks `loadRepo` for every entity's comments to return one entity's; `ReadTreeOptions.comments` already has `all|prs|none`, and a scope for one entity (or lazy comment loading on `EntityRecord`) would cut the walk to roughly `loadRepo(none)` cost. With (1) this matters less.
4. **Take the fetch off the request path.** The first request after `pullIntervalMs` of quiet pays a network round trip while holding the lock. A background timer that fetches every interval (and merges under the lock) keeps reads from ever waiting on the network, at the same staleness bound the interval already promises; mutations keep their forced pull. Cheapest immediate mitigation on prod without a code change: raise `NAVBOOK_PULL_INTERVAL_MS` (e.g. 60000), which reduces how often the fetch is paid but not its cost when it is.
5. **Stop blocking the loop.** `readNavTree` is `readdirSync`/`readFileSync`; at 1 858 files that is ~400 ms during which `/health` and token refusals stall too. An async walk (`fs.promises` with bounded concurrency) or moving the parse to a worker would keep the process answerable, and is orthogonal to the above.
6. **Cheaper frontmatter parsing** (`yaml` is a fifth of the time). Only worth it after (1), since a memo makes parse a once-per-change cost.

Not an option: a committed index. Spec 06 §6.6 rules it out and nothing above needs one.
