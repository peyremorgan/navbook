Confirmed on `dev` at 90e8ff2, against a server spawned by the suite's own harness (`packages/server/test/helpers/harness.ts`), so the same JWKS path a deployment takes. A token the stub issuer signs for an address it has never seen before both reads and writes, and the commit lands on the origin under that name:

```console
$ node repro.ts     # signs { name: "Some Registrant", email: "stranger@elsewhere.invalid" }
viewer as stranger: {"name":"Some Registrant","email":"stranger@elsewhere.invalid"}
openIssue as stranger: {"issue":{"id":"bdifsbm9","author":"Some Registrant <stranger@elsewhere.invalid>"},
                        "commit":{"committed":true,"pushed":true,"subject":"docs(issue): open #bdifsbm9"}}
startup stderr: ""
```

The last line is the third edge in the issue: nothing at startup says the deployment is open.

## Where it happens

- `packages/server/src/auth.ts`: `verify` runs `jwtVerify` with issuer, audience and a required `exp`, then `identityFrom(payload)` keeps `email` and `name` and drops the rest. There is no hook between the two where a claim could be judged, and `AuthOptions` has nothing to configure one with.
- `packages/server/src/server.ts`: `verify` is called from Yoga's `context` factory, before any resolver, which is where the policy belongs too — every operation, `viewer` and introspection included, goes through it.
- `packages/server/src/errors.ts`: `unauthenticated()` is the only auth-shaped error, and it carries `http: { status: 401 }`. A `FORBIDDEN` needs its own constructor with a 403.
- `packages/server/src/config.ts`: `OPTIONS` is a plain `parseArgs` table; a repeatable flag needs `multiple: true`, and the `read()` helper only handles single strings, so the three new options need their own reading of flag-versus-environment.
- Web, `packages/web/app/plugins/03.apollo.ts`: the error link treats only `UNAUTHENTICATED` as "sign in again", so today a `FORBIDDEN` on a read would be swallowed silently (reads are not toasted) and on a write would be a toast headed "The operation failed". Neither is the page the issue asks for, and the route middleware (`app/middleware/auth.global.ts`) has no route that is exempt from the guard except `/auth/callback` and `/signed-out`, so a "not allowed" page has to be exempted too or it would bounce to the provider.
- `packages/web/script/dev-issuer.ts` mints only `email` and `name` in the access token (and `email_verified: true` in the id token only), so nothing in development or the e2e stack carries a `roles` claim to test against; the server suite's `SignOptions` has no way to add arbitrary claims either. Both need a way to say what claims a token carries.

## On the shape of `roles`

Brickcode's provider puts an array in `roles` (the deployment that prompted this wants `d3952bfb::developer` in it); Better Auth's is a space-separated string; `scope` is always the latter. The "equals, or contains when the claim is an array or a space-separated string" rule from the issue covers all three, so one `--require-claim roles=d3952bfb::developer` is the whole policy for that deployment.

Taking this one.
