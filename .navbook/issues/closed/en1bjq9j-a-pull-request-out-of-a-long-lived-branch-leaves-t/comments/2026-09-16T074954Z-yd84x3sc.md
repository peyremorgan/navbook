Confirmed on `dev` at 257c1fd, with the CLI run from source (`node packages/cli/src/main.ts`) in a throwaway repository: `main`, a `dev` branch two commits ahead, a pull request opened from `dev` targeting `main`, then `nav pr merge` from `main`.

```console
$ git rev-list --left-right --count main...dev     # before
0	2
$ nav pr merge jy3v
Merged #jy3vjayr  .navbook/prs/merged/jy3vjayr-dev-into-main/
$ git rev-list --left-right --count main...dev     # after
1	0
$ nav pr list status:merged
#jy3vjayr  merged  main    Dev into main
$ nav pr list --all-refs
#jy3vjayr  open    main    dev   Dev into main
$ git checkout dev && git merge --ff-only main --stat
 .navbook/prs/{open => merged}/jy3vjayr-dev-into-main/pr.md | 3 +++
 rename .navbook/prs/{open => merged}/jy3vjayr-dev-into-main/pr.md (80%)
```

The same pull request reads `merged` on `main` and `open` on `dev`, and the only difference between the two branches is the archive commit.

## Where it happens

- `executePrMerge` in `packages/core/src/ops/pr.ts` fast-forwards or merges the target, then `recordMergedBlock` writes the `merged:` block and commits on the checked-out branch. Nothing looks at the source ref again after the merge. The same is true of `continuePrMerge`, so `--continue` has the gap too.
- It is independent of the strategy: after a `--no-ff` merge the source tip is a parent of the merge commit, so the source can still fast-forward to the target. Every `pr-merge` conformance fixture uses a local `feat/auth` source and would show it.
- `locatePr` (same file) already decides which ref is the source, and is the one place that knows whether it is a local branch or a remote-tracking one (`Ref.remote`), so the "local branches only" edge is available at plan time for free.
- The CLI side is only `reportMerge` in `packages/cli/src/commands/pr.ts`, which prints two lines and knows nothing about the source.

## Two things worth knowing for the fix

- `git branch -f <source> <target>` is not usable for the ref move: with git 2.55 it dies with `cannot force update the branch 'dev' used by worktree at ...` whenever the source is checked out in another worktree. `git update-ref refs/heads/<source> <new> <old>` moves the ref regardless, which is exactly the case the issue says to skip, because it would leave that worktree's index and files behind its own HEAD. So the worktree check has to be done explicitly (`git worktree list --porcelain` lists `branch refs/heads/...` per worktree) and the update done with `update-ref`, whose old-value argument also guards against the source moving between the check and the write.
- The source is only guaranteed to be an ancestor of the new target head when the merge came from the ref itself, so the fast-forward test (`merge-base --is-ancestor <source> HEAD`) belongs after the merge, not on the plan.
