The five bug fixes are all real, and four of the five are ones I would not have found without a Windows machine. The findings below are mostly about verification and consistency rather than about the fixes being wrong.

## Blocking

### `pnpm lint` fails, so CI cannot go green as it stands

`ci.yml` runs `pnpm lint` on `ubuntu-latest`. Three errors are new here — `TestStateBadge.vue` is the only one `dev` has:

```
packages/core/test/remote.test.ts:8         assist/source/organizeImports   (fixable)
packages/cli/test/cli/spawning.test.ts:41  lint/complexity/noUselessStringRaw
packages/cli/test/cli/spawning.test.ts:42  lint/complexity/noUselessStringRaw
```

`biome check --write` fixes the import order. The other two are `String.raw` on templates holding no escape sequence, so the wrapper just goes. The PR body notes `pnpm check` was not run; this is the consequence, and it is a one-command fix.

## Worth fixing before this merges

### `hermetic.ts` is not hermetic

`packages/core/test/helpers/hermetic.ts:12` sets `GIT_CONFIG_NOSYSTEM=1` and nothing else. The leakage that matters just as much is `~/.gitconfig`: Git for Windows' installer offers to write `core.autocrlf=true` globally, and a developer who took that option gets exactly the CRLF failures this preload exists to prevent. The comment above it talks only about system config, so the gap is not acknowledged either.

The repository already has the right pattern twice — `test/deploy/helpers.ts:97-98` sets `GIT_CONFIG_GLOBAL` *and* `GIT_CONFIG_SYSTEM`, and `packages/server/test/unit/git-env.test.ts:21-22` pairs `GIT_CONFIG_NOSYSTEM` with `GIT_CONFIG_GLOBAL`. Core's `exec.ts:121` passes `process.env` (and so `HOME`) straight through, so pinning the global config is the one line that closes this.

### The preload is only on `core`

Only `packages/core/package.json:43` gained the `--import`. The `cli`, `plugin-kb` and `plugin-tests` suites run real git against byte-level assertions too, and this PR claims all three now pass on Windows — but under the machine's config, not a hermetic one. Either extend it to those packages or say in the PR why they do not need it. Right now the reasoning is applied unevenly with no stated principle, which reads as an oversight rather than a decision.

### The `fileVersions` fix is unverified outside your machine

`packages/core/src/git/history.ts:77` (`if (current !== opening.from) break;`) only fires on a git that follows renames through merges without listing the merge. Local git is 2.50.1, so the existing tests around `history.test.ts:201` exercise the *old* path and the new line is dead code here. Worth knowing that the change is also cross-platform in a way the PR body does not spell out: a plain merge commit listed with no name-status fields resolves `current` back to the requested `path`, so the new check can truncate on an ordinary merge too, not only on a hidden rename. A version-gated test, or an explicit note that it is unverified outside the Windows run, would help.

### `hasScheme` and `looksLocal` have no test at all

`packages/cli/src/commands/plugin.ts:278` is one of the five bugs fixed, and the drive-letter case is only reached indirectly, through the odd-filename test whose path is a `C:\…` path solely on Windows. On Linux and macOS CI that test exercises the plain `spawnSync` path, so nothing in CI can catch a regression in the scheme logic. `spawning.test.ts` sets the precedent for exactly this — export `hasScheme` and `looksLocal` (or take a `platform` argument) and pin both.

### `taskkill` has no timeout

`packages/core/src/git/exec.ts:379` resolves only on `taskkill`'s `exit`, and the exit handler waits on it before settling at `exec.ts:300`. A `taskkill` that hangs turns the very timeout path this PR hardens into a hang. A deadline that resolves regardless would close it.

Relatedly, the grace timer at `exec.ts:250` is now a no-op on Windows: `send("SIGKILL")` reaches the `treeKilled ??=` short-circuit at `exec.ts:235` and does nothing. Harmless, but it is dead code on the only platform that sets it.

### `NO_GIT_SHIM` skips five tests for a reason this PR disproves

The stated reason is "Windows will not launch a shell script named `git`" — yet this branch adds `packages/cli/test/fixtures/fake-npm/npm.cmd`, a batch shim forwarding to node, which is exactly the technique that would recover those five (`doctor.test.ts`, `pr.test.ts`, `operations.test.ts` twice, `blobs.test.ts`). Worth attempting before permanently giving up five tests of Windows coverage. The other three skip groups — unreadable files, symlinks, process groups — are genuinely unavoidable, and naming them per-test is the right call.

### `killTree`'s reach is asserted nowhere

`assertReached` at `packages/core/test/git-async.test.ts:170` skips its assertion entirely when `ORPHANS_OUTLIVE_STOP` is set. Combined with there being no Windows CI job, that means the riskiest new production code here — `taskkill /T /F` reaching git's children — has no automated verification of any kind. The honest alternative to skipping would be to assert that *git itself* is gone, which the tree kill does guarantee.

### No Windows CI job

`ci.yml` is `ubuntu-latest` and `macos-latest` only. The pure-function cases in `spawning.test.ts` do run on Linux and are genuinely valuable — that part of the design worked. But `killTree`, `posixShell`, the `EOF` arm of `exitedEarly`, and the end-to-end odd-filename quoting all execute on one developer's machine and nowhere else. Given that this branch's entire premise is Windows behaviour, a `windows-latest` runner for `core` and `cli` is what would make it durable rather than anecdotal.

## Minor

- **`cmd.exe` is hardcoded** at `packages/cli/src/plugins/store.ts:192`. cross-spawn uses `process.env.comspec || 'cmd.exe'`; worth the same. Apart from that the escaping is a faithful reproduction of cross-spawn's cmd-shim path — I traced `CMD_META`, the double pass and the outer quoting, they match, and `spawning.test.ts:33` pins the exact output. Good work on a fiddly piece of code.
- **`posixShell` degrades silently.** At `packages/cli/src/editor.ts:42`, if `git --exec-path` ever answers MSYS-style (`/mingw64/libexec/git-core`), `join` normalises to `\bin\sh.exe`, `existsSync` reads that as `C:\bin\sh.exe`, and you fall back to `cmd.exe`. Safe, but silent.
- **Duplicated helpers.** `NO_SYMLINKS` is byte-identical at `packages/core/test/helpers/platform.ts:34` and `packages/cli/test/helpers/temprepo.ts:194`, in two partial sets that have already drifted — core also has `realTempDir`, `NO_UNREADABLE_FILES`, `POLITE_STOP`, `ORPHANS_OUTLIVE_STOP`, `PID_OF_*` and `recordInIndex`. #ra3cek1n exists because of precisely this class of duplication.
- **`.gitattributes` carve-out is incomplete.** `* text=auto eol=lf` with only `*.cmd text eol=crlf`. A future `.bat` or `.ps1` gets silently mangled on Windows. Adding them, or noting the convention, costs one line.
- **The single-letter scheme change is unstated.** The `+` in `hasScheme` means `x:foo` is no longer a URL. Real-world impact is nil, but it is a behaviour change and belongs in the PR body rather than only in a code comment.

## Pre-existing, not this branch

`plugin-tests` → *"shows the steps a run followed after the plan changed, and says when it cannot"* fails on macOS both here and on `dev`: its editor script uses `sed -i 's/…/' "$1"`, and BSD sed needs a suffix argument. Out of scope for this PR, but the README's new claim that the suites pass on Windows does not extend to it, and the Platforms section's "Developed and tested on Linux and macOS" is currently not quite true.
