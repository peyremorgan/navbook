Self-review (`/code-review high`, eight finders and a verify pass) found seven correctness problems and three cleanups in revision 1; all are answered in revision 2.

**Correctness**
- Inbox: `pending.value === held` compared Vue's reactive proxy with the raw object, so a landed drop never cleared its placement and `items` kept splicing the row for the rest of the session. The placement is now the edit `usePendingEdits` keeps (`{ placement }`), read back through `overlay`, so landing, discarding and settling clear it through one store.
- Inbox: handles were live while a refusal was kept, on a preview that no longer matched the list every drop's arithmetic reads; a second drop landed elsewhere and silently replaced the refusal. `busy` is now "any edit kept", and a kept refusal is let go when the order changes or the row leaves the list. The e2e test asserts the handles are disabled and covers Retry landing.
- A save equal to the cached value while the previous save of that field was in flight was settled as a no-op, so a revert was never sent. The patch is now built against `edits.basis(current)` — the cache with in-flight edits over it — and `settle` leaves an in-flight field alone.
- Feature card: a stale refusal kept *mine* over the refetched *theirs*, so theirs was never shown; and a rejected refetch replaced the stale failure. The page now uses `useStaleEdit` and `StaleEditAlert` exactly like the issue and PR pages (`summary` joined `EntityEdit` as a feature's field, the way `reviewers` is a PR's).
- PR reviewers: `reviewsShown` re-derived the server's rows and so fabricated PENDING rows on a plain load (the author with self-review off) and dropped a removed reviewer's verdict. It now applies only the difference a pending edit makes: PENDING rows added for the newly asked, PENDING rows dropped for the newly removed, verdicts always kept.
- `handled: true` silenced the toast for a FORBIDDEN refusal, which navigates to the not-allowed page and takes the inline alert with it; that one is toasted again. A refusal arriving after any page is left is reported through a `lost` callback (a toast) rather than dying with the page.

**Cleanups**
- The failure sentence is composed once (`sayFailure` in `utils/errors.ts`) for the toast and the inline alert; `fieldsOf` is one generic export in `utils/patch.ts` used by both composables.
- Edits and their states are two shallow stores, so the 1750 ms tick recomputes no page; `field()` hands an editor the same object until that field's own state changes (unit-tested).

Verification on revision 2: `nuxi typecheck`, biome, 344 unit tests, and the full e2e suite (139 tests; one unrelated features-index test flaked under load in the full run and passed on its own rerun).
