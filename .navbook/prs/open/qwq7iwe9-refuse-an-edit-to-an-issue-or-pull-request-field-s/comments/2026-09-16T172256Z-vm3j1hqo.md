Self-review, at Morgan's request, of the first revision (070f905): eight review passes over the diff, sixteen candidate findings verified one by one, ten kept. All ten are addressed in 947dcd4, which this review is bound to.

**Would have defeated the guard.** `Issue.baseSha` was hashed by a field resolver in its own `sync.locked()` turn, after the parent's transaction had released the FIFO lock. A write queued during a read ran in between, so the response paired old field values with the *new* hash, and an edit sent with it compared the file to itself and landed on top of the other person's — deterministically, not by chance. Fixed by giving `EntityRecord` a `blobSha` computed in-process from the exact text the record was parsed from (`core/hash.ts`, same SHA-1 as `git hash-object`, proved against git's known hashes and against `hash-object` in the server suite). The read path runs no git for it, and the resolver header can say again that nothing there reads a file.

**Server refusals.** A hash naming a real blob that was never an entity file (the marker, say) made `parseFile` throw and Yoga masked it as an internal error; now refused as stale. A `title: null` or `body: null`, which `applyEntityPatch` leaves alone, was counted as a field to refuse over; now the same predicate on both sides. A CRLF working copy compared its body unequal to the LF blob on every save; line endings are folded before comparing. A served clone somebody has edited by hand had a hash that named no object, so every save was refused with no way out; a hash equal to the current file's is now settled hash-to-hash, without git, as core's own `assertUnchanged` does.

**Client.** Any successful save cleared the kept edit, so toggling a label while deciding threw the typed title away without either button being pressed. The reapply button was live before the refetch had brought the new hash, so a quick click was refused again. The refetch's rejection escaped an event handler. And an unresolvable hash was reported as "Somebody changed the title", which is not what happened. Both pages now share `useStaleEdit`, which settles the kept edit only on a save that names its field, waits for the refetch before reapplying, swallows the refetch's own failure (the page's query state already reports it), and the alert says why in the server's own sentence. Seven unit cases cover the state machine.

**Left as is.** `isEmptyPatch` could be `namedFields(input).length === 0` but the two now differ on a null title, deliberately. The Playwright suite still has no case for the alert; its test ids are unchanged.
