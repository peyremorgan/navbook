Adversarial self-review with `/code-review high` found ten issues. I reproduced three on a fixture before fixing them, then added regression tests. Each test fails against the unfixed source and passes after (6989917):

1. **Stale worktree registration.** Every write failed with "git was not found on PATH". It now refuses with the fix: `git worktree prune`.
2. **Commit refused by a hook after the write.** The forced cleanup discarded the review the user had just written. The worktree is now kept, with its path printed.
3. **Ctrl-C in `$EDITOR`.** This left the temporary worktree registered with the branch checked out. Terminal signals are now ignored for the duration, as git does while its own editor runs, and cleanup goes through the normal failure path.

Also fixed:
- The removal fallback now prunes as well as deleting the directory.
- The write in the other worktree goes through `findPrToWrite`, with the Navbook directory already resolved.
- `mkdtemp` and long-branch-name failures are reported cleanly.
- The refusal no longer rescans every ref.
- `isTrackedTreeClean` is folded into `isTreeClean(cwd, { untracked: false })`.

Not changed:
- Without `--commit`, the only copy of the change stays in a worktree under the system temp directory, which may not survive a reboot. You asked for `mktemp`, and the run prints the path. If it is lost anyway, (1) now handles the leftover registration.
- A full `git worktree add` checkout is used rather than plumbing to write a single file. That is what was asked for, and it runs the repository's hooks, which is the point of a real checkout.
- `nav pr update` and `nav pr request` still load the tree twice when the pull request is held locally: once to locate it, once inside the core operation. Avoiding that means changing the core operations' signatures, which the server shares. I left it for a separate change.
