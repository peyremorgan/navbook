Adversarial self-review (`/code-review high`). It raised eight findings: three fixed in revision 2, five left as they are.

**Fixed** (`test(cli): pin the NAV_ROOT case, and that the host hook ran`):
- The `set -e` tests never checked that the existing hook actually ran. An installer that overwrote the hook instead of appending would have passed them. They now assert its output.
- The `NAV_ROOT=does-not-exist` case had only been checked by hand. It is now a test next to the removed-tree case. Both fail against the old block and pass against the new one.
- The format-violation test body was duplicated. It now loops over the two host hooks.

**Left, with reasons:**
- *A rerun of `nav install --hooks` does not upgrade an old block.* The installer keeps treating the marker as "installed", which the plan decided on purpose (§4). Existing installs need `nav uninstall --hooks && nav install --hooks`, as the PR description says.
- *Isolate the block with `set +e` or a subshell.* The plan also rejected this: `set +e` would change the shell for whatever is appended after the block. The block has no pipeline, so `pipefail` cannot affect it.
- *Hooks that end in `exit`/`exec`, or have a non-sh shebang.* This predates the change, and the issue doesn't cover it.
- *The audit report still describes the bug.* The report is a dated snapshot of `2ebc8ce`, and none of the nine findings fixed so far has changed it.

Verified at the pinned head: the install suite passes (18/18), with the two exit-1 cases failing when the old `hook.ts` is restored; `tsc --noEmit` and `biome check .` are clean.
