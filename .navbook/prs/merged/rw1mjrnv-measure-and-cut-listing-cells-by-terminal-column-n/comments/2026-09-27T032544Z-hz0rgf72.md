Adversarial self-review (`/code-review high`) of revision 1. It found seven issues, all fixed in 054af45, which is revision 2 after a rebase onto `dev`.

**Performance (measured, Node 24)**
- Revision 1 measured every non-ASCII cell three times, and `truncate` ran each grapheme it kept back through `string-width`, segmenting it again. 1000 Japanese titles took about 307 ms to lay out at 50 columns, a large share of spec 05's 500 ms cold-list budget; the perf suite's fixtures use ASCII titles only, so it didn't catch this. Each cell is now measured once, the cut reports its own width, and each grapheme's width is looked up once and remembered. The same listing now takes about 25 ms (no truncation: 113 → 16 ms).
- Importing `string-width` cost about 40 ms and constructing `Intl.Segmenter` about 13 ms, and every command loads `table.ts`. Both are now created on first non-ASCII use, through `createRequire` since `renderTable` is synchronous, so the module's import time is back to `dev`'s. An ASCII listing never loads `string-width`; a test hook on module resolution confirmed that.

**Correctness**
- `string-width` strips ANSI escapes and counts a tab as zero columns, so for a title holding either, the check for whether a cell already fits and the cut itself disagreed. A title with an escape sequence could come out as a bare escape, with its colour left open across the rest of the listing. Cells now go through `printable` before they are measured: tab, CR and LF become a space, and any other control character becomes U+FFFD. No escape sequence reaches the terminal from a listing now, and there are tests for both cases.
- A string is now measured as the sum of its graphemes' widths, the same way `string-width` counts, so the full-string measure and `fit` can't disagree.
- `nav feature show` padded spec file names with `padEnd(28)`; it now uses the width-aware `pad`, exported from `table.ts` and tested. The other `padEnd` sites pad fixed ASCII labels and statuses, so they were left as they are.

**Cleanups**
- The tests use `String.prototype.isWellFormed()` in place of a round trip through UTF-8.
- The decomposed "é" test string is built with `String.fromCharCode(0x301)`, because biome had written the escape out as an invisible literal.

**Checks on revision 2:** root and CLI `tsc` (development and build configurations) and `biome check .` are clean. CLI suite: 376 pass, 0 fail. Conformance: 119 pass, 0 fail. Render tests: 13 pass, and 9 of the original 10 still fail against `dev`'s `table.ts`. `nav doctor`: 0 errors, 10 warnings, the same as `dev`.

**Still not handled:** the title column's `minWidth: 20` floor can still push the header past the edge of a very narrow terminal, as on `dev`. Control characters in `nav issue show` and other non-table output are printed as written, which is outside this issue.
