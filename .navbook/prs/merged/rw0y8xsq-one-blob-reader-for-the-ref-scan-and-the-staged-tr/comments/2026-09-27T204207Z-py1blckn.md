Self-review of revision 2, head `e7cbd4f`. Ran `/code-review high` on the branch and fixed what it found in `e7cbd4f`.

**Fixed**
- **No ceiling on a read.** Sizing each batch's buffer to its blobs removed the scan's 256 MB cap and put nothing in its place. A huge `pr.md` on any fetched branch would have been read whole, then failed in V8's string limit without naming the file. `readBlobsBySha` and the staged tree's lazy `cat-file blob` now refuse anything over `MAX_READ_BYTES` (256 MB) before reading, naming it. `catBlobs` shares the constant. Test: a blob declared one byte over the limit is refused with 0 `cat-file` processes started.
- **Header parsing by position.** `catObjects` split each header on spaces and took the size from the third field. Git echoes a missing spec back verbatim, so a missing path containing spaces, `HEAD:a blob 12 z missing`, read as a 12-byte blob and shifted every later answer in the batch. This bug predates this PR: `catBlobs` has parsed headers that way since before #krc96gzg. Missing and ambiguous answers are now matched as the exact echo. Anything else must be a well-formed `<name> <type> <size>`, and when a SHA was asked for, the name must be that SHA (the staged tree's old check). Otherwise the read throws rather than misfiling a body. Two tests cover this: a space-laden missing path mid-batch, and a shim that answers with another object's header. Both fail against revision 1.
- **Context in errors.** Messages say which blobs failed again ("could not size staged blob …"), as the staged tree's own reader did.
- **Consistency.**
  - `catObjects` spawns with `gitEnv`.
  - `STAGED_READ_LIMITS.batch` is `BLOB_BATCH_BYTES` instead of a second literal.
  - `blobSizes` returns `SizedBlob[]`, and duplicates are removed once.
  - `blobs.ts` stays internal to the git layer instead of joining core's public exports.
  - The stale docs in `refscan.ts` are fixed.

**Deliberately kept**
- `catBlobs` stays path-keyed with a fixed cap. Its one caller, `countOpenPrsOnOtherRefs`, doesn't know sizes, and giving it them would mean reworking `batchResolve` beyond this refactor. The cap is now the same constant rather than a second policy.
