## What exists

`nav-server` serves one clone. Before a read it pulls, if it has not within the interval; around a write it pulls, runs the operation, commits and pushes, under one lock. A push it cannot fast-forward is retried once after a pull and then reported; a merge it cannot complete is aborted and reported. Conflicts surface; nothing is resolved on anybody's behalf (spec 06 §6.3).

- **Identity** comes from an OIDC bearer token whose `email` claim becomes `author:`; the machine account is the committer.
- **Authorization** is a policy the server is started with and applies after the token verifies, before any operation — `viewer` and introspection included: required claims (`--require-claim roles=navbook::member`, equal or contained when the claim is an array or a space-separated string), allowed email domains, and a required `email_verified`. All optional, ANDed. A verified token the policy refuses is `FORBIDDEN` with a 403, distinct from `UNAUTHENTICATED` because the person is signed in and sending them back to the provider would loop; the rule that refused them is logged, never answered. With no policy, any token the issuer signs for the audience may write, and the server warns so at start.
- **Reads** — `issues`, `issue`, `prs` (with `allRefs` for the cross-branch scan), `pr`, `features`, `feature`, `doctor`, `viewer`, `reviewPolicy`, `people`. A listing is the whole matching set; there is no pagination.
- **Reviews** — `Pr.reviewDecision` follows the policy `reviewPolicy` reports (spec 02 §2.10), and `Pr.approvals` says how many approvals it counted against how many were asked for, so a client can explain a pending badge rather than only draw one. A policy nobody can read is served, not raised: `problems` says what was wrong while every field beside it holds the default. Nothing here is a gate, and there is nothing for one to gate — merging is not exposed.
- **Revisions** — `Pr.commits` and `Pr.changes` read what the latest revision introduces from the two SHAs it pins (spec 02 §2.7): the commits `base..head`, oldest first, and the diff of `head` against `base`, which is the three-dot diff a forge shows and stays right after the target moves on. Both are read from the object store rather than from any branch, so a pull request found by `allRefs` answers as well as the served one, and neither takes the repository lock, since two immutable objects need no consistent tree. Every file of a diff is listed; patches come inline until a per-file (1,000 lines) and a whole-diff (10,000 lines) budget is spent, after which a file is asked for by `paths` (at most 20 per request), answered whatever its size and cut at 20,000 lines with `truncated` set — the numbers GitHub, GitLab and Gitea settled on. Answers are remembered process-wide under `base..head`, evicted by memory rather than by staleness because nothing can make them stale; a diff too large to keep is kept as a listing and diffed per file on request (§6.6). A revision whose commits the clone lacks is refused with `MISSING_COMMIT`. `ChangedFile.tracker` marks the tracker's own files, and `Pr.activity` lists the revision's commits that touch the tracker, merges left out, each with what it did: a verb and record read from the subject when it follows the grammar `--commit` writes, else from the commit's own files (a main file added is an open, a directory moved between statuses a close, reopen or merge, a comment added a comment or a review), a fact per frontmatter field whose value changed before and after, and the commit's tracker files with their patches. No model is involved; the same commit always reads the same.
- **People** — `people` answers who the repository knows of, for the fields that name one. Three sources merged into one entry per address (spec 02 §2.4): the authors of the served branch's history, read through `%aN`/`%aE` so `.mailmap` is git's business rather than ours; everyone the tree names as author, assignee, reviewer, merger or commenter; and the signed-in viewer. The clone's own committer is left out of the history alone — it commits on everybody's behalf (§6.2), so its name on a commit says who runs the server, while a file naming it was written by somebody and stands. That is also why the tree is a source at all: a person who has only ever worked through this API has no commits of their own. A name comes from the first source that has one, so the most recent commit names somebody before a file does. Only the history walk is kept, keyed on the HEAD it read; the tree half is the request's own read, so somebody assigned a moment ago is offered a moment later. Nothing is written down — derived, disposable and uncommitted is the one kind of index the format allows (§6.6) — and it is a suggestion rather than a registry: every person field still takes an address that is not in the list.
- **Writes** — `openIssue`, `updateIssue`, `closeIssue`, `reopenIssue`, `updatePr`, `openPr`, `addComment`, `linkIssue`, `unlinkIssue`, `createFeature`, `updateFeature`, `addSpec`, `updateSpec`. Every payload returns `commit { committed subject pushed }`, and a client is expected to say so when `pushed` is false.
- **Composing** stays on the server: a client sends fields, the server builds the file with core's constructors and validates it before anything is written.
- **Patches** distinguish absent from `null`; unknown frontmatter keys always survive. `rank` and `deadline` follow that contract too, so unplacing an issue is an explicit null and a rank of zero is a value rather than an absence.
- **Priority and dates** — `Issue.rank` and `Issue.deadline` project spec 02 §2.5, and `IssueFilter.deadline` narrows by `OVERDUE` or `NONE` against the server's own day, in UTC. Each listing takes its own filter input — `IssueFilter` for `issues`, `PrFilter` for `prs` — so a term describing something the noun does not have (`deadline` on a pull request; `reviewers`, `reviews`, `awaiting` or status `MERGED` on an issue) is refused by GraphQL validation before any resolver runs: an error, not a filter matching nothing (spec 04 §4.3). There is no sort argument, by design — an order the server owned would be the index spec 06 §6.6 refuses — so a listing arrives newest first and each front end reads it in whatever order it offers.
- **Writes on other branches** — a pull request's files live on its source branch (spec 03 §3.5). `openPr`, and `addComment` or `updatePr` on a pull request the served checkout does not hold, check out the server's own copy of that branch — `nav-server/<branch>`, made from `origin/<branch>` — into a temporary worktree of the clone, write and commit there, push it to `<branch>`, and remove the worktree. The branch written on is the one the pull request's `source:` names, and the remote's copy of it must carry the pull request: a branch that merged the source in carries it too, and is never written on instead. The branch must already be on the remote, and the push is leased on the tip the copy was merged with, so a branch deleted or moved meanwhile is refused or merged again, never made anew or written over. The copy is merged with the remote's under the served branch's rules (fast-forward, merge, or `SYNC_CONFLICT`), and kept only while it carries something the remote lacks, which the next write to the branch pushes. The clone's own local branches are never written on, pushed from or deleted — with no remote, there is nothing to copy from and the clone's branch is written on directly. The payload's `Pr.refs` names the branch written on; temporary worktrees a killed server left are removed at startup, and one a close could not remove holds its copy until the next write to that branch removes it.
- **Refusals** — `REPARENT_REQUIRED` for a link that would move a subtask; `INVALID_INPUT` for an `openPr` whose `source` or `target` is not a branch name (a revision, an option); `PRECONDITION` with `extensions.branch` for a pull-request write whose branch is not on the remote, no longer carries it, or whose copy is checked out in a worktree the server did not make, and for an `openPr` on the served or the default branch — anybody signed in may open one, and opening one commits to its source and pushes it — or one that targets its own branch, a branch not on the remote, or one it shares no history with; `STALE_CONTENT` for a document save made against a version somebody has replaced.
- **Not exposed** — appending a revision to a pull request, merging it; deleting anything; `init`; `doctor --fix`; renaming or removing a feature or document. A pull request's metadata is patchable, `reviewers` included.

## Drift from the specification

- Spec 06 §6.3 says what reaches the browser "is the canonical JSON projection of 04 §4.2". The schema is a projection of the same records but not the same shape: `assignee` becomes `assignees`, `feature` becomes `features`, statuses and kinds are uppercase enums, and pull requests carry a `refs` field the projection does not have. A reader of the API and a reader of `nav --json` are looking at the same data under different names.
