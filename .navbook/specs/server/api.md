## What exists

`nav-server` serves one clone. Before a read it pulls, if it has not within the interval; around a write it pulls, runs the operation, commits and pushes, under one lock. A push it cannot fast-forward is retried once after a pull and then reported; a merge it cannot complete is aborted and reported. Conflicts surface; nothing is resolved on anybody's behalf (spec 06 §6.3).

- **Identity** comes from an OIDC bearer token whose `email` claim becomes `author:`; the machine account is the committer.
- **Authorization** is a policy the server is started with and applies after the token verifies, before any operation — `viewer` and introspection included: required claims (`--require-claim roles=navbook::member`, equal or contained when the claim is an array or a space-separated string), allowed email domains, and a required `email_verified`. All optional, ANDed. A verified token the policy refuses is `FORBIDDEN` with a 403, distinct from `UNAUTHENTICATED` because the person is signed in and sending them back to the provider would loop; the rule that refused them is logged, never answered. With no policy, any token the issuer signs for the audience may write, and the server warns so at start.
- **Reads** — `issues`, `issue`, `prs` (with `allRefs` for the cross-branch scan), `pr`, `features`, `feature`, `doctor`, `viewer`, `reviewPolicy`, `people`. A listing is the whole matching set; there is no pagination.
- **Reviews** — `Pr.reviewDecision` follows the policy `reviewPolicy` reports (spec 02 §2.10), and `Pr.approvals` says how many approvals it counted against how many were asked for, so a client can explain a pending badge rather than only draw one. A policy nobody can read is served, not raised: `problems` says what was wrong while every field beside it holds the default. Nothing here is a gate, and there is nothing for one to gate — merging is not exposed.
- **Revisions** — `Pr.commits` and `Pr.changes` read what the latest revision introduces from the two SHAs it pins (spec 02 §2.7): the commits `base..head`, oldest first, and the diff of `head` against `base`, which is the three-dot diff a forge shows and stays right after the target moves on. Both are read from the object store rather than from any branch, so a pull request found by `allRefs` answers as well as the served one, and neither takes the repository lock, since two immutable objects need no consistent tree. Every file of a diff is listed; patches come inline until a per-file (1,000 lines) and a whole-diff (10,000 lines) budget is spent, after which a file is asked for by `paths` (at most 20 per request), answered whatever its size and cut at 20,000 lines with `truncated` set — the numbers GitHub, GitLab and Gitea settled on. Answers are remembered process-wide under `base..head`, evicted by memory rather than by staleness because nothing can make them stale; a diff too large to keep is kept as a listing and diffed per file on request (§6.6). A revision whose commits the clone lacks is refused with `MISSING_COMMIT`.
- **People** — `people` answers who the repository knows of, for the fields that name one. Three sources merged into one entry per address (spec 02 §2.4): the authors of the served branch's history, read through `%aN`/`%aE` so `.mailmap` is git's business rather than ours; everyone the tree names as author, assignee, reviewer, merger or commenter; and the signed-in viewer. The clone's own committer is left out of the history alone — it commits on everybody's behalf (§6.2), so its name on a commit says who runs the server, while a file naming it was written by somebody and stands. That is also why the tree is a source at all: a person who has only ever worked through this API has no commits of their own. A name comes from the first source that has one, so the most recent commit names somebody before a file does. Only the history walk is kept, keyed on the HEAD it read; the tree half is the request's own read, so somebody assigned a moment ago is offered a moment later. Nothing is written down — derived, disposable and uncommitted is the one kind of index the format allows (§6.6) — and it is a suggestion rather than a registry: every person field still takes an address that is not in the list.
- **Writes** — `openIssue`, `updateIssue`, `closeIssue`, `reopenIssue`, `updatePr`, `addComment`, `linkIssue`, `unlinkIssue`, `createFeature`, `updateFeature`, `addSpec`, `updateSpec`. Every payload returns `commit { committed subject pushed }`, and a client is expected to say so when `pushed` is false.
- **Composing** stays on the server: a client sends fields, the server builds the file with core's constructors and validates it before anything is written.
- **Patches** distinguish absent from `null`; unknown frontmatter keys always survive. `rank` and `deadline` follow that contract too, so unplacing an issue is an explicit null and a rank of zero is a value rather than an absence.
- **Priority and dates** — `Issue.rank` and `Issue.deadline` project spec 02 §2.5, and `EntityFilter.deadline` narrows by `OVERDUE` or `NONE` against the server's own day, in UTC. `prs` refuses that filter as `issues` refuses the three review terms: a term describing something the noun does not have is an error, not a filter matching nothing. There is no sort argument, by design — an order the server owned would be the index spec 06 §6.6 refuses — so a listing arrives newest first and each front end reads it in whatever order it offers.
- **Refusals** — `REPARENT_REQUIRED` for a link that would move a subtask, `PRECONDITION` for a comment or a patch on a pull-request branch this clone does not serve, `STALE_CONTENT` for a document save made against a version somebody has replaced.
- **Not exposed** — opening a pull request, appending a revision to one, merging it; deleting anything; `init`; `doctor --fix`; renaming or removing a feature or document. A pull request's metadata is patchable, `reviewers` included.

## Drift from the specification

- Spec 06 §6.3 says what reaches the browser "is the canonical JSON projection of 04 §4.2". The schema is a projection of the same records but not the same shape: `assignee` becomes `assignees`, `feature` becomes `features`, statuses and kinds are uppercase enums, and pull requests carry a `refs` field the projection does not have. A reader of the API and a reader of `nav --json` are looking at the same data under different names.
